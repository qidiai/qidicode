# 严格代码质量审查

使用此技能进行异常严格的审查，重点关注实现质量、可维护性、抽象质量和代码库健康状况。

最重要的是，此技能应推动审查者在代码结构上追求**雄心**。不要仅仅识别本地清理机会。积极寻找"代码柔道"动作：在保留行为的同时，使实现变得更简单、更小、更直接、更优雅的重组。

## 核心提示

从此基线开始：

> 对当前分支的更改进行深度代码质量审计。
> 重新思考如何构建/实现这些更改，以显著提高代码质量而不影响行为。
> 致力于改进抽象、模块化，减少意大利面条式代码，提高简洁性和可读性。
> 要有雄心，如果存在明确的改进实现路径且涉及重组部分代码库，那就去做。
> 极其彻底和严谨。三思而后行。

## 不可协商的附加标准

应用上述基线提示，加上这些明确的审查规则：

0. **在结构简化方面要有雄心。**
   - 不要停留在"这可以更干净一点"。
   - 寻找机会重构更改，使整个分支、辅助函数、模式、条件或层完全消失。
   - 优先选择事后让代码感觉不可避免的解决方案。
   - 假设通常存在可用的"代码柔道"动作：一种更有效地利用现有架构的重组，使更改更简单、更优雅。
   - 如果你看到一条删除复杂性而非重新排列它的路径，大力推动选择该路径。

1. **不要让 PR 将文件从 1000 行以下推到 1000 行以上，除非有非常充分的理由。**
   - 默认将此视为强烈的代码质量异味。
   - 优先提取辅助函数、子组件、模块或本地抽象，而不是让文件蔓延超过 1000 行。
   - 如果差异跨越该阈值，明确询问是否应首先分解代码。
   - 仅在有令人信服的结构原因且结果文件仍然组织清晰时才豁免此规则。

2. **不允许现有代码中随机意大利面条式增长。**
   - 对新即席条件、分散的特殊情况或插入不相关流程的单次分支保持高度怀疑。
   - 如果更改添加了"随机位置的奇怪 if 语句"，将其视为设计问题，而非风格吹毛求疵。
   - 优先将逻辑推入专用抽象、辅助函数、状态机、策略对象或独立模块，而不是将现有路径纠缠在一起。
   - 指出使周围代码更难推理的更改，即使它们在技术上有效。

3. **倾向于清理设计，而不仅仅是接受可工作的代码。**
   - 如果行为可以保持不变而结构变得更干净，推动选择更干净的版本。
   - 不要对"能用"的实现盖橡皮章，而这些实现让代码库更混乱。
   - 强烈偏好完全消除运动部件的简化，而非仅仅将相同复杂性分散开来的重构。

4. **优先选择直接、无聊、可维护的代码，而不是 hacky 或神奇的代码。**
   - 将脆弱、即席或"神奇"行为视为代码质量问题。
   - 对隐藏简单数据形状假设的通用机制保持怀疑。
   - 标记薄抽象、身份包装器或不增加清晰度的直通辅助函数。

5. **在影响可维护性时大力推动类型和边界整洁性。**
   - 当存在更清晰的类型边界时，质疑不必要的可选性、`unknown`、`any` 或大量强制转换的代码。
   - 优先选择显式类型化模型或共享契约，而非松散形状的即席对象。
   - 如果一个分支依赖静默回退来掩盖不清晰的不变量，请问是否应该使边界显式化。

6. **将逻辑保留在规范层中并重用现有辅助函数。**
   - 指出功能逻辑泄露到共享路径中，或实现细节通过 API 泄露。
   - 优先选择现有的规范实用程序/辅助函数，而不是定制的一次性函数。
   - 将代码推向正确的包、服务或模块，而不是默认接受架构漂移。

7. **当更清晰的结构显而易见时，将不必要的顺序编排和非原子更新视为设计异味。**
   - 如果独立工作无缘无故地被序列化，请问流程是否应该并行运行。
   - 如果相关更新可以使状态处于半应用状态，请推动更原子的结构。
   - 不要过度关注微优化，但确实要标记那些使实现更脆弱的可避免编排复杂性。

## 主要审查问题

对于每个有意义的更改，请问：

- 是否存在一个"代码柔道"动作，使这变得 dramatically 更简单？
- 此更改是否可以重构，以便需要更少的概念、分支或辅助层？
- 这是改善还是恶化了本地架构？
- 差异是否在应该有更好抽象的地方添加了分支复杂性？
- 以前内聚的模块是否变得更耦合、更有状态或更难扫描？
- 此逻辑是否存在于正确的文件和层中？
- 此更改是否将文件或组件扩大到超过健康大小边界？
- 是否有重复的条件表明缺少模型或辅助函数？
- 实现是直接和可读的，还是依赖于特殊情况和偶然控制流？
- 此抽象是否真正值得保留，还是仅仅是一个包装器？
- 差异是否引入了强制转换、可选性或即席对象形状，从而掩盖了真正的不变量？
- 此逻辑是否存在于规范层中，还是差异跨越边界泄露了细节？
- 此编排是否比必要的更顺序化或更少原子性？

## 要积极标记的内容

当你看到以下情况时提升发现级别：

- 复杂的实现，而更清晰的重构可以删除整个类别的复杂性。
- 重构移动了代码但未能减少读者必须掌握的概念数量。
- 由于 PR，文件超过 1000 行，尤其是如果新代码可以被拆分出来。
- 附加到不相关代码路径上的新条件。
- 使现有控制流复杂化的一次性布尔值、可空模式或标志。
- 功能特定逻辑泄露到通用模块中。
- 隐藏简单结构并使代码更难推理的通用"神奇"处理。
- 不简化任何内容的薄包装器或身份抽象。
- 不必要地掩盖真实契约的强制转换、`any`、`unknown` 或可选参数。
- 复制粘贴的逻辑而不是提取的辅助函数。
- 在已经繁忙的函数中间实现的狭窄边缘情况处理。
- 技术上通过测试但使代码模块化或可读性降低的重构。
- 可能成为永久债务的"临时"分支。
- 代码库中已有规范实用程序的定制辅助函数。
- 添加在错误层/包中的逻辑，而它应该存在于更中心的位置。
- 顺序异步流程，其中明显独立的工作可以通过并行执行保持更简单和更清晰。
- 部分更新逻辑使状态比必要的更少原子性。

## 首选修复建议

当你识别出代码质量问题时，优先建议如下：

- 删除一整层间接性，而不是打磨它。
- 重构状态模型，使条件消失而不是被集中化。
- 更改所有权边界，使功能成为现有抽象的自然扩展。
- 将特殊情况逻辑转变为更简单的默认流程，例外更少。
- 提取辅助函数或纯函数。
- 将大文件拆分为更小、更专注的模块。
- 将功能特定逻辑移到专用抽象后面。
- 用类型化模型或显式分发器替换条件链。
- 将编排与业务逻辑分离。
- 将重复分支折叠为单一更清晰的流程。
- 删除没有意义阐明 API 的包装器。
- 重用现有的规范辅助函数，而不是引入近乎重复的函数。
- 使类型边界更显式，使控制流更简单。
- 将逻辑移到已经拥有该概念的包/模块/层中。
- 当独立工作也能简化编排时，并行化它们。
- 当部分状态更难推理时，将相关更新重组为更原子的流程。

当真正的问题是结构性的时，不要满足于"也许重命名这个"的反馈。
如果存在合理路径通向更简单的想法，不要满足于同样混乱想法的仅仅是更干净的版本。

## 审查语气

要直接、严肃、对质量要求严格。
不要粗鲁，但不要将重大的可维护性问题软化温和的建议。
如果代码让代码库更混乱，要明确说出来。
如果实现错过了 dramatic 简化的机会，也要明确说出来。

好的短语：

- `这推动了文件超过 1000 行。我们能不能先分解一下？`
- `这向已经繁忙的流程添加了另一个特殊情况分支。我们能不能把它移到自己的抽象后面？`
- `这能用，但它使周围的代码更意大利面条化。让我们保留行为并重构实现。`
- `这看起来像功能逻辑泄露到共享路径中。我们能不能把它隔离出来？`
- `这个抽象似乎不必要。我们能不能保留直接流程？`
- `为什么这里需要强制转换 / 可选？我们能不能使边界更显式？`
- `这看起来像是为其他地方已有的东西定制的辅助函数。我们能不能重用规范的那个？`
- `我认为这里有一个代码柔道动作，使这简单得多。我们能不能重构这个，使这些分支消失？`
- `这个重构移动了复杂性，但并没有真正删除它。有没有办法让模型本身更简单？`

## 输出期望

按此顺序优先排列发现：

1. 结构性代码质量回归
2. 错过了 dramatic 简化 / 代码柔道重组的机会
3. 意大利面条式 / 分支复杂性增加
4. 使代码更难推理的边界 / 抽象 / 类型契约问题
5. 文件大小和分解问题
6. 模块化和抽象问题
7. 可读性和可维护性问题

如果有较大的结构问题，不要用低价值的吹毛求疵淹没审查。
优先选择少量高置信度评论，而不是一长串表面说明。

## 批准标准

不要仅仅因为行为似乎正确就批准。
批准的标准是：

- 没有明显的结构回归
- 当存在可见的路径使实现 dramatically 更简单时，没有明显 missed opportunity
- 没有 unjustified 文件大小爆炸
- 没有来自特殊情况分支的明显意大利面条式增长
- 没有明显 hacky 或神奇、使代码更难推理的抽象
- 没有不必要包装器 / 强制转换 / 可选性混乱掩盖真实设计
- 没有明显的架构边界泄露或可避免的规范辅助函数重复
- 没有明显分解机会的 missed opportunity，该机会会实质性地提高可维护性

除非作者能明确证明合理，否则将这些视为推定阻止项：

- PR 在存在 plausible 代码柔道动作可以删除复杂性时保留了大量附带复杂性
- PR 将文件从 1000 行以下推到 1000 行以上
- PR 添加了即席分支，使现有流程更加纠缠
- PR 通过将功能检查分散到共享代码中来解决局部问题
- PR 添加了不必要抽象、包装器或大量强制转换的契约，使设计更间接
- PR 重复了现有辅助函数，或当存在明确的规范归属时，将逻辑放在错误的层中

如果这些条件不满足，留下明确、可操作的反馈并推动更干净的分解。
