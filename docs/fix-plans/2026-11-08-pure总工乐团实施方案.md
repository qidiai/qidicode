**派活可行，隔离不可行。** 总工（主会话）能派子代理，且 plan 权限不拦派活；但子代理的 cwd 无法指到任意目录（`IsolationMode` 只有 `None | Worktree`），所以"双盲席物理读不到仓库"做不到，只能降级为"材料优先 + 声明来源"。

## 2. 对原方案的三处修正

### 修正 1：`mcpInheritance: none` 对主会话是空操作

原方案给 4 个 agent 都写 `mcpInheritance: none` 并认为这样零 MCP。**对主会话（总工）不成立**——`McpInheritance` 只在子代理通道被消费，主会话不读该字段（此结论来自 2026-11-08 独立审计，判 ✅）。

**真正生效的是** `disallowedTools: [search_tool, use_tool]`（F5，按名删除 MCP 元工具）。

**但要注意**：删掉元工具只让模型**调不到** MCP，MCP 服务器进程**仍会连接**。若要真零 MCP，得用裸 home（`QIDI_HOME=~/.qidi-local`，其 config 无 `[mcp_servers]` 且 ai-bridge 工具全禁）。

**结论**：总工保留 `mcpInheritance: none`（无害、语义自文档），但**真正的 MCP 开关是 `disallowedTools`**；要真零 MCP 就走裸 home。

### 修正 2：blind-auditor → material-auditor，判据降级

改名，因为"双盲"名不副实。新判据：

| 原判据 | 新判据 |
|---|---|
| 仓库内问题**拒答或明示不知道** | **必须声明信息来源**——答案来自材料（指到段落/行）还是来自仓库（指到文件:行号） |

后者可机器校验：回执里每条结论都要带来源标签。答得出来不可怕，**不声明才可怕**——因为那正是锚定污染的发生方式。

### 修正 4：总工可以开"写半径"，但配置段名是 `[permission]`（单数）

原架构要求"总工不写任何文件"，实践中方案产出率远高于代码产出率，全部派 coder 写会是数量级浪费。可用现成的路径 glob 规则切半径，**不靠自律**：

```toml
# ⚠️ 段名是 [permission]（单数）！写 [permissions] 会被静默忽略
# ⚠️ 建议放 G:\qidicode\.qidi\config.toml（项目级整体覆盖全局，不动全局配置）
[permission]
prompt_policy = "ask"          # ask / deny / auto，默认 ask

[[permission.rules]]
action = "allow"
tool = "read"
pattern = "**"

[[permission.rules]]
action = "allow"
tool = "grep"
pattern = "**"

# 写：只给过程区（glob 基准未定，配两条兜底）
[[permission.rules]]
action = "allow"
tool = "edit"
pattern = "docs/orchestra/**"

[[permission.rules]]
action = "allow"
tool = "edit"
pattern = "**/docs/orchestra/**"

# 交付区硬挡
[[permission.rules]]
action = "deny"
tool = "edit"
pattern = "crates/**"

[[permission.rules]]
action = "deny"
tool = "edit"
pattern = "**/AGENTS.md"
```

**已核实的机制**：
- 段名 `[permission]`（单数）——活路径 `cf-workspace/src/permission/resolution.rs:166` `config.get("permission")`；解析失败会 `warn!("Failed to parse [permission]")`（`:185`），加载成功有 `info!(count, "Loaded permission rules")`（`:172-174`）。**（勘误：`cf-shell/src/util/config/load.rs:90/120` 的 `resolve_permission_config` 是死代码、零调用者，真正的入口是 `resolution.rs:312 resolve_permission_config_with_fallback`，由 `spawn.rs:280` 调用。原"静默忽略"的判断作废。）**
- glob 语义：`*`/`**`/bare tool name=全匹配/`Bash(cmd:*)` 前缀（`cf-workspace/src/permission/rules.rs:105-145`）
- `search_replace` 与 `write_file`（`Write`）都映射到 `AccessKind::Edit(file_path)`（`permission/types.rs:269-270, 274`）→ 一条 `edit` 规则同时管新建与修改
- 优先级 `deny > ask > allow`（`permission/policy.rs:155-157`）
- **无匹配返回 `None` → 走 `prompt_policy`（默认 `Ask`）→ 问用户，不是拒绝**。原方案所称"deny 是无规则即拒绝"不准确
- 项目级 `[permission]` **整体覆盖**全局（`load.rs:113` doc：no deep merge）

**必须同时满足的两个前提**：
1. `permissionMode` 必须是 `default`。`plan_mode_edit_gate` 拦的正是 `AccessKind::Edit`（`tool_calls.rs:197-212`）——留着 plan 等于开了权限又被自己的模式拦死。
2. 划"过程区 vs 交付区"：`docs/orchestra/**` 总工可写；`docs/<主题>/`、`AGENTS.md`、`crates/**` 只能 coder 写 + 人工审。理由：文档即事实源，若总工能改交付文档，事实源变成执行者自产 → 自证循环。

**规则对主会话生效：已静态关闭（2026-11-08）。** `spawn.rs:267-268`：`owns_permission_manager = inherited_permission_handle.is_none()`；主会话无父句柄 → 走 else 分支 → `resolve_permission_config_with_fallback(tool_context.cwd)` → 编译成 `compiled_policy`（`manager.rs:1031`）。主/子走同一函数，差别只有 cwd 与是否继承句柄。

**deny 赢过 yolo：已关闭。** `manager.rs:1225-1231` 注释原文 "permission policy: deny rule matched (enforced before YOLO)"，`Decision::Reject` 分支位于 `yolo_auto_approves` 快路径**之前**。

**write_file 可用性：已关闭。** `default_qidi_build_toolset()`（`cf-agent/src/config.rs:270`）含 `search_replace` 但**不含** `Write`；而 `write_file` 的回填注入在 `builder.rs:700` 的 `if definition.inject_default_tools {` 块内 → **`injectDefaultTools: false` 时不会注入**。故 conductor 必须显式列 `search_replace` 和 `write_file`。

**compact 简写语法**（`resolution.rs:106-144`）：除 `[[permission.rules]]` 外还支持
```toml
[permission]
allow = ["Read(**)", "Grep(**)", "Edit(docs/orchestra/**)", "Edit(**/docs/orchestra/**)"]
deny  = ["Edit(crates/**)", "Edit(**/AGENTS.md)"]
```
⚠️ **compact 命中即早返回，verbose 被静默忽略**——两者不要混写。

**日志验收（替代 TUI 实测，成本≈0）**：会话跑完 grep 日志
```bash
rg -n "Loaded permission rules|Failed to parse \[permission\]" <日志目录> -g "*.log"
```
- `Loaded permission rules count=N` 且 N = 配置条数 → 规则真加载、主会话生效
- `Failed to parse [permission]` → 语法/段名错
- 两者都无 → 配置文件没被 `find_project_grok_configs` 找到

### 修正 3：agent 定义必须带 `model:`，否则分席压缩阈值白设

阶段 2 的 `[model.seat-*]` 三个条目，其解析口径是"spawn 时按**子代理自身模型 id** 查 `[model.<id>]`"（F7）。若 agent 定义没写 `model:`，子代理**继承父模型**，阈值条目匹配不上。

**所以 4 个字段必须同时给**：agent 定义的 `model:` + config 的 `[model.<id>]` + 该段的 `auto_compact_threshold_percent`。

## 5. 未决项（需用户拍板）

### 未决 1：证据区放哪

这是**真矛盾**，不是偏好问题：

- 总工只有 `read_file`，而 `read_file` **有工作区边界**（读不了仓库外）
- 所以证据区必须在 `G:\qidicode` 内
- 但 AGENTS.md §1 禁止根目录新建散目录（白名单：`README.md`/`AGENTS.md`/`Cargo.toml`/`Cargo.lock`/`.gitignore`/`build_release.ps1` + 既有目录）

三个选项：

| 选项 | 位置 | 代价 |
|---|---|---|
| A | `target/tmp/orchestra/` | **在 `cargo clean` 销毁半径内**，台账会丢 |
| B | `docs/orchestra/` | 仓库内、可提交、总工读得到；但 §2 说 docs/ 只收与代码演进直接相关的文档 |
| C | 仓库外 `G:\qidi-orchestra\` | 最安全，但**总工读不到**，违背设计前提 |

**我的建议：B**，并把"工作台账"与"已定论结论"分开——台账在 `docs/orchestra/` 滚动，阶段性结论按 §3 归位到文档私有库。这样既满足总工可读，又不让半成品长期占 `docs/`。

**若你选 A**，必须接受台账随时可能被 `cargo clean` 带走，且 §6 的雷区纪律要求删除前列内容。

### 未决 2：plan 模式下派工要人工批准

`task` 走正常权限路径（非 edit 工具不被 plan 门拦）。非 yolo 时**每次派活都会弹批准**。要么接受（你在旁边点），要么给总工换 `permissionMode: default`（失去"只读"这层语义约束）。

**建议**：先按 `plan` 跑，确认弹批准不烦再说。

### 未决 3：编码席位用哪个模型

`bonsai-coder.md` 现有定义未指定 `model:`（继承父）。若要分席阈值生效，需给它加 `model: seat-coder` 或在派工时指定。改它会影响你现有用法——**要不要为乐团单独复制一份 `bonsai-coder-orchestra.md`**？

**E2 是这套东西的生死判据。** 若核验席只会附和，"总工的事实全是推断"这个前提就塌了——那就该改成"总工只写方向，断言由编码手自证"，那是另一个方案。

## 8. 落地修正（2026-11-09 T1/T2 实施后发现，编码手实证 + 指挥官复核）

### 修正 5：项目级 `.qidi/config.toml` 的 `[model.*]` **不进模型目录**

编码手在 T1 自测时发现，指挥官复核确认：

- 模型目录唯一来源 `ConfigLayers::load()`（`cf-config/src/loader.rs:186-200`），
  只由 `system_managed` / `managed` / `user` / `*_requirements` 构成，**没有项目层**
- `find_project_configs` 的全部调用方是 MCP / watcher / folder_trust / claude_import /
  project-plugin-dirs / reloader，**没有一处向模型目录喂数据**
- 后果链：`model: seat-conductor` → `resolve_model_id` 返回
  `Err("unknown model id")`（`agent/mvp_agent/agent_ops.rs:1076-1081`），
  且只有 `tracing::debug!`（**正常日志级别看不到**）→ 子代理初始化 warn 后回落父模型
  → **90/95/85 三档阈值全部静默失效，零报错**

**修正**：三个 `[model.seat-*]` 段必须放**全局** `~/.qidi/config.toml`（user 层）；
项目级 `.qidi/config.toml` 只保留 `[permission]`（该段确实从项目层加载，见
`resolution.rs:253-282` 的 `find_project_grok_configs` 调用）。

### 修正 6：`[permission]` 规则是**叠加**，不是"项目覆盖全局"

原方案（源自更早转述）称"项目 `[permission]` 整体覆盖全局"——该说法只对
`cf-shell/src/util/config/load.rs:117-144` 的**死代码路径** doc 注释成立。

活路径 `resolution.rs:253-282`：先 `extend` 全局 `~/.qidi/config.toml` 的规则，
再 `extend` 项目 `.qidi/config.toml` 的规则，全部合并后进 `CompiledPolicy`
（`:500-525`），按 `deny > ask > allow` 求值。

**实际语义：全局 deny 会对所有项目压住。** 当前无害（全局无 `[permission]`），
但记成"叠加"而非"覆盖"。
