# 缺陷记录：上下文用量估算系统性偏低（已立项，未实施）

> **状态**：**已定稿，本轮不改**（2026-10-21 用户决定：不单独编译，随下次改动一起出包；不新建分支）
> **方案**：`docs/token-optimization/M1-fix-plan.md`（v5，五轮审计定稿 ACCEPT WITH NITS）
> **实测依据**：`docs/token-optimization/tokenizer-calibration-and-plan.md`（v2）

---

## 1. 现象

产品显示的"上下文用量"与自动压缩的触发判断都依赖本地估算。实测该估算**系统性偏低约 18%**：

| 口径 | 结果 |
|---|---|
| 分层语料（40 会话 / 6,376 项 / 3.91M 真值 token） | 估算/真值 = **0.819**（少算 18.1%） |
| 双尾语料（40 会话 / 15,071 项 / 5.74M） | 0.768（少算 23.2%，抽样偏斜，仅作对照） |
| 会话级 | **39/40 会话同向低估**，中位 −22.6% |
| 最差类别 | assistant 0.741、tool_result 0.820 |

## 2. 根因

`cf-token-estimation::estimate_tokens_aware` 用「4 字符 ≈ 1 token」的 ASCII 经验率。但真实工作量里 ASCII 主体是**工具输出 / JSON / 代码 / markdown**，官方 DeepSeek V4.1 词表实测只有 **3.10 chars/token**（纯 ASCII 项 n=1,211）；JSON 2.85、markdown 2.10。

中文侧（0.6 token/字）反而接近真值（纯中文 0.569），**不是问题所在**——这也推翻了过去"对中文高估"的判断。

## 3. 影响（已校准，不要夸大）

- **不是当前故障**：自动压缩在实测中每次都能成功，溢出预检兜住了边界。
- 真实影响是**安全余量被吃掉**：85% 阈值本留 15% 缓冲，低估 18% 后闸门实际在真实用量 **89%–93.5%** 才触发（取决于"增量占比"）。
- 最危险的形态：单轮内出现超大工具输出（读大文件、长日志），估算少算那部分，可能在同一轮内越过 100%，靠 preflight 拦截。
- 次生影响：`/context` 显示偏低；子代理派发与 recap 的预算判断偏松；成本预估偏低。

## 4. 修法（详见 M1-fix-plan.md）

只改两个比率，其余不动：

| 项 | 现在 | 改为 |
|---|---|---|
| ASCII | `bytes ÷ 4` | `10 / 34`（= 3.4 chars/token，**floor**） |
| CJK | `3/5`（0.6/字） | `4/5`（0.8/字，**ceil**） |
| other 字节 | `/ 4` | **不变** |
| `BYTES_PER_TOKEN` / `estimate_tokens` / `estimate_chars` | — | **一律不动**（被 read_file 截断、web_fetch 预算、工具定义、base64 计数共用） |

预期：分层语料聚合比 0.819 → **0.9811**；夹具 194 条实测 **0.9841 / MAPE 16.3%**。

## 5. 为什么这次不做

1. 改的是**余量**，不是修故障——现在不修也不会出错；
2. 编译成本不划算：改完必须重出 exe 才生效，单独为它编一轮不值；
3. 等下次有别的改动要出包时一起编进去，一次编译覆盖两项。

**做的时候不需要新建分支**，直接在当前 `feat/evo-1-5-evolution-management` 上提交。

## 6. 什么时候要提前做

出现下列任一情况，说明余量已经不够，应当立刻插队：

- 会话里出现"上下文超限 / 请求被截断 / preflight overflow"提示；
- 自动压缩失败或压缩后仍溢出；
- 一次读入超大文件（>1MB）之后紧接着的请求报错；
- 用户反馈"/context 显示还有空间，但模型说超了"。

## 7. 遗留（不在本次修复内）

| 项 | 说明 | 处置 |
|---|---|---|
| `estimate_chars` 仍是 `×4` | 与新速率 3.4 差 17.6%，web_fetch 抓取预算偏大（溢出方向） | M1c，0.25 天，单独做并附 web_fetch 前后对比 |
| `state.rs:39` 工具定义仍 bytes/4 | 降低约 15%，`/context` tools 行偏低 | M1b，1 行 + 测试 |
| 逐项 MAPE 仍 16% | 两个常数在混排段互相补偿，单条消息仍可能偏 20%+ | 根治需 M2 精确 tokenizer（接官方词表，2.5–3 天） |
| 非 DeepSeek 模型未标定 | GLM / Kimi / Qwen 的词表不同，偏差方向未知 | M2.5，逐家跑一次校准脚本 |

## 8. 验证方式（开工时照此验收）

1. `cargo test -p cf-token-estimation` 全绿（含新增校准夹具）；
2. `cargo test -p cf-chat-state --lib` 全绿（28 处断言中的 21 处在这里）；
3. `cargo test -p cf-shell --lib` 全绿（跳过 17 项既有失败，基线 5630 passed）；
4. 夹具聚合比 ∈ [0.97, 1.01]、MAPE ≤ 18%；
5. 出包后同一会话 `/context` 百分比上升、压缩触发点提前（约 89% → 约 85%）。
