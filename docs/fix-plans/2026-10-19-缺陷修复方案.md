## 批次 1（低风险高价值，建议先行）

### F1. `qidi_build_SchedulerCreate` 广告即败（P1）

- **根因**：ToolId = `qidi_build:SchedulerCreate`（冒号，`cf-tools/src/types/slash_commands.rs:91`，运行时 `scheduler/create.rs:112` `ToolId::new(...)`）；LLM 暴露的函数名是下划线形式 `qidi_build_SchedulerCreate`；注册表按 client_name 精确查找（`cf-tools/src/registry/types.rs:1580` try_parse），无冒号↔下划线归一化 → 查找失败。指挥官席与子代理席双双实测复现；`scheduler_list`/`scheduler_delete`（id 无冒号）正常。
- **前置侦察**（编码手第一步）：① 搞清 client_name 的生成规则（为何 id 冒号而暴露名变下划线——找 listing/schema 生成处）；② 全仓列出 `qidi_build:` 冒号族全部工具（已知嫌疑：UpdateGoal/CreateTask/CompleteTask/ImageGen/ImageToVideo/SchedulerCreate/LoopSchedule，slash_commands.rs 常量区）；③ 确认改 id 的影响面（遥测、存量会话、斜杠命令展开 `/loop` 等）。
- **修复方案**（二选一，侦察后定）：
  - A（推荐）：查找层归一化——`try_parse`/dispatch 查找时把 `_` 归一化回 `:` 再试（或双向：先精确、再替换重试），对全体冒号族一次生效，不动存量 id。
  - B：把冒号族 ToolId 改为下划线形式——必须全仓核断言点（R-001），评估遥测/会话兼容性后再动。
- **测试**：对每个冒号族工具加"广告名可调用"契约测试（用无害参数，如 SchedulerCreate 建即删或 dry-run；断言不再 `Tool not found`）；断言带消息（R-003）。
- **工作量**：侦察 1h + 修复 2-4h。**风险**：A 低；B 中（兼容性）。

### F2. 内置 grep 静默返空——即时修复（P1）

- **根因**：`grep/mod.rs:835-845` spawn 失败时把 `Error calling tool: {e}` 写进**不被渲染的 stderr 字段**、stdout 留空、以 `Ok(Early)` 返回 → "工具坏了"伪装成"没有匹配"。上游原因：Windows 构建不捆绑 rg（`cf-shell/build.rs:43`）+ PATH 无 rg 回落裸名（`ripgrep.rs:99`）。
- **修复**：Early 分支把错误写进 **stdout**（参照同文件 1044/1058 行 exit_code==2 的处理路径），使 rg 缺失时调用方能看到明确错误。
- **测试**：mock spawn 失败（或 RG_BIN_PATH 指向不存在路径）断言错误文本出现在 stdout、match_count=0 但 exit_code/stderr 语义清晰。
- **工作量**：<1h。**风险**：低。
- **配套（F2b，根治，可同批或批次 2）**：`rg_path()` 解析后加 `exists()`/`--version` 探针，不可用者在启动期告警一次（announcement/warn）；Windows zip 解捆（build.rs TODO）作为独立后续。

### F3. headless `--worktree` 静默失效——即时修复（P1）

- **根因**：`headless.rs:1005/1011` 只把 `options.worktree` 当布尔量 `has_worktree` 用于 materialize 上下文，**从不创建 worktree**；CLI 参数透传完好（`main.rs:1927`）但无人消费。实测 cwd 不变、`git worktree list` 无新条目、exit 0。
- **修复（即时）**：headless 单轮路径启动时若 `options.worktree.is_some()` 且未走创建链路 → **显式报错退出**（如 `--worktree is not yet supported in headless mode`），杜绝静默。
- **修复（根治，批次 2）**：接通创建——参考 TUI `worktree_cmd`/`new_worktree_dialog`/`cf-fast-worktree` 的同一套创建逻辑，headless 创建后把 session cwd 指向新 worktree，结果里回带 worktree 路径。
- **测试**：① 报错路径：`--worktree=x` 断言非零退出+明确消息；② 根治后：断言 `git worktree list` 新条目 + cwd 正确 + 结束清理。
- **工作量**：即时 1h；根治 0.5-1 天（涉 session 创建主链路）。**风险**：根治中。

## 批次 2（中风险，需设计）

### F4. `capability_mode=read-only/execute` 不禁 write（P1）

- **根因**："先过滤、后注入"顺序倒置：`cf-shell/src/agent/subagent/handle_request.rs:405-406` 对代理定义的 `tool_config` 按能力过滤后，`cf-agent/src/builder.rs:755-761` 的 write 回退层发现无 write 工具（`has_write_tool=false`）又把 `OpenCodeWriteTool` 加回——builder 不知道过滤已发生。
- **修复方案**（按推荐序）：
  - A：builder 感知能力过滤——给 AgentBuilder 传入 capability 过滤结果（或 `write_disabled` 标志），`if self.write_file_enabled && !has_write_tool && !write_forbidden`。
  - B：顺序倒置修正——把 capability 过滤移到 builder 默认工具注入之后（跨 crate，需设计传递点）。
  - C（兜底）：`filter_tool_config` 在 tool_config 上留"write 已禁"元数据，builder 的 `has_write_tool` 检查也认该元数据。
- **测试**：把 T2 的权限矩阵探针固化成契约测试：4 模式 × {read_file, write, run_terminal_command}，read-only/execute 下 write 必须不可用（注意 T2 实测 read-write 也不能跑命令——与代码允许集一致，保持不变）。
- **工作量**：2-4h。**风险**：中（只收紧不放宽；需确认无既有测试依赖"read-only 可写"）。

## 批次 4（功能恢复：指定派发子代理 + 实时状态）——范围待用户确认

### 现状调查结论（2026-10-19 代码级）

TUI 的子代理派发/监控机器**都在**：
- **Agent Dashboard**（`/dashboard`、`Ctrl+\`）：派发输入栏 + 模型选择（`dispatch_model`，sticky）+ prompt 模式 + worktree  armed（`Ctrl+W`）+ 工作目录选择器；行内实时活动（`Running: cargo build`、子代理行的运行中工具、后台任务状态）；attach/stop/group/reorder、peek-reply、权限/问题跟进。
- **Tasks Pane**（`Ctrl+B`）：子代理 + 后台任务交错列表，`Subagents` 可折叠分组置顶，逐行状态。
- **Scrollback 生命周期块**：`Subagent running: "..." (Implementer · model) · Running: cargo test` 实时后缀，Enter 展开全文。
- **Agents 模态**（`/config-agents`）：管理代理定义与 persona（增删/启禁），**不含派发**。

**确定的缺口**：Dashboard 的 `[+ New Agent]`/dispatch 只消费 `pending_model`/`pending_mode`（`dispatch/dashboard.rs:614-650`），**全仓无代理类型/角色/persona 选择器**——即用户无法在 TUI 手工"指定派哪个子代理"（类型只能是主会话模型自己调 `spawn_subagent` 时决定）。

### 提案（若用户所指即此缺口）

- **F8**：Dashboard 派发链路增加代理类型选择：
  - 新增 `dispatch_agent_type` 状态（仿 `dispatch_model`，sticky，随 `/` 斜杠或 `Ctrl+` 快捷键打开选择器：general-purpose/explore/plan + 用户自定义代理（`~/.qidi/agents/*.md`，如 coding-default/office-bid）+ 可选 persona）。
  - `[+ New Agent]` 详情表单同步加类型/persona 字段。
  - 派发时按所选类型创建**子代理会话**（非 plain top-level session），tasks pane/dashboard 行已天然显示实时状态，无需改动。
- **F9（备选，若用户指的是状态不显示）**：若用户现象是 Tasks Pane/scrollback 块**不显示或不更新**——那是回归 bug，需用户提供复现步骤（哪个界面、什么时候发现的、哪个 exe 版本），按 bug 流程派工。
- **依赖**：无（F8 独立）；注意与 capability 过滤（F4）的交互——新会话默认 capability=all 不受影响。
