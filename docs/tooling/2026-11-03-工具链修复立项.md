**输入是输出的 1257 倍**——成本几乎全部来自"重复发送同样的上下文"，而非"模型思考"。

进一步拆解这 152 次请求的构成（人工复盘）：

| 类别 | 估计占比 | 可压缩性 |
|---|---|---|
| 正常推进 | ~45% | 不可压 |

## 1. 问题清单

### P0-1　ripgrep 缺失，内置搜索完全不可用

| 项 | 内容 |
|---|---|
| **现象** | 内置 `grep` 工具在本机**100% 返回空**；本机 PATH 无 `rg`。本次会话全部搜索被迫改用 `git grep`，且多次因命令构造失败而重试。 |
| **根因（已定位）** | ① Windows 构建不捆绑 rg（`crates/codegen/cf-shell/build.rs:43`）；② PATH 无 rg 时回落裸名（`crates/codegen/cf-shell/src/tools/ripgrep.rs:99`）。 |
| **实测** | `git grep "fn main"` → 89 处；内置 grep 同串 → **0 处**（2026-10-19 全面测试）；2026-11-03 复现一致。 |
| **影响** | ① 每次搜索多 1–2 个往返；② `git grep` 只搜已跟踪文件，**未跟踪文件搜不到**——本次"前端没调用 `/api/keys/info`"的误判就源于搜索范围不全。 |
| **方案 A（快）** | 装 `rg` 到系统 PATH（`winget install BurntSushi.ripgrep.MSVC` 或解压到 `C:\tools\rg`）。**10 分钟**。 |
| **方案 B（根治）** | 构建期捆绑 rg 二进制 + 启动期探针 + 缺失时明确报错（不是静默返空）。**2–4 小时**。 |
| **验收** | ① `rg --version` 有输出；② 内置 grep 对已知存在的串返回非空；③ 找不到 rg 时**报错而非静默返空**。 |

### P0-2　PowerShell 命令解析导致高频失败

| 项 | 内容 |
|---|---|
| **现象** | 单引号内的 `|`、`(`、`$()` 被 PowerShell 当作管道/子表达式解析，命令直接语法错误。本次会话**至少 10 次**因此重跑。 |
| **根因** | 工具层用 PowerShell 作 shell，但按 bash 习惯组织命令；PowerShell 的参数解析规则与 bash 不同（尤其 `|`、`&&` 不支持、`$()` 在双引号内会展开）。 |
| **实测样例** | `ssh host 'cd /x; ls \| grep y'` → PowerShell 报 "表达式或语句中包含意外的标记"；已改用「本地写脚本 → base64 → 远端解码」绕过，但每次多 2–3 个往返。 |
| **影响** | ① 直接浪费往返；② 迫使改用更笨的写法，进一步降低成功率。 |
| **方案 A（快）** | 在 AGENTS.md 固化「PowerShell 安全写法」清单：优先用脚本文件、避免嵌套引号、`&&` 改 `;`、`$()` 改中间变量。**30 分钟**。 |
| **方案 B（根治）** | 工具层增加 `shell` 参数，支持 `bash`（Git Bash / WSL），或内置「命令预检」：检测 `|`/`&&`/`$()` 在单引号内的场景并自动转义。**1–2 天**。 |
| **验收** | ① 含 `|` 的单引号命令能一次成功；② 或工具在检测到危险模式时**预检拦截并给出改法**，而不是执行后报错。 |

### P1-1　远端/多行脚本传输成本高

| 项 | 内容 |
|---|---|
| **现象** | 每次远端执行多行脚本需：本地写文件 → `[Convert]::ToBase64String` → `ssh "echo <b64> \| base64 -d > /tmp/x.py; python3 /tmp/x.py"`。本次会话此模式用了 **30+ 次**，每次多 2–3 个往返。 |
| **根因** | 无专门工具；跨平台（Windows → Linux）传输 + 引号问题是组合痛点。 |
| **方案** | 封装 `run_remote.py`（或 qidicode 内置工具）：接受脚本正文 → 自动 base64 → 远端执行 → 回传 stdout/stderr/exit。**1 小时**。 |
| **验收** | 一条命令完成远端多行脚本执行，无需手工编码。 |

### P1-2　工具输出截断与丢失

| 项 | 内容 |
|---|---|
| **现象** | ① 部分工具结果返回 `Tool result omitted — too old`；② 后台任务输出偶发丢失，需重跑。 |
| **根因** | 未完全定位。疑似会话上下文压缩与工具结果缓存策略冲突。 |
| **方案** | 先复现与定位（读取时为何被判定 "too old"），再决定修缓存策略还是改提示。**定位 2 小时，修复待定**。 |
| **验收** | 同一结果在会话内可稳定重复读取。 |

### P2-1　中文编码不一致

| 项 | 内容 |
|---|---|
| **现象** | 控制台 GBK 乱码；读文件需 `-Encoding UTF8`；PowerShell `>` 重定向默认 UTF-16。 |
| **影响** | 每次涉及中文输出都可能需重跑或转码。 |
| **方案** | 工具层统一 UTF-8（读/写/回传）；文档化 PowerShell 输出编码陷阱。**1 小时**。 |
| **验收** | 中文输出在工具结果中不乱码。 |

## 3. 与"Agent 智能"的关系

工具修复解决的是**机械性返工**。另一半是**判断性返工**——本次会话中我犯了 5 次误判，根因全是"证据不全就下结论"：

| 误判 | 真相 | 缺的证据 |
|---|---|---|
| "52duck 没 key" | 有 1 个 key | 读错字段（`api_keys` vs 其他） |
| "`-ms` 名字不存在" | 是条目名，不是模型名 | 没区分两层命名 |
| "路由到了 agnes" | agnes 与 1017 是两件独立事件 | 没按时间戳对齐台账 |
| "前端没调用 `/api/keys/info`" | app.js 里早有实现 | grep 范围不全（未跟踪文件搜不到） |
| "静态文件热加载" | 只有 `/static/*` 热，模板要重启 | 没读 Flask 配置 |

**已落地的对策**：AGENTS.md §9「回执契约」——缺证据的回执拒收，Router 抽验命令而非读代码。

**待落地**：
- **自检清单**：交审计前，自己先按 rubric 走一遍（本次 4 轮审计 → 若前置自检，预计 2 轮）
- **负向断言纪律**：说"不存在/没有"前必须两种正交搜法（`R-021` 已有，但未执行）
