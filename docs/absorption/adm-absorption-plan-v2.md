## 一、三席收敛结论（共识内核）

1. **地基判断成立但需收窄**："GUI 型功能塌缩为技能层"只对**程序性知识类**功能成立（部署 SOP/调优 playbook），**不能外推到常驻服务、状态回显、多用户交互**——后者需要实体进程（qwen 席 O-4 的关键限定）。
2. **wecom-unified 无审批 API**（step5+qwen 双席实证：SKILL.md+39 references 仅 1 处"审批"命中且是 webhook 示例）；`send_message` 在 0.1.9 **仅支持 text**。v1 方向 2/3 建立在不存在/未验证的能力上——**必须重写**。
3. **"触达个人微信"表述过宽**：官方路径=①企微成员经**微信插件**在个人微信收应用消息（需成员身份+绑定）；②外部联系人/微信客服（需成员侧先决动作）。**个人微信用户不能直接向自建应用发消息**。"零封号风险"仅相对协议 hook 成立。
4. **形态必须"技能+常驻 daemon"双层**（三席一致）：技能=知识（安装/配置/运维/诊断），daemon=实体（消息循环/验签/去重/围栏/审计）——与 qwen-image-lowvram 先例同构（技能是知识，ComyUI 是实体）。保活可复用本机既有计划任务形态（§11.9 先例）。
5. **工作量重估**：仅方向 1+围栏 ≈1-2 天成立；含确认通道 **3-5 天**；方向 3（回调）在公网条件落实前不可估。
6. **prompt injection 是最大风险缺口**（三席一致）：白名单只控制"谁能触发"，不控制"消息内容"；且**"只读自动"拦不住读+外传组合**（haiku 席补充）。必须内容侧护栏+来源分级。
7. **第一批只做方向 1**（三席一致）。

## 三、修订后的 P0 规格（wecom-bridge，v2）

**架构**：`wecom-cli`（外部 CLI，**需先升级 0.1.9→1.x 并回归全部 references**）↔ **常驻 daemon**（Node 脚本或 Rust 小 exe；保活参照 §11.9 计划任务形态）↔ agent 表面（`agent serve` :2419 WS + secret，或 ACP stdio——均已实证存在）。**技能只负责安装/配置/自检/诊断 SOP**。

**第一批（唯一承诺批，≈1-2 天）**：
- 方向 1：结果推送（`send_message` text；**只推终态结果，中间进度合并**——防频率限制）
- 来源围栏：userid/群白名单；**私聊与群聊分级**（群默认只读）；fail-closed（能力缺失即拒+告警，不静默降级）；会话绑定（同一 userid 绑同一 agent 会话，防跨会话串话）
- 内容围栏：`qidi <指令>` 前缀协议；长度/类型白名单；敏感操作二次确认

**第二批（≈1-2 天）**：方向 2 关键词确认（`ok #N`/`no #N`，TTL 10 分钟默认拒绝，#N 一次性消费）；模板卡片按钮 PoC（微信插件内可达，成功则替换关键词）

**Backlog**：方向 3（公网回调：先定中继形态——复用 ba 中继作信任根 vs 独立穿透；5 秒应答+消息 ID 去重+验签）；审批流加强档（高敏操作留痕）
