# ADM 吸收方案（2026-10-19）

> 对象：`github.com/autoDeploymentModel/adm`（Tauri 2.x + llama.cpp 本地部署 + Agent 管理台 + 微信 Bot，48 star 活跃项目，与 qidicode 功能面 80% 重叠的直接竞品）。
> 本文档结论待三模型审计（GLM-5.3-222 云中转 / qwen3.8-flash 魔塔 / step-5-preview）评审后定稿。

## 一、框架判断（本方案的地基）

**核心论点：在 agent-native 架构里，GUI 型产品功能塌缩为技能层，不构成能力差距。**

实证：
- ADM 的"本地模型一键部署/GUI 管理" ↔ 我们的 `qwen-image-lowvram` 技能先例（ComfyUI + Qwen-Image-2.1 低显存部署全套程序性知识，白名单技能，F:\AI\ComfyUI 实体在跑）——**同类能力，我们已技能化**
- ADM 的 ComfyUI 图像生成 ↔ 同上，已覆盖
- ADM 的 Docker 镜像模型管理 ↔ 程序性知识，技能可覆盖

推论：ADM 真正值得吸收的不是"功能清单"，而是**交互面（微信）**和**工程纪律**。功能缺口一律用技能补，不进产品核心。

## 二、吸收清单（分级）

### P0：WeCom/微信消息桥（`wecom-bridge` 技能）——唯一的产品级候选

**为什么是它**：ADM 的微信 Bot 给了启发——遥控面不应该要求装 APK。但**路线必须官方化**：
- ❌ 不做个人微信协议 hook（ADM 的 wechatbot crate 路线：违反 ToS、封号风险、协议常断）
- ✅ 走 **WeCom 官方 API**（地基已在：`wecom-unified` 技能 = wecom-cli，消息/文档/审批/通讯录全套+扫码授权）；WeCom 官方通道可触达个人微信（企业微信↔微信互通），零封号风险

**技能规格草案**：
- **架构**：`wecom-cli`（已有）↔ 消息循环（薄桥进程）↔ 本地 agent 表面（复用 `agent serve` :2419 WS 或 ACP stdio——两者都已存在，不造新通道）
- **三个方向**：
  1. **结果推送**：agent 任务完成 → 发微信/群（最简，wecom-cli 现成）
  2. **审批式权限确认**：写/执行类操作 → 发 WeCom 审批消息 → 手机上点"批准"=放行（补上遥控链路"最后一公里"；ADM 的手机确认我们用官方审批实现）
  3. **任务下发**：WeCom 收到指定来源消息 → 投喂本地 agent → 结果回传（需要回调/机器人配置）
- **安全围栏（硬要求）**：wxid/群白名单（非白名单消息一律忽略）、权限门禁（只读自动、写/执行必审批）、防环（bot 自己的消息不回投）、速率限制（防刷）、审计日志
- **工作量估计**：地基可用的情况下 1-2 天（消息循环+围栏+回调配置），全部是技能+外部 CLI，产品核心零改动

### P1：`qidi-update` 技能（自更新的技能化）

- ADM 的自更新三态机（下载→哈希/大小校验→三态 UI→平台化安装）值得吸收；我们今天手工编译 101 分钟+手动四步换装=痛点实证
- 落点：技能（查 GitHub releases→下载→校验 hash→暂存 `G:\qidi-exe-backup\`→提示换装+验证命令），不做进产品
- 工作量：半天

### P2：工程纪律互鉴（进 AGENTS.md/RUBRICS，不写码）

1. "**没写在 doc 里的规则=不存在**"——直接抄进我们 §0（我们已有"先修文档再继续"的同款精神，化为明文）
2. **sidecar/外部组件版本钉死**：ADM 规定 Go sidecar 改版必须 push 二进制后主程序才生效——我们对应：技能引用的外部组件（wecom-cli 版本、ComfyUI 版本等）变更必须登记+回归
3. **并行会话文件守卫**（ADM doc 有设计）：我们现在靠"零文件交集"纪律，技术守卫作 backlog 研究

### P3：明确不吸收

- llama.cpp GUI 管理面板（技能更轻，已有先例）
- Go 双栈架构（我们 Rust 单栈+skill 扩展是不同架构选择，不跟）
- Docker/ComfyUI 产品化管理（已技能化）

## 三、落地路线

1. **第一批**：`wecom-bridge` 技能（P0，1-2 天）——先做方向 1（结果推送）+方向 2（审批确认），方向 3（任务下发）视回调配置难度
2. **第二批**：`qidi-update` 技能（P1，半天）
3. **第三批**：纪律条款进 AGENTS.md（P2，即时）
4. **Backlog**：并行会话文件守卫的技术方案研究

## 四、风险与开放问题（留给审计评审）

1. WeCom 回调/机器人配置的真实门槛（应用消息频率限制、用户关注要求）——`wecom-unified` 技能覆盖的是主动调用，**接收方向的能力边界未验证**，这是 P0 最大不确定点
2. wecom-cli 的维护状态与协议稳定性（npm 包 @wecom/cli 0.1.9，早期版本）
3. 审批式确认的 UX：WeCom 审批流是为业务流程设计的，用作"工具执行批准"是否顺手（还是普通消息+按钮/关键词回复更合适）
4. 技能形态 vs 产品形态的边界：消息循环作为"技能"运行（agent 驱动）还是独立常驻进程——前者与 agent 生命周期绑定，后者需要守护
5. ADM 的 license 状态矛盾（badge MIT vs 无 license 文件）——借鉴其设计前的法律前提
