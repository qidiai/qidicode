# `[skills] subagent_listing` —— 子代理基线技能清单注入旋钮

> 归属：子代理技能面（F2 / F2R）。配置字段：`cf_agent::prompt::skills::SkillsConfig::subagent_listing`。
> 生效范围：**仅子代理会话**（`PromptAudience::Subagent`）；与主会话的 `[skills].mode` 相互独立。

## 1. 语义

子代理会话在**启动时**无条件注入一份基线技能清单（一段包装为 `<system-reminder>` 的
`<skill catalog>` 文本），告知子代理"有哪些技能可用"。`subagent_listing` 决定这份清单的投影范围：

| 取值 | 语义 | 注入内容 | 可激活集（`AvailableSkills`） |
|---|---|---|---|
| `"essential"` | **缺省**。只列核心编程技能 | 投影到解析后的 essential 白名单（用户 `[skills].essential_allow`，缺省用内置 `DEFAULT_ESSENTIAL_SKILLS`） | 投影为同一白名单子集，再扣除 F2S 门禁（§5） |
| `"full"` | 列出全部已发现技能（历史行为） | 全量清单（已扣 F2S 门禁） | 全量技能集，再扣除 F2S 门禁 |
| `"none"` | 完全不注入 | 无清单块 | 写入 `全量 - 被禁`（F2S 门禁；F2R 原为"不改写"，见 §5.4） |

> **F2S 门禁（§5）与此表正交**：无论上表取何值，危险的技能族都不会进入子代理的清单与可激活集。

**缺省 = `essential`**。未设置时字段保持 `None`（不落盘），由
`SkillsConfig::subagent_listing_or_default()` 解析为 `Essential`——与 `[skills].mode` 的
`Option` + `skip_serializing_if` 先例一致。

```toml
[skills]
# 子代理基线技能清单投影：essential（缺省，仅核心编程技能）| full（全量）| none（不注入）
subagent_listing = "full"
```

## 2. 与主会话 `mode` 的区别

| | `[skills].mode` | `[skills].subagent_listing` |
|---|---|---|
| 作用对象 | 主会话（`PromptAudience::Primary`） | 子代理会话（`PromptAudience::Subagent`） |
| 默认值 | `essential` | `essential` |
| 消费点 | `SkillManager::set_skills_mode` | 子代理注入缝（见 §3） |

两者互不影响：子代理 `essential` × 主会话 `full`、子代理 `full` × 主会话 `essential` 均按各自值生效。

## 3. 注入点（F2R 修正后的真实路径）

子代理**从不发送 `SessionCommand::Initialize`**，因此原 F2 落在
`session_setup.rs::inject_baseline_skill_reminder` 的子代理分支在生产子代理流程中**不可达**
（该缝仅由 ACP 主会话 `new_session` 与 zero-turn 模型切换触发）。F2R 把注入搬到子代理的
**真实初始化点**：

- **主路径（spawn）**：`spawn_session_actor` 在 `install_system_prompt` 之后调用
  `spawn::inject_subagent_baseline_listing`（覆盖 New / Forked / Resumed 三类子代理）。
- **次路径（zero-turn rebuild）**：`handle_rebuild_agent_for_definition` 经
  `inject_baseline_skill_reminder` 的子代理分支，委托给**同一个** helper，保证策略不漂移。

两条路径都复用 F2 的只读资产 `ToolBridge::subagent_skill_listing`：
`SkillManager::listing_for_subagent`（只读渲染，**不读写** `announced_names` 账本）+
`clear_pending`（丢弃子代理陈旧 pending，防首次工具调用 drain 出第二份清单），并把**投影后的
runtime 技能集写入 `AvailableSkills`**（O-1 一致性），使"清单所列"与"技能工具可激活"集合一致。

## 5. `[skills] subagent_denied_skills` —— 子代理技能门禁（F2S）

> 归属：子代理技能面（F2S）。配置字段：`cf_agent::prompt::skills::SkillsConfig::subagent_denied_skills`。
> 生效范围：**仅子代理会话**；主会话（用户自己）**永不受限**。

### 5.1 语义

F1（commit `362eb07c`）让子代理可以激活**全部**技能，其中包括本机特有的危险族（生图 / OCR /
起服务）。门禁恢复一条**默认权限边界**：子代理默认不许碰这些技能，除非用户显式放开。

| | `subagent_listing`（§1） | `subagent_denied_skills`（本节） |
|---|---|---|
| 性质 | **成本**投影（少注入 → 省上下文） | **权限**边界（不许激活） |
| 作用面 | 只影响"模型被告知什么" | 清单 **+** `AvailableSkills`（技能工具真正能激活的集合） |
| 与对方关系 | 被门禁叠加（三值都绕不过门禁） | 独立于 listing 旋钮，三值下都生效 |

**内置默认集**（`DEFAULT_SUBAGENT_DENIED_SKILLS`，缺省即生效）：

| 条目 | 覆盖 |
|---|---|
| `qwen-image-lowvram` | 低显存 Qwen-Image 生图（ComfyUI） |
| `pdf-to-word-ocr` | HunyuanOCR 文档流水线 |
| `seal-extractor` | HunyuanOCR 印章/盖章提取 |
| `bid-` | 全部 `bid-*` 办公/标书解析族（OCR） |

### 5.2 匹配语义

条目与技能 `name`（frontmatter / 命令标识，与 essential 白名单、技能工具同一标识）逐条比较：

- **相等**：`name == 条目`
- **前缀**：`name.starts_with(条目)` —— 所以 `"bid-"` 盖住整个 `bid-*` 族，`check-work` 也会盖住
  `check-work-extra`

条目**锚定在开头**，不是子串搜索：`"bid-"` 不匹配 `my-bid-write`，也不匹配 `bidding`（无 `-`）。
条目两端空白会被裁掉；**空条目被忽略**（`""` 若当真会前缀匹配一切、静默禁掉整个目录，属误配而非意图）。

### 5.3 覆盖方式

```toml
[skills]
# 缺省（不写）= 内置危险族默认集；写 [] = 完全放开；写自定义集 = 替换（非追加）默认集
subagent_denied_skills = ["qwen-image-lowvram", "seal-extractor"]
```

- `None`（不落盘）→ 解析为内置默认集（安全默认：即使某会话从未配置门禁也生效）
- `Some([])` → 门禁全开，子代理恢复 F1 行为
- `Some([...])` → **替换**默认集（不是追加）

字段为 `Option` + `skip_serializing_if`，与 `mode` / `subagent_listing` 先例一致：
未设置时不落盘。**解析点在子代理注入缝**：`spawn.rs` 把
`SkillsConfig::subagent_denied_skills` 原样交给 `ToolBridge::subagent_skill_listing`，由
`SubagentSkillDenylist::resolve`（`cf_tools`，匹配语义的唯一权威）解析。门禁因此**不依赖**
`seed_skill_discovery` 是否已被调用——沿用与 `subagent_listing` 完全相同的接缝，
任何按子代理路径建起来的桥接都会被门禁覆盖。

### 5.4 `none` 的写回语义变化（F2S 有意覆盖 F2R）

F2R 对 `subagent_listing = "none"` 的选择是"**不回写** `AvailableSkills`"（成本语义：不注入就不改写，
保持 `finalize()` 落的全量集）。但门禁是**权限**语义：若 `none` 不回写，用户只要设一个
`subagent_listing = "none"` 就能让子代理拿到**全量可激活集**，门禁被一行配置绕过。

因此 F2S 起：`none` **也写回** `AvailableSkills = 全量 - 被禁`（清单仍不注入）。三值的可激活集统一为：

| listing | 可激活集 |
|---|---|
| `essential` | essential 白名单 ∩ ¬被禁 |
| `full` | 全量 ∩ ¬被禁 |
| `none` | 全量 ∩ ¬被禁（**改动点**） |

### 5.5 应用点与不覆盖面

门禁叠加在**子代理共享投影层**（`listing_for_subagent` / `subagent_runtime_skills` 共用的
`deny_subagent_skills`），在投影**之前**过滤技能集，所以：任何 harness（含刻意跳过 essential
白名单的 XML 分支）都生效；清单与可激活集不可能漂移（列表里不会出现工具激活不了的技能）。

主会话零影响：主会话清单（`listing_snapshot` / `take_pending`）与 `slash_skills` 都不经过该投影，
被禁技能照常可用。

**已知未覆盖面（F2S 交付时点，待后续裁定）**：门禁只挂在子代理**启动注入缝**。子代理运行中若
触发**动态技能发现**（阅读落在配置目录内的文件 → `SkillDiscoveryReminder`），
`ToolBridge::apply_pending_skill_update` 会用 `SkillManager::take_pending` 的**未投影**合并集
（`discovered ∪ startup`，含被禁技能）覆写 `AvailableSkills`，绕过门禁。该路径与主会话共用，
`SkillManager` 不知道自己是子代理；封堵需要把"是否子代理"传进该投影（本次未做，避免扩大改动面）。
