## 1. 省钱与限权的分离（v2 根基节，全稿第一原理）

### 1.1 用户三连拍板（2026-10-09，逐字采信）

1. **「没有工具了模型能干好活嘛？」→ 不能。** 藏工具必须配「怎么拿回来」——`search_tool` 下发 schema 就是拿回通道；藏 ≠ 删，是收进抽屉，抽屉上必须有标签。
2. **「为啥不给工具？」→ 不是安全，是省钱。** 工具定义每轮全量发送是开销大头（ling-B v8 实测 `--tools` 过滤 Δ ≈ 8.5K tok/轮，§8-1）。本管线自始至终是**成本工程**，不是权限工程。
3. **「不想让调用工具直接派子智能体限制工具不就可以了嘛？」→ 完全正确，且点破 v1.1 根基错误。** 需要限制模型用某工具时，用**子代理工具限制**——这是已有机制（spawn 时 `apply_to_subagent_definition` 绑定父会话 `--tools`/`--disallowed-tools`/`--permission-mode`，`subagent/mod.rs:401-407`；acp/mod.rs:424-431 doc 背书双方法语义 "main sessions: direct replace via apply_to_definition; spawned subagents: session-clamp via apply_to_subagent_definition"——**session-clamp 比直接替换更强：子代理被钳制、不得放宽**；子代理独立 auto-compact 阈值即上下文硬预算实例，`subagent/mod.rs:388-400`）。限权不归本管线。（v3 补注：另有一条**独立的子代理 capability_mode 链**——`cf-subagent-resolution`：`EffectiveRuntimeConfig.capability_mode`（`types.rs:29-30`，"controlling tool access"）四档 read-only/read-write/execute/all（`config.rs:29-30`），解析链 `overrides.rs:60-66`——同样支撑「限权已有机制」结论，v2 未提及、v3 补全。覆盖面注：`apply_session_cli_overrides` 在 `agent_config: Option` 为 None 时静默跳过（`subagent/mod.rs:404-406`），为潜在 fail-open 面，本审计手段未能全链核实所有派发路径——见 R-8。）

### 1.2 拍板推翻了 v1.1 的什么

v1.1 的根基错误：把「defs 投影层过滤」与「权限/安全」藕断丝连——

- v1.1 §2.1 把 use_tool 旁路称为「**安全注意点**」；
- v1.1 R-2 称「安全边界在 server-side denylist + plan 过滤器」——但 plan 过滤器同样只作用于 defs（且现状是恒等 pass-through，§3-2.4），`use_tool` 旁路 plan 过滤器与旁路 defs 是**同一性质**，R-2 的「安全」主张自相矛盾（Sonnet 必改 6）；
- 整体隐含把 search_tool 解锁当成分级授权——方向性错误。

拍板 2 纠正：defs 全量发送的动机自始至终是**省钱**。投影面裁剪省的是每轮 token，不是权限。

### 1.3 旁路实锤（2026-10-09 实验，权限侧死刑判决）

**实验**：`--disallowed-tools` 将终端工具从 defs 摘除后下达需要跑 shell 的任务。
**结果**：模型自行发现 `monitor` 工具可代行终端能力，经其旁路**跑完了整个任务**。
**结论**（三点，全部写入 v2/v3 设计）：

1. **defs 摘除完全不是执行边界**。不是「理论上有 use_tool 旁路」（v1.1 仅此程度），而是**模型有创造力主动找旁路且当天就找到了**——Sonnet R-2 预言实锤且更严重。
2. 对**省钱目标无害甚至有利**：模型绕过投影面拿到工具 = 工作没被卡死，常驻段照样省了 token。旁路是本管线的**可接受现象**。
3. 对**限权期望是死刑**：任何把「投影面裁剪」当限制的用法都会被模型绕过。限权必须落在执行面（注册面裁剪 / capability-mode / 子代理限制）。

### 1.4 权限完全剥离声明（v2 对 v1.1「安全注意点」的改写）

本管线（常驻切分 / search_tool 解锁 / imported 追加）做出如下**不可撤销的设计声明**：

1. 投影面的任何变化**不构成、不得被解读为、不得被用于**权限语义。defs 里没有某工具 ≠ 模型用不了它（use_tool 间接派发是现状：`registry/types.rs:1665` 的 `if tool_name == "use_tool"` 分派 + `:421-422` `effective_tool_name` 记录）。
2. 解锁 ≠ 授权；不解锁 ≠ 禁用。search_tool 的解锁域描述的是「本轮 defs 里有什么」，不是「模型被允许用什么」。
3. 执行面闸门（若需要）属于**权限侧独立事项**，与本文互不改动：注册面 capability-mode（ToolConfig.kind doc `registry/types.rs:131-143`，fork 时能力约束见 v2 会话实测）、`--permission-mode`、子代理工具限制（`subagent/mod.rs:401-407` + §1.1 v3 补注的 capability_mode 链）。本管线不实现、不依赖、不声称其中任何一个。**唯一例外（v3 显式声明）**：B-12 use_tool corrective 语义门控——它不是权限闸，是 MVP 路径的**功能前置**（让被藏工具可经 use_tool 中转），详见 Q2.1。

### 1.5 职责对照表（谁管什么）

| 需求 | 正确机制 | 所在层 | 与本文关系 |
|---|---|---|---|
| 每轮 defs 太贵（~8.5K/轮） | **本管线**：常驻切分 + 按需投影 | 投影面 | ✅ 本文全部内容 |
| 模型不知道某工具存在 | `search_tool`：藏了就给检索通道（schema 下发） | 投影面 + meta 层 | ✅ 本文 Q2 |
| 「模型不该用工具 X」（权限） | capability-mode（注册面）/ `--disallowed-tools` + 子代理继承（`subagent/mod.rs:405`）/ 子代理 capability_mode 四档（`cf-subagent-resolution`，§1.1 补注）/ permission-mode / 主循环 spawn 只读受限子代理 | 执行面 | ❌ **明确不在本文**（§1.4 声明 3；B-12 是功能前置非权限闸） |

## 2. 目标与非目标

### 2.1 目标

1. **把每轮 defs 从「全量恒带」改为「常驻段 + 按需段」**：直接砍每轮固定开销大头——**动机是省钱（拍板 2），不是限权**（《方案.md》§2:14「工具定义随请求全量发送」、§5:70 问题 2）。
2. **找回通道（search_tool）**：模型通过恒驻的 meta 层工具按需把藏起来的工具「拿回来」（schema 下发到 tool_result，MVP 路径零 defs 变化，见 Q2）——主循环不被卡死。
3. **KV cache 分段稳定**：常驻段前缀永不变；imported 段 append-only；杜绝 per-turn 随机裁剪（v3 #2 处方）。
4. **成果压缩层**：per-turn 对历史工具输出的确定性降级/丢弃，填补 P0-2 第一步做不到的**历史增长**维度（《方案.md》§1:15）。
5. **口径单一**：与第一步已落地的 `--tools` 静态过滤共用同一收口与同一计数面，防止三处漂移复发。
6. **【v3 新增】use_tool 直呼域与 corrective 语义门控（B-12）**：MVP 路径的功能前置——声明 use_tool 的可调名域（registry_id）并门控其 native_tool_correction 语义（现状对原生工具名一律返回 "call it directly" 纠正性错误，`use_tool/mod.rs:30-45`；MVP 场景被藏工具正是原生工具名且不在 defs，模型听从该建议必败）。**这是本设计唯一的执行面改动**，显式列入 Phase B 范围（§6，含跨层数据流设计，v3.1），不属隐式越界。

### 2.2 非目标（本次不做）

| 非目标 | 理由 |

**与 headless `--tools` 的关系（v3.2 裁决终版：白名单 ∪ meta 恒驻 + 解锁域 ⊆ 白名单——推翻 v1.1 Opus 的 ∩ 方向；理由：∩ 会排除默认集外用户显式点名的工具（`--tools x,read_file` 的 x 不在默认集即被吃掉），∪+⊆ 同时保住表达力与裁剪力——裁剪力由「解锁域 ⊆ 白名单」承担，非 ∩）**：

- **设置白名单时（v3.2：∪+⊆ 裁决）**：常驻段 = **白名单 ∪ meta 恒驻集**（**替换**默认集，默认集整体不参与）；解锁域 **⊆ 白名单**。**meta 恒驻集不在白名单裁剪域内（v3.2 写明，grok-4.7 必改 1）**：meta 二元（SearchTool/UseTool）与防卡死红线 AskUser 恒驻，不受白名单裁剪——白名单裁的是「默认集成员」，meta 自通道与提问红线是任何配置下的保底（C-4 断言对象）；白名单显式列出的默认集外工具照常进常驻段（∪ 的表达力面——∩ 会把它们吃掉，此为推翻 ∩ 的核心理由）。用户显式给名单是明确的上下文裁剪意图（省钱语义，非权限语义——§1.4），search_tool 不得越过它：否则 `--tools` 失去裁剪力（Opus 阻塞场景）。白名单之外但注册面存在的工具，模型仍可经 use_tool 触达（**v3 勘误**：现状 use_tool 对原生工具名默认返回 "call it directly" 纠正性错误（`use_tool/mod.rs:30-45`），须经 B-12 门控放行中转后方触达——**不是纯现状能力，是 B-12 后能力**，v2 此处声称有误已修正）。
- **未设置白名单时**：常驻段 = 默认集（Q1 表）；解锁域 = 注册全集 − 排除面（plan 真身排除 + server 策略排除；MCP 面按 namespace 排除规则见 Q1）。
- 第一步白名单是**手工**裁剪，第二步是**自动**按需；二者在「设置时」叠加为「白名单内再切常驻/按需」。

**分层选择理由**（v1.1 保留）：defs 是每轮固定开销、conversation 是可变增长开销（《方案.md》§1:11-15），两层作用对象、触发时机、缓存破坏语义完全不同，合成一套「动态裁剪」会互相拖累验收口径——故显式三分。

## 5. 四问题的设计决策

### Q1：常驻段怎么切——36 变体穷尽表（无通配符 match，Sonnet 必改 6）

**代价模型**（v1.1 保留）：

| 错误方向 | 代价 | 量级 |
|---|---|---|
| 常驻段留了低频工具 | 每轮白带其 definition tokens（200-800 tok/个）× N × 每轮 | 线性积累，不卡流程 |

#### Q2.1 双路径定义

| 路径 | 机制 | defs 影响 | 缓存影响 | 裁决 |

**MVP 路径的模型行为背书（2026-10-09 会话实证 + v3 实现层证据）**：

1. **模型原生两轮模式**：当前会话的系统提示明文「MUST call `search_tool` first to retrieve the tool's input schema before calling `use_tool`. NEVER guess parameter names — always use the exact schema returned by `search_tool`」——**藏（defs 无 schema）+ 告诉怎么拿回来（明文指路）+ 拿回（tool_result 携带可调名与完整 schema）+ 用（use_tool 精确调用）** 的完整闭环是模型可稳定执行的使用模式。**背书边界（v3 诚实标注）**：该实证来自 harness 注入的系统提示（厂商原生 MCP 使用模式），**非 ling 系模型对嵌套 schema 经 tool_result 文字解析的独立实测**（ling wrap 实验为文字描述+echo）——B-1 验收因此必须含**复杂 schema 变体**（browser_act 多层 action 参数级），不能只测 video_gen 单层。
2. **verify-then-use**：模型先 `search_tool` 验证注册表再行动，对注入的伪工具名盲从被拒——找回通道自带一层防幻觉属性（安全副产品，非设计目标，§1.4）。
3. **命名域混淆教训**：同一实验中模型自述 `run_terminal_command`，wire 实名 `run_terminal_cmd`（保留名表 `registry/types.rs:40`）——**search_tool 返回的名字必须逐字节等于 use_tool 可调名（registry_id 域）**，并在 tool_result 中明示「逐字节用于 use_tool 的 tool_name 参数」。制度化为契约 C-5（v3 两域重写）。

**【v3 新增，B1 核心；v3.1 补数据流】use_tool 直呼域与 corrective 门控（B-12，Phase B 范围项，v3 唯一执行面小改）**：

- **直呼域声明**：use_tool 接受的名字域 = **registry_id**（`use_tool/mod.rs:13-15` → `ToolId::new` :89 → `LocalRegistry.find` `registry/types.rs:1695-1703`）。内建工具 registry_id = id；MCP = `server__tool`。**与 defs 的 client_name 是两个域**——name_override 的内建工具按 client_name 经 use_tool 调用会失败，tool_result 必须返回 registry_id 域名。

#### Q2.3 增强路径的解锁时机——盈亏平衡模型（Sonnet 阻塞 2，v3.1 增杀死判据）

**问题**：defs 位于 system + messages 之前，第 t 轮追加 defs 等于其后全部前缀缓存作废一次；晚期解锁的重算成本可能远超收益（v1.1 §7 的 66.4%→94.7% 是**静态过滤后保持稳定**的数据，不能证明会话中途追加安全——Sonnet 正确指出）。

**模型**（简化线性，参数待遥测回填）：

- 追加代价 ≈ `B_k`（追加字节对应的 token 数）× `H_t`（第 t 轮 history 已有 token 数）× `Δprice`（cache-write 与 cache-read 单价差，LAN 端点实测口径待采）——一次性；
- 持续代价 ≈ `B_k × (R − t)`（其后每轮多带）；
- 收益 ≈ 每次省 MVP 拿回全程 = **2 轮采样（search_tool 一轮 + use_tool 一轮，非 1——v3.2 顺手修正：间接成本进判据，收益项按 2 轮采样成本计）**的采样延迟 + 中转 output tok，× 期望使用次数 `U_k × (R − t)`。
- **判据**：`H_t × Δprice + B_k × (R−t) < 每次拿回省下的 2 轮采样成本 × U_k × (R−t)`。因 `H_t` 随 t 单调增长，**晚期解锁净收益转负**——这就是时机门控的依据，不是拍脑袋。**v3.2 注**：收益按 2 轮采样（非 1 跳）计使判据**更严**——低频工具更早转负，与杀死判据（裁决 6）同向。

**裁决**（数据不足时保守）：

1. **会话早期窗（默认前 N 轮，N 待遥测定参，O-11）**：imported 追加自由；
2. **晚期**：只走 MVP 路径（use_tool 直呼，defs 零变化零缓存代价，代价仅每次一跳中转）；
3. **compact 边界**：压缩重建后前缀本就重算，**追加零缓存代价**——天然解锁窗口，晚期攒下的解锁请求在 compact 后一次放行；
4. Phase B 并行收集：per-tool 定义 token 表（B-10）、解锁时点 × 剩余轮数 × ratio 曲线（B-5）——回填模型参数后把 N 从开放问题转配置；
5. **【v3 新增】中转成本测量口径（ledger 归因）**：MVP 一次拿回 = **2 轮采样**（search_tool 一轮 + use_tool 一轮）；use_tool 调用的 `ToolRunResult` 记 `effective_tool_name`（现状 `registry/types.rs:421-422` 已有）——**B-5/B-10 遥测按 effective_tool_name 归因到实际工具**，中转一跳成本（use_tool 轮的 output tok + 采样延迟）计入 Q2.3 收益公式的测量面；ledger 中 search_tool 与 use_tool 各记一次 model_calls，不合并、不折叠（对账可分）。
6. **【v3.1 新增，K3 必改 6；v3.2 收益口径同步】杀死判据**：imported 路径收益 = 省每次拿回的 **2 轮采样**（v3.2：search + use 各一轮，非 1 跳——收益更小、判据更严；B-5/B-10 数据）——按本节公式，**低频工具（U_k 小）几乎必亏**（追加代价 `B_k × H_t × Δprice` 一次性 + 持续 `B_k × (R−t)`，收益仅 `U_k × (R−t) × 一跳`）。**若 B-5/B-10 数据回填后证明全工具类场景均不盈利 → Phase B-2（增强路径）整条砍掉**——MVP use_tool 路径独立成立（defs 零变化零缓存代价，Q2.1），B-2 是纯增量增强，砍掉不伤主线、不回滚 MVP。B-2 的启动与保留均以本判据为闸（Phase B 范围 3 注）。

**KV cache 分段三律**（v1.1 保留，措辞规范化）：

1. **常驻段 = 最前缀**：defs 按固定顺序（常驻段内部排序键 = client_name 字典序，Phase A 固化；plan 对钉尾部）恒置于头部，任何轮不增删重排。
2. **imported 段 append-only**：新解锁永远追加尾部，不按字典序插队（插队会在已有 imported 工具之间移位，作废其后全部前缀——含整个 history）；解锁后不回收（per-session lifetime，/clear 例外）。**v3.1 注**：MCP 运行期新注册工具进追加段尾部，同样满足本律（Q2.5 MCP 行）。
3. **杜绝 per-turn 随机裁剪**：任何轮不得从 imported 段摘除工具。

实测背书（ling-B v8，§8-2）+ **证据边界声明（v3.2 顺手补强，grok-4.7）**：工具集构成稳定后是可缓存段（cold 66.4%→warm 94.7%）——**但该数据只证明「静态稳定」保值，不证明「中部 append」保值**（v8 是过滤后工具集全程不变的曲线；imported 中途追加的缓存代价是 Q2.3 线性近似，**未经实测**）——三律的 append-only 设计以 Q2.3 模型 + compact 边界天然窗口为依据，**中部追加的实际 ratio 代价待 B-5 曲线实测回填**（实测前增强路径保守启用即 O-11 早期窗 + 杀死判据闸）。硬边界：数据来自 LAN 端点分段共享，第三方 provider 分段语义不透明（§7 R-1）。

**回退**：`[features] dynamic_tools`（默认 false，**会话启动一次性读取**——会话中途翻转 flag 会使 defs 变化，禁止，Sonnet 必改 11）→ 关闭即回到当前「全量 defs」基线；A/B/C 三段层级解耦可独立回退；**per-endpoint 灰度覆盖**（全局 flag 之上的 endpoint 级 override，对齐 R-1 灰度需求）。

## 8. 实测数据引用

1. **`--tools` 过滤收益 Δ ≈ 8.5K tok/轮**（ling-B 第八版，2026-10-09 指挥官提供）——defs 是每轮固定开销重要构成的直接证据；本管线三层设计是该收益的全自动形态。
2. **过滤工具集更新后 cold 66.4% → warm 94.7%**（ling-B v8）——工具集构成稳定后是可缓存段；imported append-only 的实证前提。**注意**：服务器端分段不对称（「无过滤 resume ratio 持平」成因）仍是待跟进项——R-1 列为最大风险，不作跨端点普适结论。
3. **旁路实验（2026-10-09）**：`--disallowed-tools` 从 defs 摘除终端工具后，模型自行找到 `monitor` 旁路跑完 shell 任务——defs 摘除完全不是执行边界（Sonnet R-2 预言实锤且更严重：模型有创造力找旁路）。**「藏工具=限权」路线废除的铁证，v2 根基改写的直接动因**（§1.3）。
4. **verify-then-use（2026-10-09）**：模型先 `search_tool` 验证注册表再行动，盲从注入的伪工具被拒——找回通道自带防幻觉属性（安全副产品，非设计目标）。
5. **命名域混淆教训（2026-10-09 eval）**：wire 名 `run_terminal_cmd`（`registry/types.rs:40`）vs 模型自述 `run_terminal_command`——eval 失败根因之一；制度化为 C-5 契约（Q2.1，v3 两域重写）。
6. **cache_read_ratio 全链已通**：`UsageTotals::cache_read_ratio`（`usage.rs:78-82`）→ headless JSON 投影；批次 1 修复 `Default::default()` 真 bug（commit e6c6a461）——本设计对账仪器就位。
7. **ling 系供源说明**：上述 ling-B 数据出自 ling-B 第八版实测；ling-A 为同系列对照实测（方向一致，口径以 ling-B 为主）。两路均为指挥官转述并作为评审输入，本文引用时保持原始口径，若后续实测修正以实测为准（AGENTS.md §0 裁决顺序）。
8. **【v3 新增】use_tool 实现层证据（2026-10-10 产出方自审）**：`UseToolInput` doc 明文 "Must be a tool previously discovered via `search_tool`" + "Use the parameter schema returned by `search_tool` to construct this"（`use_tool/mod.rs:13-19`）——MVP 两轮模式是现状 MCP 域机制的同构推广；`native_tool_correction` 默认 true 对原生工具名返回 "call it directly"（`:30-52`）——**v2 的「直呼=纯现状能力」声称被此证据推翻**，B-12 门控为 MVP 必需前置；use_tool 设计动机 doc（`:75-78`）"keeping the tool set stable across turns (no KV cache breaks)"——本设计的天然先例。
9. **【v3.1 新增】compact 档案层 detail 四档（2026-10-10 K3 终审核验）**：`CompactionDetail`（`compaction_transcript.rs:34-56`）None/Minimal/Balanced/Verbose（默认 Verbose）——档案层 tool_use 签名保留度随档位；**重建层 raw_input 保留未核**（O-14，Phase C 前置）——重放提示依赖挂牌的直接依据。
10. **【v3.1 新增】PTY harness scripted 先例**：`cf-pager-pty-harness/src/scripted.rs` + `scenarios/`（8 场景文件）——脚本化序列回放的现成 harness 形态，B-1/B-2 hermetic 主验收的参照。
