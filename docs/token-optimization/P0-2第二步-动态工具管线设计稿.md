## 0. 术语约定

| 术语 | 本文含义 |
|---|---|
| **常驻段（resident）** | 每轮 defs 无条件携带的工具集合，顺序固定，回合内/跨回合永不变化（尾部 plan 对例外，见 Q2-plan） |
| **按需段（imported）** | 经 `tool_search` 解锁后追加到 defs 尾部的工具集合，append-only，本会话不解锁不出现 |
| **meta 层工具** | `use_tool` / `search_tool`（ToolKind::UseTool / ToolKind::SearchTool，`tool_taxonomy.rs:67-68`）——工具管线的自通道，恒保留 |
| **defs** | 每轮 API 请求中的 tools 定义数组（tool definitions wire 段） |
| **wire 名（client_name）** | 模型在 tool_use 里写的名字 = defs 里的 function.name。内建保留名单 `RESERVED_BUILTIN_TOOL_NAMES`（`registry/types.rs:31-50`，`run_terminal_cmd` 在 :40） |
| **模型自述名** | 模型在思考/文本中**自称**的工具名——可与 wire 名不一致（实例：wire 名 `run_terminal_cmd`，模型自述 `run_terminal_command`——2026-10-09 eval 教训，制度化为 C-5 契约） |
| **注册面** | 工具能否被**执行**的边界：`ToolServerConfig.tools` 装配（`registry/types.rs:267`）+ `CapabilityMode::filter` 在此层裁剪（`capability.rs:41-53`）。注册面之外 = dispatch 必然失败 |
| **投影面** | 每轮 defs 发送哪些已注册工具的定义（`prepare_tool_definitions_inner`，`sampler_turn.rs:169-173`）。投影面裁剪 ≠ 执行边界（§1.3 实锤） |
| **成果压缩层** | 对**历史工具输出正文**的清洗层（pruning/hard-clear），与 defs 无关，作用于 conversation items |

## 1. 省钱与限权的分离（v2 根基节，全稿第一原理）

### 1.1 用户三连拍板（2026-10-09，逐字采信）

1. **「没有工具了模型能干好活嘛？」→ 不能。** 藏工具必须配「怎么拿回来」——`tool_search` 下发 schema 就是拿回通道；藏 ≠ 删，是收进抽屉，抽屉上必须有标签。
2. **「为啥不给工具？」→ 不是安全，是省钱。** 工具定义每轮全量发送是开销大头（ling-B v8 实测 `--tools` 过滤 Δ ≈ 8.5K tok/轮，§8-1）。本管线自始至终是**成本工程**，不是权限工程。
3. **「不想让调用工具直接派子智能体限制工具不就可以了嘛？」→ 完全正确，且点破 v1.1 根基错误。** 需要限制模型用某工具时，用**子代理工具限制**——这是已有机制（spawn 时 `apply_to_subagent_definition` 绑定父会话 `--tools`/`--disallowed-tools`/`--permission-mode`，`subagent/mod.rs:401-407`；子代理独立 auto-compact 阈值即上下文硬预算实例，`subagent/mod.rs:387-400`）。限权不归本管线。

### 1.2 拍板推翻了 v1.1 的什么

v1.1 的根基错误：把「defs 投影层过滤」与「权限/安全」藕断丝连——

- v1.1 §2.1 把 use_tool 旁路称为「**安全注意点**」；
- v1.1 R-2 称「安全边界在 server-side denylist + plan 过滤器」——但 plan 过滤器同样只作用于 defs（且现状是恒等 pass-through，§3-2.4），`use_tool` 旁路 plan 过滤器与旁路 defs 是**同一性质**，R-2 的「安全」主张自相矛盾（Sonnet 必改 6）；
- 整体隐含把 tool_search 解锁当成分级授权——方向性错误。

拍板 2 纠正：defs 全量发送的动机自始至终是**省钱**。投影面裁剪省的是每轮 token，不是权限。

### 1.3 旁路实锤（2026-10-09 实验，权限侧死刑判决）

**实验**：`--disallowed-tools` 将终端工具从 defs 摘除后下达需要跑 shell 的任务。
**结果**：模型自行发现 `monitor` 工具可代行终端能力，经其旁路**跑完了整个任务**。
**结论**（三点，全部写入 v2 设计）：

1. **defs 摘除完全不是执行边界**。不是「理论上有 use_tool 旁路」（v1.1 仅此程度），而是**模型有创造力主动找旁路且当天就找到了**——Sonnet R-2 预言实锤且更严重。
2. 对**省钱目标无害甚至有利**：模型绕过投影面拿到工具 = 工作没被卡死，常驻段照样省了 token。旁路是本管线的**可接受现象**。
3. 对**限权期望是死刑**：任何把「投影面裁剪」当限制的用法都会被模型绕过。限权必须落在执行面（注册面裁剪 / capability-mode / 子代理限制）。

### 1.4 权限完全剥离声明（v2 对 v1.1「安全注意点」的改写）

本管线（常驻切分 / tool_search 解锁 / imported 追加）做出如下**不可撤销的设计声明**：

1. 投影面的任何变化**不构成、不得被解读为、不得被用于**权限语义。defs 里没有某工具 ≠ 模型用不了它（use_tool 间接派发是现状：`registry/types.rs:1665` 的 `if tool_name == "use_tool"` 分派 + `:422` `effective_tool_name` 记录）。
2. 解锁 ≠ 授权；不解锁 ≠ 禁用。tool_search 的解锁域描述的是「本轮 defs 里有什么」，不是「模型被允许用什么」。
3. 执行面闸门（若需要）属于**权限侧独立事项**，与本文互不改动：注册面 `CapabilityMode::filter`（`capability.rs:41-53`，fork 时 `is_subset_of` 拒绝能力放大 :59-66）、`--permission-mode`、子代理工具限制（`subagent/mod.rs:401-407`）。本管线不实现、不依赖、不声称其中任何一个。

### 1.5 职责对照表（谁管什么）

| 需求 | 正确机制 | 所在层 | 与本文关系 |
|---|---|---|---|
| 每轮 defs 太贵（~8.5K/轮） | **本管线**：常驻切分 + 按需投影 | 投影面 | ✅ 本文全部内容 |
| 模型不知道某工具存在 | `tool_search`：藏了就给检索通道（schema 下发） | 投影面 + meta 层 | ✅ 本文 Q2 |
| 「模型不该用工具 X」（权限） | capability-mode（注册面，`capability.rs:41-53`）/ `--disallowed-tools` + 子代理继承（`subagent/mod.rs:405`）/ permission-mode / 主循环 spawn 只读受限子代理 | 执行面 | ❌ **明确不在本文**（§1.4 声明 3） |
| 上下文历史太长 | 成果压缩层（Q3）+ auto-compact（不动） | conversation 内容 | ✅ 本文 Q3（只碰 ToolResult 正文，无权限语义） |

## 2. 目标与非目标

### 2.1 目标

1. **把每轮 defs 从「全量恒带」改为「常驻段 + 按需段」**：直接砍每轮固定开销大头——**动机是省钱（拍板 2），不是限权**（《方案.md》§2:14「工具定义随请求全量发送」、§5:70 问题 2）。
2. **找回通道（tool_search）**：模型通过恒驻的 meta 层工具按需把藏起来的工具「拿回来」（schema 下发到 tool_result，MVP 路径零 defs 变化，见 Q2）——主循环不被卡死。
3. **KV cache 分段稳定**：常驻段前缀永不变；imported 段 append-only；杜绝 per-turn 随机裁剪（v3 #2 处方）。
4. **成果压缩层**：per-turn 对历史工具输出的确定性降级/丢弃，填补 P0-2 第一步做不到的**历史增长**维度（《方案.md》§1:15）。
5. **口径单一**：与第一步已落地的 `--tools` 静态过滤共用同一收口与同一计数面，防止三处漂移复发。

### 2.2 非目标（本次不做）

| 非目标 | 理由 |
|---|---|
| **权限语义完全剥离（v2 新增，第一非目标）** | 本管线不做、做不了、也不声称任何权限效果——旁路实锤（§1.3）+ defs 摘除非执行边界（§1.4）。需要限权 → 执行面机制（§1.5 表） |
| **不修复 use_tool 对 plan/server 策略的既有旁路** | 现状即如此（`registry/types.rs:1665`）；是否在执行面加闸是权限侧独立事项，改 use_tool 语义超出本文（v1.1 已声明 use_tool 派发语义不动，维持） |
| MCP 工具面与注册机制不动 | MCP 工具经 `register_mcp_tools` 动态注册（`bridge.rs:157-174`，调用点 `mcp.rs:353`、bridge 重建后重注册 `mcp_snapshot.rs:372`），注册本体、`into_registration` 歧义名校验（`cf-mcp/src/servers.rs:1264`）、use_tool 间接派发全部原样。本设计只改 defs **投影层** |
| 异步 plan 模式甄别机制不动 | `filter_cursor_tools_by_plan_mode` 现状为恒等 pass-through（§3-2.4），本设计只声明未来真身激活时的约束（Q2-plan），不改 plan 进出判定 |
| 不做 reasoning 块老化（#1-B） | v3 #1 真增量 B 单列设计（prune 范围仅 ToolResult——`request_builder.rs:222-225` 非 ToolResult 即 continue；Reasoning 仅在 token 估算中计数、不清，`mutations.rs:301-304`）。Phase C 的 prune 输入通路天然可容纳，留待 Phase C 后评估 |
| 不做 P1-2 动态压缩阈值 / P1-3 自适应 effort | 各有小设计稿；本文只声明边界（§7 R-4） |
| 不动 auto-compact 既有阈值链 | 6 级解析与 85% 触发（《方案.md》§3:35-36）是 high-watermark 兜底；成果压缩层是低水位独立层，二者并存不互改 |

## 4. 设计总览：三层管线

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 每轮请求组装（defs 投影层；dynamic_tools=false 时整图退化为现状单段）        │
│                                                                        │
│  ┌──────────────┐   ┌──────────────────────────┐   ┌───────────────┐   │
│  │ 常驻段        │ + │ 按需段（imported）          │ + │ (回合级)       │   │
│  │ resident set  │   │ tool_search 解锁追加       │   │ STRUCTURED_   │   │
│  │ 固定前 N defs │   │ append-only，按解锁时序     │   │ OUTPUT_TOOL   │   │
│  │ 跨回合永不变   │   │ 本会话不解锁不出现          │   │ （现状沿用）    │   │
│  └──────────────┘   └──────────────────────────┘   └───────────────┘   │
│      ▲ 常驻段一旦发出，后续轮字节级不变；plan 对恒驻常驻段尾部固定槽        │
│      ▲（Q2-plan）；imported 段只增不减                                   │
└────────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────────┐
│ 对话内容组装（成果压缩层，低水位独立层；无权限语义）                        │
│  低水位批量清（仅 ToolResult 正文，滞回先例 request_builder.rs:290-307）    │
│   →  既有 >50% should_prune 层 →  85% auto-compact 兜底（不动）           │
└────────────────────────────────────────────────────────────────────────┘
```

**与 headless `--tools` 的关系（Opus 阻塞项终裁：替换语义，非 ∪ 非 ∩）**：

- **设置白名单时**：常驻段 = **白名单 ∪ meta 二元**（**替换**默认集，默认集整体不参与）；解锁域 **⊆ 白名单**。用户显式给名单是明确的上下文裁剪意图（省钱语义，非权限语义——§1.4），tool_search 不得越过它：否则 `--tools` 失去裁剪力（Opus 阻塞场景）。白名单之外但注册面存在的工具，模型仍可经 use_tool 触达（现状能力，非本管线授予）。
- **未设置白名单时**：常驻段 = 默认集（Q1 表）；解锁域 = 注册全集 − 排除面（plan 真身排除 + server 策略排除；MCP 面按 namespace 排除规则见 Q1）。
- 第一步白名单是**手工**裁剪，第二步是**自动**按需；二者在「设置时」叠加为「白名单内再切常驻/按需」。

**分层选择理由**（v1.1 保留）：defs 是每轮固定开销、conversation 是可变增长开销（《方案.md》§1:11-15），两层作用对象、触发时机、缓存破坏语义完全不同，合成一套「动态裁剪」会互相拖累验收口径——故显式三分。

### Q2：tool_search——藏 + 告诉模型怎么拿回来（v2 大改）

**v1.1 错误回顾**：v1.1 直接选了「解锁 = defs 追加」为唯一路径（最破坏缓存的方案，Sonnet 阻塞 3），且没回答「模型怎么拿回来」的完整闭环。v2 采信拍板 1（藏必须配拿回通道）+ Sonnet 替代方案评估，改为**双路径**：

#### Q2.1 双路径定义

| 路径 | 机制 | defs 影响 | 缓存影响 | 裁决 |
|---|---|---|---|---|
| **MVP：schema 入 tool_result + use_tool 直呼** | `tool_search(query)` 返回结果列表含**完整 input schema**；模型立即以 `use_tool` 按 qualified 名调用 | **零变化** | **零破坏** | ✅ **Phase B 首发形态** |
| 增强：imported 段 defs 追加 | 解锁后下一轮起该工具进 imported 段，直接正名调用 | 尾部追加 | 追加点后前缀作废一次 | ⏸ 数据支持后按盈亏平衡启用（Q2.3） |

**MVP 路径的模型行为背书（本会话实证，2026-10-09）**：

1. **模型原生两轮模式**：当前会话的系统提示明文「MUST call `search_tool` first to retrieve the tool's input schema before calling `use_tool`. NEVER guess parameter names — always use the exact schema returned by `search_tool`」——**藏（defs 无 schema）+ 告诉怎么拿回来（明文指路）+ 拿回（tool_result 携带 qualified 名与完整 schema）+ 用（use_tool 精确调用）** 的完整闭环是模型可稳定执行的使用模式。
2. **verify-then-use**：模型先 `search_tool` 验证注册表再行动，对注入的伪工具名盲从被拒——找回通道自带一层防幻觉属性（安全副产品，非设计目标，§1.4）。
3. **命名域混淆教训**：同一实验中模型自述 `run_terminal_command`，wire 实名 `run_terminal_cmd`（保留名表 `registry/types.rs:40`）——**tool_search 返回的名字必须逐字节等于模型可直接调用的名字**，并在 tool_result 中明示「逐字节使用此名」。制度化为契约 C-5。

**tool_result 语义（MVP 契约）**：`tool_search(query) -> { results: [{ name, kind, one-line description, input_schema, qualified_name }] }`；结果按 kind 聚簇排序；**不含常驻段已有工具**（防元工具自我检索成环）；被 server 策略/注册面排除的工具**不出现**（未注册即不可见，B-8）；plan 真身排除的工具标注「当前模式不可用」（真身未激活时无此形态）。

#### Q2.2 clock 语言（落地锚点，v1.1 保留）

- defs 组装点唯一：`prepare_tool_definitions_inner`（`sampler_turn.rs:169-173`）——imported 投影（若启用增强路径）在此追加第三段（**投影过滤，非 registry 状态变更**——registry 全量注册不动）。
- 口径单一点：`turn_base_tool_specs`（`sampler_turn.rs:159-165`）——unlock 状态先于该点生效，turn 列表 / `/context` 计数 / compaction 三口同口径（doc :154-159 + drop_web_search doc :111-121 的三口共用契约）。
- 先例：headless `--tools`（D 通道 `acp/mod.rs:431-433`）已是「per-session 工具面由 config 决定」的先例——tool_search 的 imported set 是其运行时孪生：同一投影点、同一计数面。

#### Q2.3 增强路径的解锁时机——盈亏平衡模型（Sonnet 阻塞 2）

**问题**：defs 位于 system + messages 之前，第 t 轮追加 defs 等于其后全部前缀缓存作废一次；晚期解锁的重算成本可能远超收益（v1.1 §7 的 66.4%→94.7% 是**静态过滤后保持稳定**的数据，不能证明会话中途追加安全——Sonnet 正确指出）。

**模型**（简化线性，参数待遥测回填）：

- 追加代价 ≈ `B_k`（追加字节对应的 token 数）× `H_t`（第 t 轮 history 已有 token 数）× `Δprice`（cache-write 与 cache-read 单价差，LAN 端点实测口径待采）——一次性；
- 持续代价 ≈ `B_k × (R − t)`（其后每轮多带）；
- 收益 ≈ 每次省 use_tool 中转一跳（采样延迟 + 中转 output tok）× 期望使用次数 `U_k × (R − t)`。
- **判据**：`H_t × Δprice + B_k × (R−t) < 跳数收益 × (R−t)`。因 `H_t` 随 t 单调增长，**晚期解锁净收益转负**——这就是时机门控的依据，不是拍脑袋。

**裁决**（数据不足时保守）：

1. **会话早期窗（默认前 N 轮，N 待遥测定参，O-11）**：imported 追加自由；
2. **晚期**：只走 MVP 路径（use_tool 直呼，defs 零变化零缓存代价，代价仅每次一跳中转）；
3. **compact 边界**：压缩重建后前缀本就重算，**追加零缓存代价**——天然解锁窗口，晚期攒下的解锁请求在 compact 后一次放行；
4. Phase B 并行收集：per-tool 定义 token 表（B-10）、解锁时点 × 剩余轮数 × ratio 曲线（B-5）——回填模型参数后把 N 从开放问题转配置。

#### Q2.4 imported 生命周期（Sonnet 阻塞 4，四场景全定义）

| 场景 | 裁决 | 理由 / 现成锚点 |
|---|---|---|
| **resume** | imported 状态随会话持久化；恢复时投影重建 = 常驻段 + **历史全部 imported 工具全量恢复** | 恢复后 defs 必须与历史已出现的 tool_use 对齐，否则部分 provider 拒绝未知 tool_use；保守全量恢复优先于「精确还原解锁时序」（时序还原为 O-8 优化项）。存储点开放（O-8：会话状态文件的 defs 快照段） |
| **fork（verbatim-fork）** | fork 子代理工具前缀与父 turn 一致是**现状契约**（`sampler_turn.rs:154-159`：「a verbatim-fork child's tool prefix can never silently drift」）——imported 快照随 defs 快照自然走，无新机制 | 现成锚点直接覆盖 |
| **subagent** | 子代理**从零开始**：不继承父 imported 集；子代理工具面由 spawn 限制机制决定（`subagent/mod.rs:401-407`），上下文独立硬预算（`subagent/mod.rs:387-400` 独立 auto-compact 阈值） | 权限/预算都在子代理机制内（§1.5）；工具面继承会让父的省钱决策污染子的独立预算 |
| **auto-compact** | imported 集**保留**（registry 全量不动、投影状态保留）；compact 后前缀本就重建，imported 不构成额外破坏 | 与 Q2.3-3 同一窗口逻辑 |
| **/clear** | imported 清空，全量回归常驻段 | 新任务新抽屉 |

#### Q2.5 与既有机制的交互（不破坏条款，v1.1 保留 + 修正）

| 机制 | 交互设计 |
|---|---|
| SearchTool/UseTool 恒保留 | `kind ∈ {SearchTool, UseTool}` 永不成为 imported 候选（已在常驻 meta 层），tool_search 结果列表不收录它们 |
| **capability-mode（v2 补成行，Opus Q2 缺口）** | capability-mode 是**注册面上游闸**（`CapabilityMode::filter` 裁 `ToolServerConfig.tools`，`capability.rs:41-53`；kind 驱动，`registry/types.rs:132-139` doc）——被它过滤的工具**根本没注册**，use_tool 也够不着（dispatch 必败），tool_search 自然查不到。**与 `--tools`（投影面）的本质区别：capability 在注册面、`--tools` 在投影面**。tool_search 解锁域 ⊆ 注册全集，天然在 capability 闸下游——**B-8 契约：deny 工具无法经 tool_search 复活**（因为不存在，不是被藏） |
| plan 模式（Q2-plan，Sonnet 必改 5） | 现状：过滤器恒等（§3.2.4），plan 进出零 defs 影响。**设计约束（真身激活时生效）**：① EnterPlan/ExitPlan 恒驻常驻段**尾部固定槽位**、永不被 plan 门控裁剪（v1.1 C-4 的「plan 过滤除外」修正为「plan 二元恒驻」）；② plan 门控若裁工具，只允许裁 imported 段或声明 plan 切换为**允许的缓存断点**（低频事件，一次断点买整个 plan 会话稳定）；③ 解锁不绕过 plan 的表述修正为：解锁 = 知道它存在，投影层仍过 plan 真身闸——**此为投影面排序，非权限闸**（§1.4） |
| server-side denylist/allowlist | 同 capability 行：注册面排除 = tool_search 不可见（B-8）。admin-fallback 不被 tool_search 干涉（unlock 是投影层 unary 操作，不回写 registry）；unlock 后 server 收紧的中间窗口 = 下一轮投影生效（O-2 保留） |
| STRUCTURED_OUTPUT_TOOL | 合成工具位于 defs 尾部（`turn.rs:4-7`）；imported 追加会使其后移——因其本就 per-turn 易变（合成、never executed），影响接受（Sonnet 可后补 16 升级为明示） |

**KV cache 分段三律**（v1.1 保留，措辞规范化）：

1. **常驻段 = 最前缀**：defs 按固定顺序（常驻段内部排序键 = client_name 字典序，Phase A 固化；plan 对钉尾部）恒置于头部，任何轮不增删重排。
2. **imported 段 append-only**：新解锁永远追加尾部，不按字典序插队（插队会在已有 imported 工具之间移位，作废其后全部前缀——含整个 history）；解锁后不回收（per-session lifetime，/clear 例外）。
3. **杜绝 per-turn 随机裁剪**：任何轮不得从 imported 段摘除工具。

实测背书（ling-B v8，§8-2）：工具集构成稳定后是可缓存段（cold 66.4%→warm 94.7%）；硬边界：数据来自 LAN 端点分段共享，第三方 provider 分段语义不透明（§7 R-1）。

**回退**：`[features] dynamic_tools`（默认 false，**会话启动一次性读取**——会话中途翻转 flag 会使 defs 变化，禁止，Sonnet 必改 11）→ 关闭即回到当前「全量 defs」基线；A/B/C 三段层级解耦可独立回退；**per-endpoint 灰度覆盖**（全局 flag 之上的 endpoint 级 override，对齐 R-1 灰度需求）。

### Q3：per-turn compress 时机（成果压缩层）——与 prune_retained TTL 协调（Sonnet 必改 9）

**作用对象**：历史 `ConversationItem::ToolResult` 正文（prune 作用域 `request_builder.rs:222-225`：非 ToolResult 即 continue）。

**触发候选**（v1.1 保留，B 推荐）：

## 8. 实测数据引用

1. **`--tools` 过滤收益 Δ ≈ 8.5K tok/轮**（ling-B 第八版，2026-10-09 指挥官提供）——defs 是每轮固定开销重要构成的直接证据；本管线三层设计是该收益的全自动形态。
2. **过滤工具集更新后 cold 66.4% → warm 94.7%**（ling-B v8）——工具集构成稳定后是可缓存段；imported append-only 的实证前提。**注意**：服务器端分段不对称（「无过滤 resume ratio 持平」成因）仍是待跟进项——R-1 列为最大风险，不作跨端点普适结论。
3. **旁路实验（2026-10-09）**：`--disallowed-tools` 从 defs 摘除终端工具后，模型自行找到 `monitor` 旁路跑完 shell 任务——defs 摘除完全不是执行边界（Sonnet R-2 预言实锤且更严重：模型有创造力找旁路）。**「藏工具=限权」路线废除的铁证，v2 根基改写的直接动因**（§1.3）。
4. **verify-then-use（2026-10-09）**：模型先 `search_tool` 验证注册表再行动，盲从注入的伪工具被拒——找回通道自带防幻觉属性（安全副产品，非设计目标）。
5. **命名域混淆教训（2026-10-09 eval）**：wire 名 `run_terminal_cmd`（`registry/types.rs:40`）vs 模型自述 `run_terminal_command`——eval 失败根因之一；制度化为 C-5 契约（Q2.1）。
6. **cache_read_ratio 全链已通**：`UsageTotals::cache_read_ratio`（`usage.rs:77-82`）→ headless JSON 投影；批次 1 修复 `Default::default()` 真 bug（commit e6c6a461）——本设计对账仪器就位。
7. **ling 系供源说明**：上述 ling-B 数据出自 ling-B 第八版实测；ling-A 为同系列对照实测（方向一致，口径以 ling-B 为主）。两路均为指挥官转述并作为评审输入，本文引用时保持原始口径，若后续实测修正以实测为准（AGENTS.md §0 裁决顺序）。
