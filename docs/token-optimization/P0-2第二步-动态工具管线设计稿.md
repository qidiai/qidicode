## 0. 术语约定

| 术语 | 本文含义 |
|---|---|
| **常驻段（resident）** | 每轮 defs 无条件携带的工具集合，顺序固定，回合内/跨回合永不变化或尾部只增 |
| **按需段（imported）** | 经 `tool_search` 解锁后追加到 defs 尾部的工具集合，append-only，本会话不解锁不出现 |
| **meta 层工具** | `use_tool` / `search_tool`（ToolKind::UseTool / ToolKind::SearchTool，`tool_taxonomy.rs:69-70`）——工具管线的自通道，恒保留 |
| **defs** | 每轮 API 请求中的 tools 定义数组（tool definitions wire 段） |
| **成果压缩层** | 对**历史工具输出正文**的清洗层（pruning/hard-clear），与 defs 无关，作用于 conversation items |

## 1. 目标与非目标

### 1.1 目标

1. **把每轮 defs 从「全量恒带」改为「常驻段 + 按需段」三层管线**：直接砍 P0-2 识别的每轮固定开销大头（《方案.md》§2:14「工具定义随请求全量发送」、§5:70 问题 2）。
2. **解锁触发器（tool_search）**：模型通过恒驻的 meta 层工具按需把长尾工具「拉进」本轮会话，主循环不被卡死。
3. **KV cache 分段稳定**（#2 张力核心）：常驻段前缀永不变；imported 段 append-only；**杜绝 per-turn 随机裁剪**（v3 #2 处方："动态裁剪与 hard-clear 老化统一在缓存段稳定设计下考虑"，v3 勾连节 :37-39）。
4. **成果压缩层**：per-turn 对历史工具输出的确定性降级/丢弃（硬清占位符 + spill 指针回读），填补 P0-2 第一步做不到的**历史增长**维度（第一步只砍 defs 固定段，历史是可变开销大头——《方案.md》§1:15）。
5. **口径单一**：与第一步已落地的 `--tools` 静态过滤共用同一收口与同一计数面，防止三处漂移复发。

### 1.2 非目标（本次不做）

| 非目标 | 理由 |
|---|---|
| **MCP 工具面与注册机制不动** | MCP 工具经 `ToolBridge::register_mcp_tools` 动态注册（`bridge.rs:153-171`），注册本体、`into_registration` 歧义名校验链、`use_tool` 间接派发（registry/types.rs:419-423 `DispatchParts::effective_tool_name`）全部保持原样。本设计只改 defs **投影层**（每轮发送哪些定义），不动注册与执行 |
| **异步 plan 模式甄别机制不动** | `filter_cursor_tools_by_plan_mode(defs, plan_active)`（调用点 `sampler_turn.rs:169`）既有语义保留；本设计只保证解锁工具**再次穿过** plan 过滤器，不改动 plan 模式自身的进出判定 |
| **`use_tool` 间接派发语义不动** | 模型经 `use_tool` 调用未直接暴露在本轮 defs 中的已注册工具是**现状**（meta 层旁路）；本设计的 tool_search 解锁是 defs 投影层增强，不改变 `use_tool` 执行路径 |
| **不做 reasoning 块老化（#1-B）** | v3 #1 真增量 B 单列设计（prune 范围仅 ToolResult——`request_builder.rs:217-219` 非 ToolResult 即 continue、Reasoning 只测不清 :302-305）；与成果压缩层同图窗但独立验收，并入设计范围会让 Phase C 验收口径复杂化。标注：**Phase C 的 prune 输入通路已天然可容纳**（作用域判断集中在一处 switch），留待 Phase C 验收后评估是否顺路 |
| **不做 P1-2 动态压缩阈值 / P1-3 自适应 effort** | 各有小设计稿（《优化执行规划.md》§3.2）；本文只声明边界（§6 风险 4） |
| **不动 auto-compact 既有阈值链** | 6 级解析与 85% 触发（《方案.md》§3:35-36）是 high-watermark 兜底；成果压缩层是低水位独立层，二者并存不互改 |

## 3. 设计总览：三层管线

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 每轮请求组装（defs 投影层）                                               │
│                                                                        │
│  ┌──────────────┐   ┌──────────────────────────┐   ┌───────────────┐   │
│  │ 常驻段        │ + │ 按需段（imported）          │ + │ (回合级)       │   │
│  │ resident set  │   │ tool_search 解锁追加       │   │ STRUCTURED_   │   │
│  │ 固定前 N defs │   │ append-only，按解锁时序     │   │ OUTPUT_TOOL   │   │
│  │ 跨回合永不变   │   │ 本会话不解锁不出现          │   │ （现状沿用）    │   │
│  └──────────────┘   └──────────────────────────┘   └───────────────┘   │
│      ▲ 裁剪只允许发生在「非本轮 Konversation 内容」：                      │
│      ▲ defs 段一旦本轮发出，下一轮常驻段字节级不变(R-006 可验收)            │
└────────────────────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────────────────────┐
│ 对话内容组装（成果压缩层，低水位独立层）                                    │
│                                                                        │
│  低水位（新，仅 ToolResult，批量对齐段边界 hard-clear 占位符+指针/重放提示    │
│  →  既有 >50% should_prune 层 →  85% auto-compact 兜底（不动）             │
└────────────────────────────────────────────────────────────────────────┘
```

**与 headless `--tools` 的关系：共存升级，不破坏**。`--tools` 保持现语义（静态白名单裁剪、全模式可用）；动态管线在其上叠加：「常驻集 = `--tools` 白名单命中（若设置）∪ 内建默认常驻集，imported 解锁域 = 注册全集 − 常驻 − server/plan 排除面」。第一步的白名单是**手工**裁剪，第二步是**自动**按需；二者不互斥（§4-Q4 统一空白名单语义）。

**分层选择理由**：defs 是每轮固定开销、conversation 是可变增长开销（《方案.md》§1:11-15），两层作用对象、触发时机、缓存破坏语义完全不同，合成一套「动态裁剪」会互相拖累验收口径——故显式三分。

## 4. 四问题的设计决策

### Q1：core-toolset 固定段怎么切

**代价模型**（先定量再选集）：

| 错误方向 | 代价 | 量级 |
|---|---|---|
| 常驻段选错（留了低频工具） | 每轮白带其 definition tokens（低频工具定义通常 200-800 tok/个）；N 个错误 × 每轮 | 线性积累，但**不卡流程** |
| 常驻段遗漏（缺了高频工具） | 主循环每次需要它都要 `tool_search→下一轮解锁`：一次额外 round-trip（conservative ≥ 数百 output tok + 采样延迟），且解锁前该动作**不可执行**——任务可能停在等待 | 每次遗漏一次跳数；**流派失败面子更重** |

**结论：偏保守**——常驻集宁可稍大。遗漏代价里真正的尾部风险是「模型不知道该工具存在」：tool_search 的 description 必须让模型**无需预先知识**也能查到（Phase B 验收项）。

**参照系对照表**（micro-tech 的 7 常驻 = 终端 / 读文件 / 写文件 / search / js 执行，另加 meta；对照 qidicode 内建按 `ToolKind` 语义类）：

| micro-tech | qidicode 对应（kind, tool_taxonomy.rs:35-73） | 本文裁决 |
|---|---|---|
| 终端 | `Execute`（`run_terminal_cmd`，保留名 registry/types.rs:36-42 中的 `run_terminal_cmd`） | **常驻** |
| 读文件 | `Read`（`read_file`；分页 image/pdf/pptx 同入口） | **常驻** |
| 写文件 | `Write`/`Edit`（`write_file` / `search_replace`；hashline 变体属同 kind） | **常驻**（两命一体：模型多在编辑循环里） |
| search | `Search`（grep 双实现）/`ListDir`（list_dir/list）/glob | **常驻 Search + ListDir**（探索链最小面） |
| js 执行 | qidicode 无常驻 JS 沙盒（`Execute` 已覆盖） | 不适用 |
| ——（micro-tech 未列而 qidicode 必需） | `AskUser`（`ask_user`） | **常驻**：提问是**任务不能静默卡死**的红线（《方案.md》§6:92 🚫 禁区精神——拿不到提问通道的模型会死循环或臆造） |
| —— | `SearchTool`/`UseTool` | **恒驻 meta 层**（非裁决、恒等式，见 Q2） |
| —— | `EnterPlan`/`ExitPlan` | **常驻**（低频但进出 plan 是即时意图动作，遗漏=意图翻转抖动） |

**默认常驻集（推荐，按 kind 表达所以 name_override 无关）**：

| # | ToolKind | 代表 wire 名 | 理由一句话 |
|---|---|---|---|
| 1 | `Read` | `read_file` | 万能前摇；`is_read_only`（tool_taxonomy.rs:80-90） |
| 2 | `Edit` | `search_replace`(default editor) | 写入循环主体 |
| 3 | `Write` | `write_file` | 造文件主路径 |
| 4 | `Execute` | `run_terminal_cmd` | 环境操作主轴（含后台任务子形态） |
| 5 | `Search` | `grep`（codex/qidi_build 双实现取注册项） | 探索链正文 |
| 6 | `ListDir` | `list_dir`(+glob 变体) | 轻探索；与 Search 同链 |
| 7 | `AskUser` | `ask_user` | 防卡死红线（见上） |
| 8 | `EnterPlan` | `enter_plan_mode` | plan 进出门槛（含 plan 过滤器协同，Q2） |
| 9 | `ExitPlan` | `exit_plan_mode` | 同上 |
| 10 | `SearchTool` | `search_tool` | meta 层恒驻（管线自通道之一） |
| 11 | `UseTool` | `use_tool` | meta 层恒驻（执行旁路，legacy 声明见 §2.1） |

**明确不进常驻**（首批 imported 候选 = 每轮白带纯浪费的大头）：`MemorySearch`/`MemoryGet`（会话启动普遍、持续低频）、`Task`/`BackgroundTask`/`WaitTasks`/`KillTask`（子代理与后台族）、`Monitor`/`GoalUpdate`/`Think`（编排件）、`Skill`/`DeployApp`（低频）、`ImageGen`/`VideoGen`/`ImageToVideo`/`ImageToVideo` 等生成系（低频+重）、`WebSearch`/`WebFetch`（低频；WebSearch 还要穿过 backend-search 单点剔除，现状保留）、`browser_*` 六件套（低频重头——对总 Δ 主要贡献分子）、`lsp`/`skill`。

> **注意第 10/11 条与 Q4 的关系**：`SearchTool`/`UseTool` 的恒驻不受 `--tools` 裁剪（Q4 契约 4）。

**回退方案**：常驻集以**配置表**承载（非硬编码 match），上线后由 ratio 指标 + tool 未命中遥测（Phase B 验收项）驱动一次性调表——调表不改代码路径。

### Q2：tool_search 解锁触发器

**语义定义**：`tool_search(query) -> 简短结果列表（name / one-line description / kind，不含 full schema）`。模型选择某个结果后，**下一轮起**该工具进入 imported 段（defs 追加），直接以正名调用（均值路径：search 一轮 → 调用一轮；**不强制**经 `use_tool` 中转）。

**clock 语言（落地锚点全在既有面）**：

- defs 组装点唯一：`prepare_tool_definitions_inner`（sampler_turn.rs:165-169）——在此追加第三段：`defs = resident ∪ imported` 的投影（**imported 是投影过滤，非 registry 状态变更**——registry 全量注册不动，MCP 面不动）。
- 口径单一点：`turn_base_tool_specs`（sampler_turn.rs:159-164）——unlock 状态必须先于该点生效，保证 turn 列表 / `/context` 计数 / compaction 三口同口径（该函数 doc 明示共享契约）。
- AgentDefinition 工具面先例：headless `--tools` 全模式收口（ConnectFlags→cli_agent_overrides，D 通道）已经是「per-session 工具面由 config 决定」的先例——tool_search 的 imported set 是它的**运行时孪生**：同一投影点、同一计数面。

**与三个既有机制的交互（不破坏条款）**：

| 机制 | 交互设计 |
|---|---|
| SearchTool/UseTool 恒保留 | `Kind ∈ {SearchTool, UseTool}` 的工具**永不成为 imported 候选**（已在常驻 meta 层），tool_search 结果列表也**不收录**它们（防止元工具自我检索成环）。恒保留的实现点沿用侦察报告口径（待执行复核具体行） |
| plan 模式过滤 | 解锁**不绕过 plan**：imported 段并入 defs 后**仍整体穿过** `filter_cursor_tools_by_plan_mode`（sampler_turn.rs:169，apply 顺序不变——即 plan 处于 active 时，imported 中的禁断类工具照样被剔除）。语义：「解锁 = 知道它存在」，「可用 = 再过当前模式闸」。验收：plan-active 下 tool_search 命中被 plan 排除的工具 → defs 无该工具（Phase B 验收 2） |
| server-side denylist/allowlist + admin-fallback | 解锁域 = `注册全集 − 常驻 − plan 排除 − server 侧策略排除`。server 排除面在组装链上游（ToolServerConfig 驱动注册与否，registry/types.rs:266-274；capability-mode 过滤 :131-139 是 kind 级既有先例）。**admin-fallback（server 策略变更时的既有回退行为）不被 tool_search 干涉**： unlocking 是投影层的 unary 操作，不回写 registry，server policy 重新生效时 defs 投影自动收窄——开放问题（§6 O-2）仅在「unlock 后 server 收紧」的中间窗口取证 |

**KV cache 分段稳定（与 #2 的张力核心）**：

1. **常驻段 = 最前缀**：defs 按固定顺序（排序键 = client_name 字典序，Phase A 固化）恒置于 defs 数组头部；本轮之后任何轮都不允许对其增删/重排。验收 = 相邻两轮 defs 前缀字节级相同（Phase A 验收 3）。
2. **imported 段 = append-only，按解锁时序**：新解锁工具**永远追加在 imported 段尾部**，不按字典序插队。理由：字典序插入会在已有 imported 工具之间**移位**（break 其后全部前缀缓存，包括后续 history 段——defs 位于 conversation 之前，defs 尾部变化等于把整个 history 前缀作废一次）；append-only 时序的代价仅是 imported 段顺序「不美观」，收益是**相邻轮 defs 增量 = 纯追加**。**杜绝 per-turn 随机裁剪**：任何轮次都不得从 imported 段摘除工具（本会话不解锁就不会出现，解锁后不回收；per-session lifetime）。
3. **工具集更新后的缓存行为实测背书**（ling-B 第八版，指挥官提供）：`--tools` 过滤工具集**更新后** cache cold 66.4% → warm **94.7%** 命中——工具集构成是一个**稳定可缓存段**， imposed-once 的段变化不会击穿缓存（v8 数据推翻 v5 早期「过滤击穿缓存」判断）。硬边界：该数据来自 **LAN 端点 KV 缓存的分段共享**，服务器端分段行为对第三方 provider 不透明（§6 风险 1）。
4. **批量解码（import batching）**：`tool_search` 返回结果按 kind 聚簇预取（一次 query 解锁相关联的小簇，如 `image_gen+image_edit`）——减少 suffix re-break 频率。**开放问题 O-3**：聚簇表还是模型自己多选。

**回退方案**：`tool_search` 保持恒驻但 defs 投影可整体关闭（config `[features] dynamic_tools = false` 默认关，Phase B 内部灰度再开）→ 一键回到当前「全量 defs」基线；层级解耦保证 A/B 任一阶段可独立回退。

### Q3：per-turn compress 时机（成果压缩层）

**作用对象**：历史 `ConversationItem::ToolResult` 正文（与既有 pruning 作用域一致，`request_builder.rs:217-219`）。

**触发的三个候选**：

| 候选 | 描述 | 裁决 |
|---|---|---|
| A：per-turn TTL 零碎清 | 每用户回合把「刚满年龄」的条目逐条清（现状 `prune_retained_conversation` 既有形态） | ❌ v3 #1-C 已判「**逐回合零碎清 = 破前缀缓存**」（v3 :19 C 项）——每过一个年龄边界改一次请求内容 |
| **B：批量对齐段边界**（推荐） | 低水位一次性**批量** hard-clear 到年龄线（同批所有过期 ToolResult 一次改净），把 N 次零碎清合并为 1 次 suffix break；触发后到下一个批量窗口之间**不再改**请求内容 | ✅ v3 :19 C 项明文处方（"无 cached_microcompact 原语则应批量对齐压缩段边界而非逐回合零碎清"） |
| C：交由 auto-compact 统一 | 不建低水位，等 85% 全量压缩 | ❌ 《方案.md》§3.1 既有 >50% should_prune 层与 85% auto-compact 已分层且各有质量兜底（§6:80-95 门控清单 1）——成果压缩层补的是**低水位确定性降级**，等 85% 太晚 |

**推荐 B，与既有层的边界**：低水位层在同一 prune 通路（`prune_conversation` 输入端）之上，仅把**触发时机**改为「低水位（开放问题 O-4：建议 60%？——低于 should_prune 的 50%……不对，50% 是 should_prune 现值，低水位应低于 50%；见 O-4）+ 批量诱导 + turn 边界聚合」；`PruningConfig` 配置面板扩展一节（`[compaction.pruning]` 已在 user-guide 13-memory.md:414-425），不新建第二套机制。

**成果降级语义（缺指针的处理——B1-8 结论的直接延伸）**：

- **有 spill 指针**（bash 系三站点，规划.md:111-116）：hard_clear 占位符天然保留 `full output at:` 行（`request_builder.rs:35-46`）——现状即回读可用，**复用不改造**。
- **无指针的可重放工具**（grep/read 系）：新增**重放提示**占位符形态——`[tool result aged; rerun grep with same args to reproduce]`（args 在该 ToolResult 的 raw_input 中仍可考）。语义上等价「软指针」：模型可自行重执行。不引入 spill-to-file（B1-8 已判「spill-to-file 机制本身即设计问题，不硬塞」（规划.md:111-116））。
- **无指针且不可重放**（memory get/search、image/pdf 读数、subagent 沉淀）：**降级为摘要占位符**（hard_clear 常规形态）——接受信息损失，但触发条件（低水位 + 批量）保证其发生在「该内容大概率已消费完毕」的阶段。**质量门控挂钩**：《方案.md》§6:92 🚫 禁区「**最近的工具结果原文**」不得触碰——低水位层的 `keep_last_n_turns`（既有字段，types.rs:69-94）语义原样保留并优先级最高。

**与 auto-compact 的关系**：**独立低水位层**（不在同一触发链）：auto-compact 管全量上下文重建（85%），成果压缩层管 ToolResult 正文密度（低水位起、50% should_prune 接管、85% 兜底）。三者共享 `PruningConfig` 面板但触发器、作用域、计数互不覆盖——验收各自独立（Phase C 验收 1-3）。

### Q4：空白名单 fail-soft 语义统一

**现状**（R-002 升级要求的同义词域扫描结论）：`--tools` 白名单空集 = 「未设置」= 不裁剪；`--tools 非法名,read_file` = 非法名跳过 + 合法名生效——两者都是 fail-soft。**危险绑定点**：tool_search 模式下若「空白名单」被新管线误读为「解锁域 = 空集」，则模型只有 search_tool/use_tool 可查——**剩余工具全部失联**——恰恰复现 YOLO 假阳性事故的失败形态（batch 1 已把防线修为断言语义，规划 §2.2 R-002 升级条）。

**统一规则（四条契约，全部落测试）**：

| # | 契约 | 断言形态 |
|---|---|---|
| C-1 | `--tools ""` ≡ 未设置 ≡ 全量 defs（不得裁剪） | `headless_parse_comma_list_splits_values`（既有）扩展：empty string 输入 → 无过滤分支，defs 计数全量 |
| C-2 | `--tools "非法名,read_file"` → `read_file` 生效 + 非法名 warn 日志 + 默认常驻集其余不动 | 既有 `connect_cli_tool_overrides_*` 族扩展 |
| C-3 | tool_search 模式下空白名单 = 解锁域 = **注册全集**（与 C-1 同一归一），并 emit warn 提示「白名单未设置，解锁域不受限」 | 新契约测试（Phase B） |
| C-4 | **SearchTool/UseTool 恒在 defs**（任何白名单/裁剪设置下；plan 过滤除外——plan 有自己的工具面规则并优先） | 新契约测试（Phase A）：对每一条裁剪配置输入，断言输出 defs 含 meta 二元 |

**YOLO 防线的测试化升级**：C-4 是断言语义（回归测试身份明确，R-003 带消息），不再依赖人工审读——这是 batch 1 教训的直接制度化。

## 5. 实现分层

### Phase A：常驻段固化 + 契约测试（不含 tool_search）

**范围**：defs 投影层加入 residentslice 切分（`prepare_tool_definitions_inner` 处 per-kind 分类，基于 `tool_for_kind` / `tool_kind`（bridge.rs:103-116）→ `ToolKind` 表驱动上表）；`--tools` 口径接入（白名单 ∪ 默认常驻）；四契约测试（§4-Q4 C-1～C-4）+ 常驻段字节级稳定测试。

**验收标准（可测行为断言）**：

1. **A-1（常驻稳定性）**：同一会话相邻两轮，`turn_base_tool_specs` 输出的常驻段前缀**字节级相同**（测试按 wire 序列化 strict-equal 对比两轮 snapshot）。
2. **A-2（口径一致）**：`turn_base_tool_specs` / `build_session_info` 的 `/context` 工具定义计数 / compaction 请求三处的常驻集**一致**（沿用 `drop_web_search_for_backend_search` 的三口共用测试模式，sampler_turn.rs:110-121 已有先例与测试命名即 `context_tool_definition_consistency::*`）。
3. **A-3（契约四条）**：C-1～C-4 全绿。
4. **A-4（plan 过滤后置秩序不变）**：resident 切分后 `filter_cursor_tools_by_plan_mode` 仍作用于**最终** defs（含 meta 层，except plan 有自己的规则）——plan-active 时 defs 与现状集合相同（**第一步不变量**：Phase A 单独上线对现有行为**零差异**，即 defs 全量=现状字节级）。★ 这是 Phase A 的定调验收——A 阶段是纯结构重组，不改任何用户可见行为。
5. **A-5（token 计数下降）**：常驻集对 defs 定义 tokens 的贡献 < 当前全量 defs 的 55%（ling-B v8 目标线；实测以 `/context` tool_definitions_count 为准）。

### Phase B：tool_search 解锁触发器 + imported append-only

**范围**：`tool_search` 工具（meta 层恒驻之二）；imported 投影段（append-only 时序）；plan/server 排除面交互；`[features] dynamic_tools` 总开关（默认 false）。

**验收标准**：

1. **B-1（解锁可用）**：`tool_search("video")` → 下一轮 defs 尾部含 `video_gen`（正名出现）→ 模型直接以 `video_gen` 调用成功（e2e）。
2. **B-2（plan 不绕过）**：plan-active 时 tool_search 命中被 plan 排除的工具 → 该工具不进 imported（defs 无）且 tool_search 结果标注「plan 模式下不可用」。
3. **B-3（append-only 不变式）**：解锁序 [A,B,C] 后三轮 defs 的 imported 段顺序恒为 A,B,C（不因字典序重排）；无任何轮次从 imported 段移除工具。
4. **B-4（防线契约）**：C-3/C-4 在 tool_search 模式下全绿（空白名单不被误读为空解锁域）。
5. **B-5（rate 对账）**：开启 dynamic_tools 的 warm cache_read_ratio ≥ 关闭态基线 − 2pp（B1-6 指标对账，数据源已在：`usage.rs:67-80` + notification 投影）。★ 依赖 ling-B 的多路实测口径（§7）。
6. **B-6（主循环不卡死）**：模拟 resident 遗漏场景（人为把 `MemorySearch` 移出常驻）——模型能用 tool_search 找到并解锁，无「工具不存在」死循环。
7. **B-7（回退一键）**：`dynamic_tools=false` 时 defs 与 Phase A 完成态字节级一致（关闭路径无残留）。

### Phase C：成果压缩层（低水位批量清）

**范围**：低水位触发（`PruningConfig` 新字段，命名待评审：`low_watermark_percent`，开放问题 O-4）；批量边界清（选项 B）；重放提示占位符（grep/read 系，按 tool kind 判定——`ToolKind` 现成）；与 spill 指针（bash 系）复用。

**验收标准**：

1. **C-1（分区独立）**：低水位层只改 ToolResult 正文，不动 user/assistant/Reasoning（Reasoning 不清，scope 与既有一致 `mutations.rs:302-305`——#1-B 不做，非目标）。
2. **C-2（批量语义）**：低水位触发时该批所有过期 ToolResult 同轮一次清净；从触发到下一窗口之间相邻轮请求内容**不改**（断言连续轮 suffix 前缀相等）。
3. **C-3（禁区挂牌）**：`keep_last_n_turns` 内、以及最后一个真实用户查询之后的首轮工具结果，永不落入批量清（对应《方案.md》§6:92 🚫 + §6 门控 1 的 sanitize 不变量——`compaction_utils.rs:879-918` ToolResult 配对不变量在压缩路径上的镜像）。
4. **C-4（重放可行性）**：grep 系被清结果提供重放提示占位符（含 kind 判定），模型按提示重跑可复现结果（e2e）。
5. **C-5（既有测试不破）**：`request_builder.rs:571-620` 五个既有行为测试全绿（指针保留/无指针降级/幂等/门控边界/enabled=false no-op）。
