## 1. 方案审计结论

### 1.1 原提案（三步：编译 → 设计稿 → 小项 → 再编译）

| 步骤 | 内容 | 问题 |
|---|---|---|
| 第 1 编译 | 把 0bda3df1 终清零编入 exe | 本身正确，但**不该单独成次** |
| 设计稿 | P0-2 第二步 + #5/#8 + P1/P2 | 时机无问题，与编译无关（纯文档，不触发编译） |
| 小项 → 第 2 编译 | 各未修小项再编译一次 exe | **浪费**：小项与 0bda3df1 无冲突面，两次编译可并为一次 |

### 1.2 合并为一次编译的依据（审计确认）

1. **无冲突面**【确认级】：0bda3df1 触及 31 个文件，而批次 1 小项涉及面为 `install-enterprise.sh`（脚本）、`attribution/credential_provider/storage_client`（死名改名——注意：storage_client.rs 在 0bda3df1 中改动 280 行，**同文件但不同区域**：0bda3df1 只加了 attribution callback 与 StampedBearerSuffix 转换，批次 1 只改字段标识符，git 侧为顺序追加，语义无冲突）、文档（home 目录叙事、env 命名域声明）、cf-shell 杂项。设计稿为纯文档产出，不进编译。
2. **编译成本不对称**：产品 exe 冷 30-90 分钟（AGENTS.md §12），且运行中 exe 不可覆盖需先改名。任何一次"只为小项"的编译都是全额成本，不因改动小而便宜。
3. **一次覆盖大**：第 1 编译只覆盖 0bda3df1；打散后第 2 编译覆盖小项。合并后单次编译同时覆盖 0bda3df1 + 全部批次 1 小项，exe 版本基线一次性前跃。

### 1.3 关键事实修正（诚实标注：与任务简报不符处）

**【确认级，需指挥官复核】起止时间线矛盾**：

```
0bda3df1  2026-10-07 21:51:59  终清零 commit
48d7b088  2026-10-07 22:48:24  crash-handler doctest 适配（0bda3df1 的直接子提交）
```

简报称"第五版 exe（10-07 22:13，基线 48d7b088）不含 0bda3df1"。但 git 时间线上 **48d7b088 在 0bda3df1 之后**，且 commit 时点（22:48）晚于 exe 构建记录（22:13）。两种可能：

- (a) exe 实际构建于 0bda3df1 提交后的工作树 → exe **已含终清零**，简报误记；
- (b) exe 构建进程起于 21:51 前的更早快照 → exe 不含终清零，简报基线号误记（22:13 不可能是 48d7b088 的基线）。

**裁定方式（进执行流第 0 步）**：不争论，直接用行为指纹判：跑一次 exe 内 `install.sh` 通道逻辑或检查 storage 401 归因事件是否带 `sent_key_prefix` 字段（0bda3df1 A-1/C 组新行为）。无论 (a)/(b)，**结论不变**：批次 1 唯一一次编译会把两者一起编入，浪费判定与批次编排不受影响——但归档口径必须先对齐，避免"第五版覆盖范围"在 NAS 档案里记错。
