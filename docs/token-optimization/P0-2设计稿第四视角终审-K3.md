# K3 终审报告（qidicode P0-2 动态工具管线 v3 设计稿）

## 一、Opus 关键发现复核

1. **∪/∩ 矛盾**：成立。v1.1 同一白名单在「常驻段=白名单∪meta」与「解锁域⊆白名单」间确实自相矛盾；v3 §4 改裁「替换语义」自洽（设置时白名单为全集、解锁域为其子集），方向正确。残余瑕疵：白名单外工具经 B-12 后仍可被 use_tool 触达，与「解锁域⊆白名单」并存但不冲突（省钱语义下自洽），建议 C-2 补一条「白名单外+注册面内→use_tool 可达」断言防误读。
2. **FinalizedTool 无直接 kind 字段**：成立且影响被低估——kind 经 `Arc<dyn ToolMetadata>.kind()` 读取意味着 kind 是**运行期动态分发**而非静态字段，name_override/自定义 metadata 注入场景下 kind 可被注册方伪造或错配；Phase A 的 kind→Vec 查询正确但缺「kind 与注册实例一致性」校验契约，建议 Phase A 增一测。
3. **「36 变体 vs 11 常驻」缺口严重性被 Opus 高估**：36 是 ToolKind 枚举变体数，非注册工具实例数；表中多数变体（Delete/Move/Plan/Lsp 等）标注「内建默认面未见注册实例」。实际缺口 = 注册实例数 − 常驻 defs 数（≈10-13），远小于 36−11。v3 穷尽表态 + 编译期断言已覆盖真正的风险（新增变体静默漏切分），此项可降级为非阻塞。

## 二、第三视角自由发现（前两视角盲区）

1. **【阻塞】B-12 跨层数据流未定义**：corrective 门控判定「原生名是否在本轮 defs」需要执行层（use_tool/registry）读取投影层（sampler_turn）的每轮状态——registry 层现状不持有 defs 投影（设计稿 §3.1 自证 InnerDispatch 只有 FinalizedToolset）。R-7-② 说「只读投影状态」但**投影状态如何下传到 use_tool 调用点全无机制设计**（新参数？全局状态？每轮注入？）。这是全稿唯一执行面改动，却恰好是全稿唯一没有 clock 语言的改动——v2 的教训（执行层声称须下钻实现层）在 v3 自己身上复现。
2. **【阻塞】B-1/B-2 验收不可复现**：e2e 依赖模型自主执行 search→use 两轮模式，设计稿自承「ling 系对嵌套 schema 的解析非独立实测」，且未给出 hermetic harness（mock 模型/脚本化 tool_use）方案——「hermetic skip 策略标注」只说了 skip 没说怎么测。验收标准依赖非确定性模型行为 = 无法作为 merge gate。
3. **top-k 截断引发检索死循环无护栏**：目标工具被 top-k 截掉 → 模型 refine query 再搜 → 仍截断，无次数上限/降级策略；B-6 只覆盖「常驻缺失」场景的死循环，未覆盖「检索命中面」死循环。建议 C-6 族增「N 次未命中后 search_tool 返回全量名列表（仅名不含 schema）兜底」契约。
4. **Q2.3 盈亏模型缺「杀死判据」**：MVP 路径 defs 成本恒为零，imported 路径唯一收益是省一跳中转——按设计稿自己的公式，对低频工具几乎必亏。若 B-5/B-10 数据回填后证明 imported 路径全场景不盈利，Phase B-2 整条增强路径即死重；设计未声明该情形下的砍项裁决规则。
5. **MCP 会话中动态重注册时窗未覆盖**：`register_mcp_tools` 运行期可重注册（bridge 重建后），新出现的 MCP 工具在 search_tool 索引、resident/imported 快照上的可见时机未定义；O-2 只覆盖「server 收紧」方向，「新增」方向（解锁域中途扩大）无条款——且新工具若进 imported 段会违反 append-only 的「按解锁时序」语义（它从未被解锁）。
6. **flag 生命周期在 resume/fork 下未定义**：「会话启动一次性读取」未声明 resume 恢复的会话沿用原 flag 值还是新读；fork 子代理是否继承父 flag 也未提（Q2.4 fork 只谈 defs 快照）。
7. **C-2（Phase C）断言措辞不成立**：「触发到下一窗口间相邻轮请求内容不改」为假——每轮新 ToolResult 追加必然改变请求内容；应改为「对已有 items 无回溯性修改（strict prefix-growth）」，否则测试无法编写或恒假。
8. **重放提示依赖链未挂牌**：`[rerun with same args]` 的可行性依赖 assistant tool_use 的 raw_input 永不进入任何压缩层；Phase C 只声明不动 Reasoning/user/assistant，但 auto-compact 85% 重建后 args 是否可考未声明——重放提示可能在 compact 后悬空。
9. **B-5 基线比对无效面**：resident 按 client_name 字典序重排（三律 1）意味着 flag=true 首轮前缀与 flag=false 现状**必然不同**——「warm ratio ≥ 关闭态基线 −2pp」的基线若取自关闭态 warm 值，比对的是两种排序，冷启动污染无法归因。应声明基线采集方式为「flag=true 自身 cold→warm 曲线」。
10. **A-3 双路径 golden 比对的保鲜风险**：「flag=false 输出 ≡ 现状代码路径输出」要求仓库长期维护两条 defs 组装路径并保证字节一致——一旦上游改现状路径而 skeleton 路径未同步，A-3 假绿/假红；建议改为「同一代码路径 + flag 短路」单路径实现（设计稿未禁止，但 A-3 字面诱导双路径）。

## 三、终论

**需 v2（v3.1）后再作评审基线。必改项**：

1. B-12 补跨层数据流设计（投影状态→use_tool 判定点的具体机制 + 契约测试），否则 Phase B 不可实施。
2. B-1/B-2 改 hermetic 可复现验收（mock 模型或脚本化 tool_use 序列），e2e 仅作补充。
3. search_tool top-k 未命中兜底与循环上限契约。
4. C-2 断言改为 prefix-growth 语义；重放提示对 auto-compact 的依赖挂牌。
5. MCP 运行期重注册时窗 + flag 在 resume/fork 下的继承语义补条款。
6. Q2.3 增「imported 路径全场景不盈利则砍 B-2」的杀死判据。

其余发现（kind 一致性校验、B-5 基线口径、A-3 单路径建议、Opus-36 变体降严重级）可作可后补项。设计稿的根基（省钱/限权分离、两域标注、滞回先例复用、契约测试体系）经三视角核验**站得住**，v3 自审发现的四个 ❌ 均为真问题且修订方向正确——阻塞集中在「唯一执行面改动恰好缺执行层设计」这一处，属可修复范畴，不需要推翻分层架构。
