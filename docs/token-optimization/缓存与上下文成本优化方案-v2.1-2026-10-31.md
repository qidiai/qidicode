## 0. v1 → v2 的关键更正

| 项 | v1（kimi-for-coding） | v2（审计后） |
|---|---|---|
| 成本基线 | 全量输入按 `1.25×pi` 重发，系数 2.25 | **错误**。自动缓存通道（OpenAI 兼容）没有“写入费”，未命中就是普通输入价，基线系数 ≈ **1.0×pi**；`1.25×` 只适用于 Anthropic 显式缓存写入，而当前只有 1 个 `messages` 后端模型 |
| 省幅数字 | 省 86% / 92.7% | 方向不变，但绝对值全部重算；不再引用 v1 的百分数 |
| 压缩阈值 | 85% → 40% | 40% 在 1M 窗口是 400K，仍高于均值 216K，**单靠它不触发**；必须先开批量裁剪的水位，或同时改代码 |
| pruning 配置 | 直接改 `keep_last_n_turns` 等 | 这些键存在，但 per-turn 裁剪被 `PRUNE_WATERMARK_PERCENT=50` 硬门控；**必须同时开 `batched_pruning=true` + `low_watermark_percent<50`**，否则配置不生效 |
| “客户端不是原因” | 未区分 | 改为：**前缀稳定性不是原因**；客户端仍有缓存标记缺口（Anthropic 断点、Responses cache key） |
| “两条水位永不触发” | 绝对表述 | 改为“**常态不触发**”（relay 只有小时聚合，缺单请求尾部数据） |

**实测新事实（K31 修正后）**：

1. **不能声称"按 256 token 块量化"**。原始数据里 kimi 的命中量（256/512/1280/2560）是 256 的倍数，但 codely（640/1152/2432）是 128 的倍数、glm（320/704/1408/2752）是 64 的倍数——三条量化规律互不相同，撤回"全局 256 块"结论。可保留的最窄结论：所测条目在 349–415 prompt tokens 的最短档就出现非零命中，即"该形态下未见 1K 最小门槛"。若要识别量化参数，需每长度全新独立前缀、密集边界点、重复样本，并核对 relay 前后原始 usage。
2. **同 model 名不等价**：`codely-flash` 与 52duck 的 `deepseek-flash` 都指向 relay 的同名上游，但命中行为相反（一个命中、一个未报字段）——判定缓存能力必须按 config 条目测，不能按上游 model 名推断。
3. **DeepSeek 条目名勘误**：实测命中的是 `dimleap-deepseek-v4-1-flash-1017-222`（dimleap 池），本方案早期误写为魔搭中转条目 `deepseek-v4-1-flash-1017-ms-222`。后文 P1 示例按勘误条目。

## 2. 诊断（只基于上述事实；K31 修正后口径）

1. **成本/额度的大头是"每轮重发的上下文"，不是"缓存读"。** 输入:输出 261:1（≈0.38% 输出占比，**不是成本比**——成本还需输入/输出/缓存读单价，见 P4 注），平均每请求 216K；输出侧几乎没有优化空间。
2. **缓存基本没生效。** 主力通道 4 小时窗口 90M 输入只命中 2,201（该数与"上线前无缓存记录"叠加，是**窗口观测值**；因 §6 承认 relay 可能漏解析字段，此数不作"绝对真实不命中"断言，仅作下限参考）。能观测到命中的是 Kimi 与 dimleap 系条目。
3. **客户端前缀并非完全稳定**：Responses 后端有 wire 层不变量测试（`conversation.rs:8957-8974, 8995-9002`）与 chat-state 的请求级测试，但 **retained 层 per-turn 裁剪会直接改写并持久化存储会话**（`mutations.rs:170-183, 224-239, 280-303`），且 chat_completions 的 turn-to-turn wire 回归尚未建立（P2 已列）。正确口径："已有部分稳定性设计与测试，尚未排除所有客户端改写源"。
4. **两条水位线对 1M 窗口形同虚设**：API-copy 的 50%（524K）与 85%（891K）都高于常态请求规模；但 retained 层 per-turn 硬清**不受 50% 门控**，会按 `hard_clear_age_turns` 直接改旧工具结果——所以"上下文随会话增长一路重发"需区分：**API-copy 前缀确实重发，而 retained 存储层在年龄到点时已改写**。
5. 因此优先级（K31 修正后）：**先补单请求计量与缓存字段原始状态（P3/D1），再对隔离 1M profile 做 P1 灰度，P2 仅在 messages/responses 有实测流量且有上游支持时启动**；不做路由切换（用户裁定）。

## 3. 优化方案（按 ROI 排序）

### P0 路由：把长上下文流量切到“实测能命中”的通道

> **K31 审计 2026-11-01 + 用户同日裁定**：不做模型切换，保持现有真实工作流。本条 P0 作为“路由切换”动作**冻结**，仅保留 §1.4 诊断资产；下方“动作/验收”改为最小可行集。

- **保留为诊断**：按 §1.4 的实测观察表记录各通道现状；D2 数据仍作基线。
- **不做**：模型切换、路由灰度、“≥50% 长任务走缓存通道”这类与用户裁定冲突的验收指标。
- **最小可行集（K31 建议）**：
  1. 现有工作流计量：按真实使用的 config 条目与 backend 记录单请求 prompt/cached tokens、字段缺席、输入分位数、压缩/裁剪事件；每个结论带 n 与时间窗；补上 chat_completions wire 前缀回归与 relay/上游 usage 对照，先区分客户端、relay 与上游三层原因。
  2. 安全的上下文灰度（P1）：只有在隔离 1M profile 可保证不影响小窗口时才试；不能隔离则等按模型配置上线。
  3. 条件性 P2：仅当 messages/responses 在现有流量中占有可测份额，且对应上游原生探针证明支持时实施；否则只保留代码缺口记录，不排 7 天开发。

### P1 上下文预算：两级水位（客户端配置，仅在隔离 1M profile 下灰度）

**为什么 v1 的"40% 压缩"不够**：1M × 40% = 400K，仍高于均值 216K，阈值不触发；API-copy 层的 per-turn 裁剪被 `PRUNE_WATERMARK_PERCENT=50` 硬门控，但 **retained 层的 per-turn 硬清没有 50% 门控**——`mutations.rs` 的 `prune_retained_conversation` 在每个用户消息后直接按 `hard_clear_age_turns` 改存储并持久化。必须用批量裁剪的低水位提前介入。

**2026-11-01 代码核对修正（K31 复核后）**：

- `[compaction.pruning].low_watermark_percent` 是**全局单一值**，没有按模型覆盖的入口（`cf-config/src/types.rs:2476-2507`；装配点 `cf-shell/src/session/acp_session_impl/spawn.rs:444`；`ConfigModelOverride` 无 pruning 字段）；能按模型覆盖的只有 `auto_compact_threshold_percent`。
- pruning 挂在 `[memory].enabled` 下，memory 关掉时 pruning 整体失效（`spawn.rs:444-450` 对 None 强制 `enabled=false`）。
- **低水位不是"到 15% 必清"**：批量路径要求 `prompt_index ≥ hard_clear_age_turns`（本例 10）先过年龄门槛；触发区间是 `[low, 50%)`；从 <low 直接跳到 >50% 时保留态批量路径不触发，由 API-copy 的 `should_prune` 接管；清理成功后利用率需降到 `low-5`（本例 10%）以下才重新武装。
- **分档表算术错已更正**：全局 `low=15` 在 1M / 400K / 256K / 200K 窗口下对应 token 数分别为 157K / 60K / 38.4K / 30K（都是 15% 百分比，不是各自窗口的百分比）。

```toml
[session]
# 全局默认不要动；按模型覆盖更安全（见下）
# auto_compact_threshold_percent = 85

[memory]
enabled = true            # pruning 的前置开关：此为 false 时 pruning 全失效

[compaction.pruning]
enabled = true
batched_pruning = true          # 关键：开启低水位批量裁剪
low_watermark_percent = 15      # 全局值；各窗口 token 数按"百分比×该窗口"换算（见上）
keep_last_n_turns = 3
soft_trim_threshold = 4000
soft_trim_head = 1500
soft_trim_tail = 1500
hard_clear_age_turns = 10

[model.dimleap-deepseek-v4-1-flash-1017-222]   # K31 勘误后的条目名
auto_compact_threshold_percent = 38   # 1M ≈ 400K 才真正压缩历史
```

**灰度可执行条件（K31 强调）**：全局低水位一旦开启，同一台机器上**所有窗口**同步生效；200K 会话会在 30K 触发裁剪。要"只对 1M 灰度"必须满足以下之一：

1. 用隔离 config profile 或独立进程跑 P1，且该 profile 只装载 1M 窗口模型；或
2. 先做按模型门控的代码改动（`ConfigModelOverride` 加 pruning 字段），再按条目灰度。

**验收要覆盖的不触发分支（K31 建议）**：`prompt_index < 10` 的年龄门槛期、`[15%, 50%)` 区间、跨 50% 由 API-copy 接管的场景、`total_tokens` 主要由近期大工具结果构成而无 eligible 对象的情形、滞回重武装线（利用率需降到 <10% 才再次可清）。

**副作用**：批量裁剪会把旧工具结果替换成占位符（保留 `full output at:` 指针，可回读）；压缩会丢早期细节。两者都应在单项目灰度，观察质量指标。

**前置条件**：确认每个模型 `context_window` 的真实值——如果上游实际只有 256K，而配置写 1M，所有百分比都失真。

### P2 客户端缓存标记（代码改动，条件性，ROI 未量化）

**代码缺口属实（K31 复核）**：

- Anthropic：生产赋值仅 1 处 `cache_control=Some`，在 `cf-sampling-types/src/conversation.rs:3191-3195`（最后一个 system block）；其余构造均为 `None`。
- Responses：`prompt_cache_key` 全仓 10 个构造点均为 `None`；**生产请求构造点是 `cf-sampling-types/src/conversation.rs:2134-2149`**（本方案早期误引为 `cf-sampler/src/stream/responses.rs:549`——那里是 `#[cfg(test)]` 的响应夹具，非生产路径）。

**收益前提（K31 列出，全部未验证）**：

1. messages / responses 后端实际承载足够长上下文流量（1 个 messages + 2 个 responses 是本机配置条目数，**不是流量占比**）；
2. 上游原生支持对应缓存机制；
3. relay 原样透传断点/key 并可靠回报 cache usage；
4. 请求前缀稳定、稳定会话 ID 对 Responses 路由有实际增益；
5. 命中收益覆盖 Anthropic 显式缓存的写入成本与代码维护成本。

**当前状态**：D2 全部打在 `/chat/completions`，不覆盖 messages / responses。P2 从"确定的高 ROI 代码工作"降级为**有流量与支持度门槛后的候选任务**：

- 门槛 1：先按 backend 统计真实输入 token / 请求量，证明 messages / responses 非零流量；
- 门槛 2：对有流量的条目做原生小探针，证明上游支持；
- 通过两项后再排 D5/D6 开发。

**测试**：给 `chat_completions` 补 turn-to-turn 前缀稳定性回归（目前 wire 层不变量测试只覆盖 Responses 后端：`cf-sampling-types/src/conversation.rs:8957-8974, 8995-9002`）。

### P3 计量与看板（必须先于调参）

- relay 侧增加**单请求** `prompt_tokens` 的 p50/p90/p99/max（当前只有小时聚合），用于验证 15%/38% 两条线的触发频率；同时**保留缓存字段原始状态**（命中 / 显式 0 / 未报字段），不合成归零。
- 看板字段：按通道/模型的单请求输入、日输入、压缩次数、裁剪次数、字段缺席率。
