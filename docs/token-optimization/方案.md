## 1. 背景

qidicode 是 agent 模式的 CLI：每轮把「系统提示词 + 工具定义 + 全部历史 + 用户输入」发给模型，模型可能再调工具形成多轮循环。token 消耗由两部分构成：

- **固定开销**：每轮重复发送的系统提示词与工具定义（工具定义随请求全量发送；实例数为量级估计，无代码级计数——可用 `/context` 的 `tool_definitions_count` 实测）
- **可变开销**：历史上下文（随轮次增长）、agent 循环次数、compaction 自身的摘要调用

## 4. 成本结构分析

- **省的是浪费**：noise 标签重复注入、未用工具定义、过期历史摘要化
- **省不掉的是 agent 模式本身**：每轮固定开销 × 循环轮数是结构性的
- **compaction 是双刃剑**：压缩消耗 1–2 次采样调用（two-pass prefire：pass-1 摘要 ~95% prefix、pass-2 重写 NOTE₁+5% 尾部），输入受 `fit_conversation_to_budget` 裁剪与 300s wall-clock 预算约束
- **子代理隔离有收益也有成本**：每个子代理自带一份系统提示词+工具定义（双份固定开销），小任务派发反而更贵
- **七成看用法、三成靠系统兜底**：工具过滤、任务分解、effort 选择由用户控制（经验判断，无代码级数据支撑）

## 5. 问题与权衡

1. **bytes/4 对中文高估**：中文 UTF-8 3 字节/字 → 估算 0.75 token/字，实际中文约 0.5–0.6 token/字（依赖具体 tokenizer，仓内无 BPE 可对照，幅度为经验值）。**但影响被架构限制**：压缩判定用 `get_estimated_total_tokens()` = `total_tokens`（wire 实测基数，每轮响应后被 `record_response_token_usage` 覆盖）+ `estimated_tokens_since_model`（bytes/4 估算增量）。因此估算误差**只作用于「上次响应以来的工具结果增量」**，稳态长会话下 85% 触发点约在 80–84%（视增量占比），**不是全量 30–50% 偏差**。全量偏差仅在纯估算区制成立：会话起始播种、rewind 后 reseed、压缩后 reseed、不回 usage 的 provider。
2. **每轮固定开销**：工具定义每轮全量发送（实例数待实测）。
3. **估算与实测的缝隙**：本地估算只在 wire Usage 返回前「冻结」占位；增量估算误差直接传导为压缩时机误差（增量部分）。

## 6. 质量门控原则（前置评审条件）★

**省 token 以不伤任务质量为前提**。任何省 token 改动过审前必须回答：它省的是浪费还是信息？

### 三分法

| 类别 | 内容 | 处置 |
|---|---|---|
| ✅ 安全省（纯浪费） | 未使用的工具定义与 MCP 服务器；fork 时剥离的 noise 标签；`MAX_VERBATIM_TURNS=3` 之前的早期历史 | 优先做 |
| ⚠️ 有风险省（须门控） | auto-compact 触发时机；工具输出截断；effort 降档；web_fetch 抓取预算 | 每项配质量门控（见下） |
| 🚫 禁区（绝对不能省） | 系统提示词（行为约束与安全边界）；用户当前任务完整描述；最近的工具结果原文 | 任何改动不得触碰 |

### 门控清单

1. **压缩保护清单**：现状已有保护——`build_compacted_history`（`session/compaction.rs:848-849`）压缩后继历史 verbatim 含 `last_user_query`；`CompactionStateContext.recent_messages` 保留最近一轮结构，但**工具结果内容被替换为占位符**（`cf-chat-state/src/compaction_utils.rs:437-461` `extract_messages_since_last_real_user`）。真正缺口仅「最近 N 轮工具结果**内容**」。落点：`compaction_utils.rs` + `session/compaction.rs` 编排；改动须保持 `sanitize_compacted_history` 的 ToolResult 配对不变量（`compaction_utils.rs:879-918`）
2. **截断首尾保留**：**不新造机制**——复用既有 `truncate_front_and_back`/`truncate_middle`（`truncate.rs:229-305`）接入字节截断调用点（现 `truncate_str` 仅留头部），比例 50/50→60/40 可调
3. **effort 不自动降档**：现状无任何自动 effort 变更机制（laziness_classifier 仅注入 nudge，不动 effort）。若要做自适应 effort，需**新建**复杂度分类器（laziness_classifier 是停滞检测器，职责不同），且仅分类器确定简单时降档，不确定维持默认
4. **估算偏保守方向**：宁可高估（早压缩）不可低估（溢出）——与 preflight overflow 兜底一致；但高估的代价是质量损失，精度是根本解（见 §7 P0-1）

## 7. 优化方向（按优先级）

### P0（精度/开销收益最大）

| # | 方向 | 落点 | 预期收益 |
|---|---|---|---|
| P0-1 | 真 BPE tokenizer 接入**真实判定链** | `cf-token-estimation::estimate_tokens` + `cf-chat-state/src/actor/state.rs` 的 `estimate_item_tokens`/`estimate_conversation_tokens`（auto-compact 与预检溢出的直接调用链） | 中文估算误差 ~40% → <5%（增量部分）；压缩判定更准 |
| P0-2 | 工具定义按需加载/裁剪 | 工具定义入口 `prepare_tool_definitions_inner`（`sampler_turn.rs:147-151`）+ 过滤 `turn_base_tool_specs`（`:138-145`）；`--tools`/`--disallowed-tools` 为 headless-only CLI 过滤 | 直接砍每轮固定开销大头；「每轮动态」裁剪需新增管线 |

> **⚠️ 落点勘误（审计 F1）**：`crates/codegen/cf-chat-state/src/actor/state.rs:96-104` 的 `EstimatedItemTokenCounter` 实现的是 `cf_compaction::ItemTokenCounter` seam（trait 定义于 `crates/common/cf-compaction/src/token.rs:21-24`，注释留口 "Where another host plugs a real BPE tokenizer into the same seam"），但该 seam 的消费者是 `apply_intra_compaction`（`crates/common/cf-compaction/src/intra_compaction/compact.rs:79`）——**cf-shell 生产压缩路径不引用 intra_compaction**（全仓 grep 零匹配），auto-compact/预检溢出走 `exceeds_threshold` 直连路径。把 BPE 塞进该 seam 对压缩判定**零收益**；它是留给未来宿主的潜伏 seam。

### P1（成本治理）

| # | 方向 | 说明 |
|---|---|---|
| P1-1 | 子代理派发成本预估门控 | 派发入口 `TaskTool::run`（`cf-tools/.../qidi_build/task/mod.rs:111-120`）→ `SubagentBackendResource`；派发前无现成成本估算挂点，需新增：估算（系统提示词+工具定义+预计轮数）vs 原地执行，超支则拒绝派发 |
| P1-2 | 动态 compaction 阈值 | 在既有 6 级**静态**解析（env/按模型/全局）之上增加动态自适应（按剩余窗口与任务阶段），不是从「单一 85%」起步 |
| P1-3 | 自适应 reasoning effort | 需新建复杂度分类器（见 §6 门控 3）；按任务复杂度分级 |

### P2（可观测性）

| # | 方向 | 说明 |
|---|---|---|
| P2-1 | OTel metrics 默认开启 | 当前双开关 opt-in；组织级 token 成本治理 |
| P2-2 | per-turn token 预算与超支告警 | `ContextInfo` 为 serde 结构体，消费方 `/context` → `Action::ShowContextInfo`；加预算字段工程可行 |
| P2-3 | web_fetch 预算动态化 | 固定 `WEB_FETCH_CONTEXT_PERCENT=0.03` → 按剩余窗口调整 |

**优先级逻辑**：P0 两项改动小、收益面广（估算精度影响增量判定与展示）；P1 依赖 P0 的精确估算；P2 可独立推进。**阈值调高（如 85→90）只是临时止血，不算优化**——它掩盖估算不准的问题。

## 8. 使用建议（用户侧）

- 中文密集场景：关注 `/context` 的 usage_pct 当「上限参考」而非精确值
- headless 批处理用 `--tools` 过滤到当前任务子集（**headless-only**：TUI 下会告警并忽略）；MCP 服务器按需启停
- 小任务不派子代理（双份固定开销）；探索/多文件并行任务才值得
- 长任务主动 `/compact` 控制时机，优于被动 85% 触发
- 机械任务 `/effort low`，探索任务再 high
- headless 批处理用 JSON 输出对账（`input_tokens` 仅未缓存部分）
