## 0. 一句话

**relay 的 `requests` 台账已有"每请求一行"，但每行缺缓存三态与会话维度。** 本方案不改聚合口径、不改路由、不动缓存策略，只在既有的 SQLite 台账 `requests` 表上**加 7 列**（5 个缓存/来源 + 2 个会话），让"单请求输入分位数 / 缓存命中率 / 字段缺席率 / 按会话累计曲线"第一次可以按天、按通道、按会话查询。

> 口径（K3.1 A3 修正）：这里说的"每请求"= **既有 `requests` 台账的成功/合成行**。
> 失败走 `errors` 表，不产生 usage 的调用不落 `requests`——本方案不新增记账点，只给既有 7 处调用点补 7 字段。
> **新增列总数：7**（`cache_read_tokens`、`cache_write_tokens`、`cache_field_present`、`prompt_tokens_estimated`、`model_resolved`、`session_key`、`session_epoch`）。

## 1. 为什么必须做（三条实测 + 一条使用模式，均可复现）

### 1.1 现有台账"按设计"就没有缓存字段

`proxy_core/db.py` 的 `_SCHEMA` 只有 16 列，`record_request()` 的**显式业务形参只有 14 个**（`id`/`ts` 由 DB 生成，不在形参里）：

```
id, ts, user_id, api_key_label, model_requested, model_served, status_code,
prompt_tokens, completion_tokens, total_tokens, duration_ms,
has_media, is_stream, effort, error_detail, reroute_note
```

其中**没有任何 cache_* 列**。实测（2026-11-01，服务器）：

```python
HAS_CACHE_COL: NONE
```

内存侧 `proxy_core/stats.py` 是有的——`_cache_read_tokens()`（第 24 行起）已兼容
`prompt_tokens_details.cached_tokens` / `cache_read_input_tokens` / `prompt_cache_hit_tokens` / `cached_tokens`
四路字段，`_cache_write_tokens()` 兼容 `cache_creation_input_tokens` 与 `cache_write_tokens`。
但这两个函数**只在 `TokenStats.record()` / `record_key()` 里被调用**，写进 `token_stats.json` 的进程内累计；
`routes/proxy.py:1122` 附近的 `kdb.record_request(...)` 只传 prompt/completion/total —— **缓存值在落库那一步被丢掉**。

后果：`relay_knowledge.db` 里 138,900 条历史请求**一条缓存数都没有**，任何按时间窗、按会话、按通道的回溯都不可能做。
v2.1 §1.1「90M 输入只命中 2,201」之所以无从复核，也是这个原因。

### 1.3 长请求是"多数"，但小时分布不可外推

**窗口：2026-11-01 00:08:11 – 08:44:08（n=1250，prompt 合计 210,397,574）**

- `prompt_tokens > 150K` 的请求 **753 条 / 1250 = 60.2%**——长请求是多数，不是少数。
- 按小时看 `>150K` 条数：00 时 19、01 时 155、02 时 85、03 时 116、04 时 129、05 时 92、06 时 49、07 时 **14**、08 时 94。
  有波动（07 时低点、01 时高峰），但**样本只覆盖 8 个小时、且是凌晨到上午**。

**因此本节只支撑一个结论**：长请求占比高（60%），所以任何按"平均值"设的阈值都会失真。
**不外推的**：不能说"长请求集中在某几个时段"——本数据没有 09:00 之后与夜间的覆盖，
在补齐 24 小时样本前，小时级"脉冲"只是**待验证假设**（K3.1 F19）。

### 1.4 使用模式：会话（而非自然日）才是统计单元

用户告知（2026-11-01）：**一个项目从头到尾开 2–3 个 qidicode 会话**，每个会话在该项目里持续积攒上下文；
需要时**随时 resume** 几天甚至几周前已加载的旧会话，把其完整 prompt 继续带入新一天。

数据侧可复核的事实（`relay_knowledge.db`，**已按 K3.1 F1 重算，原始窗口/排序键见附录 A**）：

- **同一 user_id 可跨日**：`主key` 10-31 末次 23:59:48（id=137928，`amd/DeepSeek-V4.1-Flash`，prompt **88,997**）；11-01 首次 00:08:11（id=137957，同模型，prompt **90,294**）。间隔 543 秒，**prompt 从 88,997 续到 90,294**（+1,297）。
  *这是同一 client key label 的流量跨日，不是"同一 qidicode 会话"的跨日——*session 归属*需要本方案落地后靠 `x-grok-session-id` 头验证，当前台账没有 session 维度列，无法直接证明 resume*。
- **`39640` 10-31 一天相邻 prompt 跳增 >50K**：`ts,id` 排序、`(user_id, model)` 分开统计，共 **33 次**，最大一次 **+509,348**。K3.1 三审独立重算：33 次相邻间隔**最大 3,986s（≈1h06m），全部 < 24h**——本样本里"大跳增"完全发生在短时窗内，**不能用来证明任何跨天长停顿，更不能证明 resume**。
- **`requests` 表当前无任何 session 维度列**（16 列清单见 §1.1）——`user_id` 是"客户端 key label"，不是"项目会话"，跨 2–3 个项目会共用同一个 label。
- **qidicode 请求头与 relay 读取的头名不匹配**（K3.1 F2 新增）：
  - 客户端侧：`crates/codegen/cf-sampler/src/client.rs:98` 发的是 **`x-grok-session-id`**；
  - relay 侧：`proxy_core/affinity.py:125-165` 的 `session_key()` 读的是 **`X-Session-Id`**（首级）与 `chat["user"]`；
  - 后果：qidicode 流量到 relay 后，`user` 字段为空（`crates/codegen/cf-sampling-types/src/conversation.rs:2078-2090` 在线构造不填 user），`X-Session-Id` 也不存在，**会退化到第 3 级"首条 user 消息前 512B sha256[:16]"**。两个不同 qidicode 会话若首条用户消息相同（同一项目同一模板）会被合并成一个 key——与本节"一个项目 2–3 个会话"的统计目标直接冲突。
  - 另有独立开关：`routes/proxy.py:1481-1494` 的 `_feature_affinity()` 为假时，主池根本不算 `session_key`，本方案 `session_key` 列会跟着变 NULL——观测与粘性选号是两件事，不能共用同一开关。
  - **头覆盖边界（K3.1 特别盯点 1，须写死）**：qidicode 的 `x-grok-session-id` **并非只在交互主会话发**——交互主 turn、ACP headless、原生子代理**三类都发**（共享 `turn.rs:1881-1884` 的同一 `SessionCommand::Prompt` 路径），后台辅助调用（recap / compaction / memory dream）也会带上所属或父 session ID。因此**这三类请求经新 `ledger_skey` 都不会退化到消息哈希**；只有**没带有效头的外部客户端或未填该字段的调用**才走 fallback（首条消息哈希 / key label），并在响应里标 `"heuristic": true`。sampler 对空 session_id 用 `unwrap_or_default()`（`client.rs:954-968`），**`ledger_skey` 必须把空/空白头当缺席**，否则无 ID 调用会全并进同一个空 key。

**对统计口径的后果**（本节是本方案的立论基础，不属开放问题）：

1. **不能按自然日切分**：同一 session_key 的 `ts` 可跨 3–30 天，按天切等于把一条曲线剪成 N 段，p50/p90/p99 全部失真；
2. **分位必须按 `session_key` 累计曲线取**：即"该会话从第 1 轮到第 N 轮的 prompt_tokens 序列"，n = 该会话的总轮数；
3. **缓存命中率的正确分母** = **该会话累计 prompt**，不是"当日 prompt"；
4. **v2.1 P1 的低水位判定**也必须按会话累计利用率触发，否则加载旧大上下文的会话会在"当天只有 5 条请求"的低水位假象下漏触发。

**本方案落地方式**：

1. 在 `requests` 表新增 2 列 `session_key TEXT`、`session_epoch INTEGER`（见 §2.1）；
2. **在 `relay` 侧新增 `ledger_skey()` 独立于粘性开关**：读取顺序为 `X-Grok-Session-Id`（qidicode 实际发送的头，见 §1.4 事实 4）→ `X-Session-Id`（既有兼容）→ 首条 user 消息哈希 → key label；**不受 `_feature_affinity()` 开关影响**；
3. **在 `relay` 侧新增 `next_epoch()`**：以同一 `session_key` 的上次落盘 ts 为基准，`ts_now − ts_prev > _EPOCH_GAP_S` 则 epoch +1；`_EPOCH_GAP_S` 缺省 **48h**（172,800s，用户 2026-11-02 拍板），**不得称作精确 resume 次数**；
4. 端点 `by=session` 时**禁用日期桶**（§2.4），分位按 session 累计取；
5. 验收补 V10/V11（§4）：V10 证明跨日同 session 不被切断，V11 证明 epoch 恰好 48h 边界与"上一 epoch 尚未 flush 又跨第二个 48h"两个用例；
6. **`x-grok-session-id` 头透传**：本方案不修改 qidicode 客户端，也不在 relay 改 `X-Session-Id` 兼容读法；只在 `ledger_skey()` 里**新增读取 `X-Grok-Session-Id` 头**作为第一优先，加一条验收：两个不同 session id + 完全相同首条 user 消息必须得到不同 key。

## 2. 设计（只加列，不改语义）

### 2.1 表结构

在 `_SCHEMA` 的 `CREATE TABLE requests` 中追加 7 列。**全部不带 `DEFAULT`**：

```sql
cache_read_tokens      INTEGER,  -- NULL=未知 / 0=明确未命中 / >0=命中
cache_write_tokens     INTEGER,  -- NULL=未知 / 0=明确无写 / >0=写入
cache_field_present    INTEGER,  -- NULL=历史行 / 1=有缓存键在场 / 0=全部缺席
prompt_tokens_estimated INTEGER,  -- NULL=未补 / 0=usage 实测 / 1=估算器补的
model_resolved         TEXT,     -- NULL=主池或 delegate / 外部池 provider 名
session_key            TEXT,     -- NULL=未能识别 / ledger_skey() 值（§2.5B，非 affinity.session_key）
session_epoch          INTEGER   -- 0-based 计数：该 session_key 距上次 >48h 再次出现则 +1，窗口内保持（"长停顿分段"，非 resume 次数）
```

索引**单独一支 DDL，不与 CREATE TABLE 同批执行**（见 §2.2 B1 修正 1）：

```sql
CREATE INDEX IF NOT EXISTS idx_req_cache   ON requests(cache_field_present, cache_read_tokens);
CREATE INDEX IF NOT EXISTS idx_req_model_ts ON requests(model_requested, ts);
CREATE INDEX IF NOT EXISTS idx_req_session ON requests(session_key, ts);
```

> `idx_req_session` 支撑"按 session_key 取累计 prompt 曲线"的端点查询（§1.4 的后果 2），
> 也是 `session_epoch` 增量算法在写入路径取"该 key 上一次的 ts"的加速索引。

**为什么必须三态而不是两态**（K3.1 B2）：

- `cache_read_tokens=0` 有两种事实：上游明确报"0 命中"，与上游根本没报这个键；
- 若统一用 `DEFAULT 0`，第二种会被写死成第一种——v2.1 §1.4 里 Qwen / 52duck 的误判就是这么来的。

所以：**列可空 + 新行显式写值**。`read` 由 read 键是否在场决定 NULL/0，`write` 由 write 键是否在场决定，
`cache_field_present` 仅是两路在场集合的并集标记，**不能决定另一字段是否未知**（K3.1 F4：分字段三态）。

**注意 `cache_field_present` 必须与 `cache_read_tokens` 分开**：`cache_read=0` 有两种含义——
上游确实没命中、上游根本没报这个字段。v2.1 §1.4 里 Qwen / 52duck / agnes 的"0 命中"就是被这个混淆坑的（K3.1 二审驳回点之一）。
本方案把**两者变成两个独立列**，从数据层根治。

### 2.2 迁移

**B1 修正 1：DDL 分批——老库必须先迁移列，再建索引。**

原稿把新索引写进 `_SCHEMA` 一起 `executescript`。老库上这会先执行
`CREATE INDEX ... (cache_field_present, ...)`，而此时新列还不存在——实测报
`OperationalError: no such column`，**启动即失败**，后面的列迁移根本轮不到执行。正确顺序：

```
第 1 批  _SCHEMA           只含 CREATE TABLE（全部 IF NOT EXISTS，幂等）
第 2 批  _migrate_columns  ALTER TABLE requests ADD COLUMN × 7
第 3 批  _SCHEMA_INDEXES   旧索引 + 新索引（全部 IF NOT EXISTS）← 此时新列必已存在
第 4 批  _verify_schema    PRAGMA 核对 + 试写一行 + 回读
```

**B1 修正 2：历史行必须是 NULL，不能是 DEFAULT 0。**

实测（`/tmp` 临时库，sqlite 3.45.1）：`ALTER TABLE t ADD COLUMN c INTEGER DEFAULT 0` 之后，
**已有行的 `c` 返回 `0`，不是 NULL**；只有省略 `DEFAULT` 子句，已有行才返回 `NULL`。
原稿写"DEFAULT 0 仅为新行兜底、历史行留 NULL"——SQLite 不支持这种语义，**V2 验收必然失败**。
本稿 7 列全部省略 `DEFAULT`，新行由 `record_request` 显式写值。

**B1 修正 3：跨进程并发。**

`_get_conn()` 由多 worker 调用，两个进程可能同时进迁移。对策：

```python
_COL_MIGRATIONS = [
    ("cache_read_tokens",       "INTEGER"),
    ("cache_write_tokens",      "INTEGER"),
    ("cache_field_present",     "INTEGER"),
    ("prompt_tokens_estimated", "INTEGER"),
    ("model_resolved",          "TEXT"),
    ("session_key",             "TEXT"),     # 新增（§1.4）
    ("session_epoch",           "INTEGER"),  # 新增（§1.4）
]

def _migrate_columns(conn, retries=20):
    """串行化跨进程迁移：BEGIN IMMEDIATE 抢写锁 → 锁内二次 PRAGMA → 逐列 ALTER。

    返回新增列数（0 = 已是新 schema）。任何非幂等错误向上抛，
    由调用方决定 readiness（不静默跳列）。
    """
    added = 0
    conn.execute("BEGIN IMMEDIATE")
    try:
        existing = {r[1] for r in conn.execute("PRAGMA table_info(requests)")}
        for col, decl in _COL_MIGRATIONS:
            if col in existing:
                continue
            conn.execute("ALTER TABLE requests ADD COLUMN %s %s" % (col, decl))
            added += 1
        conn.commit()
    except sqlite3.OperationalError as e:
        conn.rollback()
        msg = str(e).lower()
        if ("locked" in msg or "busy" in msg) and retries > 0:
            time.sleep(0.2)
            return _migrate_columns(conn, retries - 1)
        if "duplicate column name" in msg:
            # 另一进程在 PRAGMA 与 ALTER 之间抢先：重查一次即可（幂等）
            conn.commit()
            return _migrate_columns(conn, 0)
        raise
    if added:
        log.info("[知识库] 迁移：requests 增加 %d 列", added)
    return added
```

要点：

- **锁内二次 PRAGMA**：`BEGIN IMMEDIATE` 拿到写锁后再读表结构，消除"先读后写"的 TOCTOU；
- **`database is locked` 有界重试**：双 worker 首启时这是**预期错误**，原稿只吞 `duplicate column name`，不够；
- **其它错误一律上抛**：迁移失败必须让 readiness 明确失败，不得"跳过继续写新列"——那会让新行写进不存在的列。

**B1 修正 4：迁移后核验（全有或全无）。**

```python
REQUIRED = {c for c, _ in _COL_MIGRATIONS}

def _verify_schema(conn):
    cols = {r[1] for r in conn.execute("PRAGMA table_info(requests)")}
    have = REQUIRED & cols
    missing = REQUIRED - cols
    if have and missing:
        raise RuntimeError("requests 半迁移 schema：have=%s missing=%s"
                           % (sorted(have), sorted(missing)))
    return not missing
```

**历史行回填：不做。** 旧行的 `cache_*` 三列就是 `NULL`，语义为"记录时无缓存字段"。
查询侧用 `WHERE cache_field_present IS NOT NULL` 区分新旧；不带此条件的统计必须显式标注"含未知行"。

### 2.3 写入路径

`record_request()` 增加 7 个关键字参数，全部**默认 `None`**（不破坏现有 7 处调用点，R-001）：

```python
def record_request(self, user_id="", api_key_label="", model_requested="",
                   model_served="", status_code=0, prompt_tokens=0,
                   completion_tokens=0, total_tokens=0, duration_ms=0,
                   has_media=False, is_stream=False, effort="",
                   error_detail="", reroute_note="",
                   # 新增（B2：None = 未知，0 = 明确为零）
                   cache_read_tokens=None, cache_write_tokens=None,
                   cache_field_present=None, prompt_tokens_estimated=None,
                   model_resolved=None,
                   # 新增（§1.4：会话维度）
                   session_key=None, session_epoch=None):
    ...   # 函数体：写 self._buffer.append({...})，见下方"写入链三处"
```

`None` = 未知（历史行/异常路径），`0` = 明确已知为零。这个区分是 §2.1 里 Qwen 案的直接教训。

**B2 修正：写入链三处必须同时改。** 只加形参会静默丢值（K3.1 明列）：

| # | 位置 | 漏改后果 |
|---|---|---|
| 1 | `record_request` 内 `self._buffer.append({...})` 的 **14 个业务键**（`id`/`ts` 由 DB 生成，不在 buffer） | **加 7 个键**；漏则 `executemany` 报 `missing key` 或整批失败 |
| 2 | `flush()` 的 `INSERT INTO requests (user_id, api_key_label, ...)` 列清单 | **补 7 列**；漏则值丢弃 |
| 3 | 同语句的 `VALUES (:user_id, :api_key_label, ...)` 占位 | **补 7 个 `:` 参数** |

三处任一漏写，表现为「列存在但永远 NULL」——比缺列更隐蔽，V2 会假绿。必须同步改、同一提交。

**B2 修正：三态提取的单一实现放 `stats.py`。** 逐键判定 `present`，
**禁止** `bool(usage["prompt_tokens_details"])`——`{"audio_tokens": 0}` 会让它误报在场：

```python
# stats.py —— 唯一判定源（R-007）
_READ_TOP  = ("cache_read_input_tokens", "prompt_cache_hit_tokens", "cached_tokens")
_WRITE_TOP = ("cache_creation_input_tokens", "cache_write_tokens")
_DETAILS_READ  = "cached_tokens"        # 仅 prompt_tokens_details.<k>
_DETAILS_WRITE = "cache_write_tokens"


def _to_int(v):
    """与旧 helper 完全同口径（K3.1 F4）：拒 bool、拒负数、
    可 int() 的数字字符串必须转换成功；转换失败 / 非数字类型 → None（缺席）。
    这样 `{"cached_tokens": "123"}` 返回 123，而不是 None。"""
    if isinstance(v, bool):
        return None
    if isinstance(v, (int, float)):
        return int(v) if v >= 0 else None
    if isinstance(v, str):
        try:
            n = int(v.strip())
        except (ValueError, AttributeError):
            return None
        return n if n >= 0 else None
    return None

def _pick(usage, keys, details_key):
    """多路表达取 max；**全都缺席返回 None（不是 0）**。
    数字字符串按 _to_int 规则处理，与旧 helper 行为一致。"""
    seen = []
    for k in keys:
        n = _to_int(usage.get(k))
        if n is not None:
            seen.append(n)
    details = usage.get("prompt_tokens_details")
    if details_key and isinstance(details, dict):
        n = _to_int(details.get(details_key))
        if n is not None:
            seen.append(n)
    return max(seen) if seen else None


def cache_fields(usage):
    """(read, write, present)。present = 任一**已识别缓存键**在场。"""
    if not isinstance(usage, dict):
        return None, None, None
    read = _pick(usage, _READ_TOP, _DETAILS_READ)
    write = _pick(usage, _WRITE_TOP, _DETAILS_WRITE)
    present = 1 if (read is not None or write is not None) else 0
    return read, write, present
```

**为什么不在这算 `session_epoch`**（K3.1 F3）：`record_request` 只追加 `self._buffer`，
满 50 条才 flush。若在此读 `requests` 表算 epoch，**看不到本批 buffer 里已发生的行**，
连续两个 48h 长间隔会少计。因此：

- `record_request` 只 buffer 原始请求（含 `session_key` 与请求 ts），**不写 session_epoch 列**；
- `flush()` 的写事务在 `INSERT` 前按 buffer 顺序逐行算 `next_epoch`，本批内前行对后行可见；
- **禁止** routes 调 `kdb._get_conn()`（私有接口）。

`prompt_tokens_estimated` 的语义是**看 prompt 值的来源**，不是看 usage 是否为空：
`usage` 里有 `prompt_tokens` → `0`；由估算器填入 → `1`；不可知 → `None`。
原稿 `int(bool(usage_captured and not usage_captured.get("prompt_tokens")))` 在 `usage=None` 时返回 `0`，**错**（K3.1 F7）。

**B3 修正：不是所有路径都能走到这两个记账点。**
`minicode`（`:2681` 附近）与 `opencode`（`:2844` 附近）走各自的适配层，缓存字段若在适配层已被丢弃，
记账点再努力也拿不到。交付必须包含：适配层保留实际上游返回的 cache 键 + 各加一个带缓存键的转换测试。
`opencode` 的桥 tokens 若本就没有 cache 形态，**明确标未知，不得编造字段**。
delegate 合成行无上游 usage，写 `(None, None, 0)` 并由聚合层排除。

### 2.4 查询接口（kdb.query 加只读参数绑定）

现有 `kdb.query(sql, max_rows=5000)` **不接受参数绑定**，只能拼字符串——这是注入面，也是本方案的肘点。
**B4 修正：先加兼容的 `params` 参数**（已有调用点零改动）。以下是 `KnowledgeDB` 类方法的改法片段：

```python
def query(self, sql: str, max_rows: int = 5000, params: tuple = ()) -> tuple:
    """只读查询（C/G 修正）：独立只读连接 + fetchmany 限行，不持写锁。

    params：位置参数绑定（B4）。默认空元组——所有既有调用点行为不变。
    """
    safe_path = DB_PATH.replace("\\", "/")
    conn = sqlite3.connect(f"file:{safe_path}?mode=ro", uri=True, timeout=5.0)
    try:
        cur = conn.execute(sql, params)
        # 原有 fetchmany / 列名映射保持不变
        rows = cur.fetchmany(max_rows + 1)
        cols = [d[0] for d in cur.description]
        return [dict(zip(cols, r)) for r in rows[:max_rows]], len(rows) > max_rows
    finally:
        conn.close()
```

查询契约（K3.1 B4 逐条约束）：

| 约束 | 要求 |
|---|---|
| 参数绑定 | `since` / `until` / `grp` **一律走 `params`**，禁止字符串插值进 `ts` 或 group 值 |
| 分组白名单 | `by` 只接受 `model`→`model_requested`、`provider`→`model_resolved`、`user`→`user_id`、**`session`→`session_key`**、**`session_epoch`→`session_epoch`** 共 5 项；未知 `by` 返回 400，**禁止把 `by` 直接拼进 SQL** |
| 日期桶 | 按 `substr(ts, 1, 10)` 分天；**`by=session` 时禁用日期桶**——按 §1.4 后果 1，会话曲线不允许跨天切断；响应体显式标注 `bucketing:"none"` |
| 上界 | `until` 进 `WHERE`：`ts >= ? AND ts < ?`（半开区间） |
| eligible 集 | **所有** `by` 取值统一统计 `prompt_tokens IS NOT NULL AND user_id != 'delegate'`（session 类额外加 `session_key IS NOT NULL`）；n 必须就是该集行数。**delegate 合成行在所有分组下都排除**，不得在 session 分组里纳入（K3.1 F5） |
| 响应形状 | 通用：`{"method":"offset","since":...,"until":...,"by":...,"bucketing":"day|none","rows":[{"bucket","group","n","p50","p90","p99","max","sum","first_ts","last_ts"}], "excluded":{"delegate":N,"unknown_session":M,"unknown_prompt":K}}`；`excluded` 三项都返回，历史行 `session_key IS NULL` 计入 `unknown_session`，不静默丢弃 |
| **`by=session` 专属** | 每行必带 `session_epoch_max`（该 key 观测到的**最大长停顿分段序号**，不得称作 resume 次数）与 `epoch_hist`（固定为 `{"epoch_hist":[{"epoch":0,"n":4},{"epoch":1,"n":1},...]}`，按 epoch 升序，**不接受 dict / list 自选**） |
| **`by=session_epoch`** | 分组键为 **`(session_key, session_epoch)` 复合组**，不是把所有会话的 epoch 0 合并；`group` 字段返回 `[session_key, session_epoch]` 二元组 |

**分位数用偏移法（A1 实测已否掉 `PERCENTILE_CONT`）**。所有 SQL 经 `kdb.query(sql, params=...)` 走（§2.4 上方 B4 修正段），不得另开 `conn_factory.execute` 直连：

```python
# proxy_core/stats.py（新增，只读查询，不碰内存统计）
_QUANTILES = (0.50, 0.90, 0.99)

_BY_WHITELIST = {
    "model":         ("model_requested",  "day"),
    "provider":      ("model_resolved",   "day"),
    "user":          ("user_id",          "day"),
    "session":       ("session_key",      "none"),
    "session_epoch": ("(session_key, session_epoch)", "none"),   # 复合分组（K3.1 F5）
}

def quantiles(kdb_obj, since: str, until: str, by: str = "model"):
    """统一经 kdb.query(params=...)；返回 (rows, excluded, method, bucketing)。

    偏移法：k = round(q*(n-1))，LIMIT 1 OFFSET k 取**第 k+1 个**（0-based k）。
    ⚠️ 1..100 的 p50：k=round(49.5)=50 → 取排序后第 51 个 → **51**（不是 50）。
    """
    entry = _BY_WHITELIST.get(by)
    if entry is None:
        raise ValueError(f"unknown by={by!r}; allowed: {sorted(_BY_WHITELIST)}")
    col, bucketing = entry
    composite = by == "session_epoch"

    grp_sel = ("[session_key, session_epoch]" if composite
               else col)
    grp_by = ("1, 2" if composite else "1")

    where = ["ts >= ?", "ts < ?", "prompt_tokens IS NOT NULL",
             "user_id != 'delegate'"]
    params = [since, until]
    if not composite and bucketing == "none":
        where.append(f"{col} IS NOT NULL")
    if composite:
        where.append("session_key IS NOT NULL")
    where_sql = " AND ".join(where)

    base = ("select %s grp, count(*), sum(prompt_tokens), max(prompt_tokens),"
            " min(ts), max(ts)" % grp_sel)
    if bucketing == "day":
        base += ", substr(ts, 1, 10) as bucket "
    else:
        base += ", null as bucket "
    base += f"from requests where {where_sql} group by {grp_by}"
    rows_raw, _truncated = kdb_obj.query(base, params=params)

    out = []
    for r in rows_raw:
        grp = r["grp"]
        n = r["n"]
        vals = {}
        for q in _QUANTILES:
            k = int(round(q * (n - 1)))
            row2, _ = kdb_obj.query(
                f"select prompt_tokens from requests where {where_sql} "
                + (f"and session_key = ? and session_epoch = ? " if composite
                   else f"and {col} = ? ")
                + "order by prompt_tokens limit 1 offset ?",
                params=((*r["grp_key"], k) if composite else (*params, grp, k)))
            vals[q] = row2[0]["prompt_tokens"] if row2 else None
        out.append({
            "group": grp,
            "n": n, "p50": vals[0.5], "p90": vals[0.9], "p99": vals[0.99],
            "max": r["mx"], "sum": r["total"],
            "first_ts": r["min_ts"], "last_ts": r["max_ts"],
            "bucket": r["bucket"],
        })
    excluded = {"delegate": ..., "unknown_session": ..., "unknown_prompt": ...}
    return out, excluded, "offset", bucketing
```

> **注意**：`grp` 的复合二元组（`by=session_epoch`）在 Python 侧需要额外一次 `split`/解包，
> 上面伪码用 `r["grp_key"]` 表示；**编码手须用真实 SQL 的 `group_concat` 或两次查询实现，
> 不得让 SQLite 直接返回二元组**（SQLite 不支持）。
>
> `where_sql` 里含 `col`——**只**从 `_BY_WHITELIST` 取值，不来自外部输入（B4 约束，注入面）。
> 历史行 `session_key IS NULL` 计入 `excluded.unknown_session`，不静默丢弃。

### 2.5 `model_resolved` 的取值（B5：此处钉死，不由编码手自定）

`by=provider` 的分组口径统一为**实际服务该请求的外部池 provider 名**：

| 请求走的路径 | `model_resolved` | 依据 |
|---|---|---|
| 外部 provider（`providers.match(model)` 命中） | `prov["name"]` | 派发时已拿到 `prov` 字典 |
| 主账号池 | `NULL` | 主池无 provider 名，`uid` 是账号 ID |
| delegate / 合成行 | `NULL` | 无上游凭证，无 provider |

**传递规则**：在**分派那一刻**捕获 provider 名，作为参数显式传给记账点
（流式需一路传到 `_stream_body` 的记账段），**不得在记账时重新 `providers.match(model)`**——
记账发生在响应之后，此时 `config.json` 可能已被 mtime 热加载替换，重新 match 会得到不同的 provider（TOCTOU）。

**命名边界**（避免同名异义，R-013）：
- `model_requested` 继续表示**路由后向客户端公开的模型名 / alias**，本方案不改它语义，也不改称"原始客户端名"；
- 若将来需要上游真实模型 ID，**另起一列**（如 `upstream_model`），取 alias 展开后的响应 `model`，不与 provider 名混存。

### 2.5B `session_key` / `session_epoch` 的取值（钉死，不由编码手自定）

**`session_key`**：

- 来源：`proxy_core.db.ledger_skey(data, headers, key_label, remote_addr)`（**新增**，不复用 `affinity.session_key`——见 §1.4 事实 4）；
  4 级 fallback：`X-Grok-Session-Id`（qidicode 实际头）→ `X-Session-Id`（既有兼容）→ `chat["user"]` → 首条 user 消息前 512B sha256[:16] → key label / 源 IP。
  **不受 `_feature_affinity()` 开关影响**——观测与粘性选号是两件事。
- **调用点**：主池成功路径已有 `session_key` 局部变量（`_stream_body` 入参），但那是**粘性的 key**，本方案改从 `ledger_skey` 取；外部 provider / cline / minicode / opencode 路径在各自成功记账点调 `ledger_skey` 现算——纯本地计算，无 I/O；
- **历史行**：`session_key` 为 `NULL`（无法回溯补值，不做 backfill）。

**`session_epoch`**：

- 语义：同一 `session_key` 的**长停顿分段序号**；距上一请求 >48h 时 `+1`，窗口内保持（**不是"重新加载次数"，更不是精确 resume 计数**）；
- **算法（在 `flush()` 的写事务内计算，不是记账点）**：

```python
# proxy_core/db.py —— 与 KnowledgeDB 同模块，作为 flush 写事务的 helper
_EPOCH_GAP_S = 48 * 3600   # 用户 2026-11-02 拍板：停 1–2 天仍算同一段，隔 3 天才起新段。
                            # 改阈值必须同步改单测（R-001）
                            # 语义：同一 session 的"短停顿续接"（<48h）保持同一 epoch，
                            # "隔 3 天以上再续用"（>48h）切到下一 epoch。epoch 只表示
                            # "长停顿分段"，**不等于 resume 次数**（K3.1 F3 / A6）。

def _next_epoch_row(conn, session_key: str, req_ts: str,
                    batch_state: dict) -> int:
    """单行 epoch 计算。仅由 flush() 的写事务在按 buffer 顺序遍历本批时调用。

    batch_state：{session_key: [last_epoch, last_ts]}，由 flush 在同一事务内
    先以"已落盘 latest"为初始值，再逐行更新。这样本批内第 i 行看到的
    last_ts 已包含第 0..i-1 行，保证连续 2 个长间隔会 +2 而非 +1。

    返回本行的 session_epoch。
    """
    if not session_key:
        return 0
    st = batch_state.get(session_key)
    if st is None:
        row = conn.execute(
            "SELECT session_epoch, ts FROM requests "
            "WHERE session_key = ? AND session_epoch IS NOT NULL "
            "ORDER BY id DESC LIMIT 1",
            (session_key,)).fetchone()
        st = [row[0] if row and row[0] is not None else 0,
              row[1] if row else None]
    prev_epoch, prev_ts = st
    if prev_ts is None:
        ep = 0
    else:
        gap_s = int(datetime.strptime(req_ts, "%Y-%m-%d %H:%M:%S").timestamp()
                    - datetime.strptime(prev_ts, "%Y-%m-%d %H:%M:%S").timestamp())
        ep = prev_epoch + 1 if gap_s > _EPOCH_GAP_S else prev_epoch
    batch_state[session_key] = [ep, req_ts]   # 立即推进，供本批后续行看到
    return ep


def _flush_with_epoch(conn, buffer: list):
    """flush() 写事务内部：先读各 session_key 的已落盘 latest，
    再按 buffer 顺序逐行算 epoch 并写回 batch_state，最后批量 INSERT。"""
    batch_state = {}
    for row in buffer:
        row["session_epoch"] = _next_epoch_row(conn, row["session_key"],
                                                row["ts"], batch_state)
    # 批量 INSERT 列清单含 session_epoch（见 §2.3 写入链三处）
    ...
```

- **禁止由 `record_request` 或 routes 预计算**（K3.1 F3）：`record_request` 只 buffer
  原始行（含 `session_key` 与请求 ts），`session_epoch` 一律留待 `flush()` 补算。
  这样"第 1 行尚未落盘又跨第二个 48h"的 V11 反例才能正确推进到 epoch=2。
- **索引**（§2.1）：`(session_key, id)` 支撑 `WHERE session_key=? ORDER BY id DESC LIMIT 1`；
  累计曲线若按 ts 查，另建 `(session_key, ts)`——**两个索引用途分开，不混写**。
- **时区**：`requests.ts` 的 `DEFAULT (datetime('now','localtime'))` 与 `strptime().timestamp()`
  都依赖服务器本地时区。当前服务器 `CST +08:00` 是**实测事实**（K3.1 审计实测），
  不是"与时区无关"。部署到不同 TZ 前须先跑一条验收：`SELECT count(*) FROM requests
  WHERE ts <> datetime(ts, 'utc')`（若 ts 为本地时间则该式非全 0）——把时区口径显式钉死。
- **并发**：`flush()` 在 `_write_lock` 内串行执行（既有实现），`_next_epoch_row` 复用同一
  事务内的 `batch_state`，不需要额外行锁。
- **`_EPOCH_GAP_S = 48h`** 已由用户 2026-11-02 拍板确定（见 §5 A6），不再是待定项。

| V8 | 写入不阻塞请求 | 拆两个基准（K3.1 F7）：**V8a 热路径**：直调 `kdb.record_request(...)` 各 10,000 次，在**独立 test double 屏蔽自动 flush**的前提下取 p99 <100µs；**V8b 落盘**：直调 `kdb.flush()` 各 200 次（每次 50 条）取 p99，与既有 `BATCH_SIZE` 一致，不设固定阈值，只与基线对账 |
| V9 | 半套交付不允许 | 迁移故意制造失败（如临时把某列 DDL 改错）后启动：**必须**出现 `log.error` 且 kdb 进 degraded（记账 no-op），`/api/usage/quantiles` 明确返回 503 或 `"degraded": true`。**只有 `/health` 200 不得视为迁移通过**（M4） |
| V10 | 跨天会话不被切断 | 造 `session_key='u:test-a'` 共 4 行，ts 依次为 10-31 23:30、10-31 23:50、11-01 00:10、11-01 00:40（间隔均 <48h，期望全为 epoch 0）；**主断言**：`by=session` 分组结果 n=4 且 `first_ts`/`last_ts` 跨 10-31 与 11-01 两天、`bucketing=none`；**反证**：跑只读 SQL `SELECT substr(ts,1,10), count(*) FROM requests WHERE session_key='u:test-a' GROUP BY 1` 断言 10-31 与 11-01 各 n=2。不得用 `by=model` 证明 session 属性（K3.1 F6） |
| V11 | epoch 跨 48h 计数 | 造 `session_key='u:test-b'` 4 行，ts 依次为 11-01 00:10（首次 epoch=0）、11-01 23:00（间隔 22h50m <48h epoch 仍 0）、11-02 00:00（间隔 1h，仍 0）、11-02 01:00（间隔 23h50m，仍 0）；**再补 1 行 11-04 02:00（距上一条 49h >48h → epoch=1）**。`by=(session_key, session_epoch)` 端点须返回 `(u:test-b, 0): 4` 与 `(u:test-b, 1): 1` 两行；**边界**：恰好 48h 不切 epoch（`> _EPOCH_GAP_S`，非 `>=`），用 2 行 ts 差 172800s 验证。**buffer-aware 反例**（K3.1 F3）：造 3 行 epoch 递增 0→1→2，**第 1 行尚未 flush**（仍在 `self._buffer`）时读第 2、3 行，`next_epoch` 必须推进到 2 而非停在 1；此用例强制 epoch 计算落在 flush 写事务内，不得只读已落盘 |
| V12 | session_key 头识别 | 两个不同 `X-Grok-Session-Id` 值 + **完全相同的**首条 user 消息必须得到**不同** `session_key`（K3.1 F2）；同一 session id 跨 3 天必须得到同一 key。无该头的其他客户端才回落到消息哈希，且响应体里把这类 key 标为 `"heuristic": true`，不与确定 key 混排 |
