## 4. 吸收清单（核心交付）

### A 类：可移植（安全/韧性/痛点对齐）

**A-1 cf-auth 韧性修复包 —— 建议立即移植**
- **内容**（上游 xai-grok-auth 全部 fork 后演进，+150/-53）：
  1. **新文件 `bearer_fragment.rs`**（+40，纯无依赖）：`BEARER_SUFFIX_LEN=12` + 按字符（非字节）安全取 bearer 尾 12 字符的 `bearer_suffix()`——401 归因所有站点共用同一定义的「比较碎片」（取尾部因 JWT 头部与密钥前缀共享，无区分度）；含非 ASCII（CJK bearer）。我们本地 `cf-auth` **缺此文件**（`git grep bearer_fragment` 零命中）。
  2. **`retry_middleware.rs` 401 归因竞态修复**：凭证打包戳进 request Extensions（`StampedBearerSuffix` 在 `apply_auth_header` 时写入），新导出 `execute_with_stamp()` 让归因调用点直接读到「上一次实际上线路径的 bearer 尾」——避免归因时刻 re-resolve 与 401 触发的刷新竞态拿错 token；另加 `auth.retry_401` span。
  3. auth_provider/lib/visibility 的其余为文档精简。
- **价值**：401 归因遥测的一致性 bug 是真实的线上问题类型；修复小而正确（含多字节字符边界测试）。
- **成本**：极低。 translations: `xai_grok_auth`→`cf_auth`、路径重写；纯新增 + 少量 middleware 改造。cf-auth 我们 fork 后仅改过 3 次，冲突面最小。
- **建议**：**立即移植**（一个 acoustic 手一天内含测试完成；cf-auth 无独立测试门，跑 `cargo check` + 相关 crate 测试即可）。

**A-2 auth 韧性全局 review（shell auth + login 抽取对照）——建议排期1周内**
- 上游 fork 后 7 笔同步改了 sleep_gate、6 笔改了 xai-grok-auth、12 笔改了 shell/src/auth，随后整体迁至 `xai-grok-login`（含新增 `refresh_chain.rs`、`remedy.rs`、`single_flight`、`flock_wait` + loom 并发测试模型）。
- **建议**：先做一次「当前 cf-shell/src/auth 全量 vs 上游 login 状态」的 file 级 diff 审查（以文件为单位逐个裁定），把**行为修复**（如睡眠门相关、刷新链补救）逐个小步移植；**结构性抽取（login crate 化）不采纳**（见 B-6）。
- 依据本报告数据：`sleep_gate.rs` 与 `manager.rs` 单文件 diff 建议作为评审输入（本文档只确认了存在实质差异，未逐行核实全部）。

**A-3 system-power 演进跟进 —— 建议跟进移植（低风险小项）**
- Windows（我们主平台）**无行为变化**：仅文档 reflow + 新增 `hold_awake`/`SleepAssertion` 平台桩（Windows 恒无操作）。macOS/Linux 侧为 hold_awake 实现与 Clippy `indexing_slicing` deny 收紧。
- **价值**：跟随上游保持该 crate 不漂移；且 `hold_awake` API（ surgical 保活，防会话归档/登出前长任务被睡眠打断）对我们被打断的 NAS/归档类长任务有参考意义。注意本地 `cf-pager/src/notifications/sleep.rs` 已有 hold_awake 字样——移植前先查避免双实现。

## 5. 特别核查（逐项结论）

### 5.1 ① 我们的 auth 刷新链路是否有「睡眠丢 rotated token」防御

**结论：已完整持有，随 fork 继承，无需移植。** 证据：
- `crates/codegen/cf-shell/src/auth/manager/sleep_gate.rs`（完整读毕）:`SleepGate`（睡眠前**不启动**新刷新）、`InFlightGuard`（在飞计数 RAII）、`hold_sleep_ack_until_refresh_drains`（在飞刷新存在时**扣住 OS 睡眠 ack** 至 drain 或 3s 上限）、dark-wake 延迟预算（`DARK_WAKE_DEFER_MAX`）——且通过**双时钟（monotonic+wall）**计算门限（monotonic 在睡眠期停摆 + wall 跳变双量子翻转，防 gate 永久堵刷新);
- `crates/codegen/cf-system-power/src/lib.rs`：WillSleep/DidWake + `current_power_state()` FullWake/DarkWake/Unknown（Windows `PowerRegisterSuspendResumeNotification`，无 dark-wake 查询 → Unknown 语义）；
- 接线点：`cf-shell/src/auth/manager.rs`（sleep_gate 字段 + `is_sleep_gated` 刷新链检查：1584/1648 行）、`cf-shell/src/agent/app.rs`、`cf-pager/src/acp/spawn.rs`（power listener 启动，本地入口才启动）。
- 上游 fork 后 7 笔同步继续演进了 sleep_gate（现迁入 login crate）；后续演进差异在 §4 A-2 的 review 范围内（本报告确认存在差异、防偷被撤除的风险需评审时确认）。

### 5.2 ② 「Optimize per-turn tool schemas」（f1ca156，10-01）与 P0-2 的关系

**结论：该提交在 micro-tech/grok-cli 而非 xai 上游**（xai-org 推送止于 09-29，HTTP 422）。其内容=「收紧 CORE_TOOL_NAMES + per-turn 优化器接热路径」。与我们 P0-2 的关系：**P0-2 第一步（静态裁剪）已覆盖粗粒度问题上游第二步（动态细化）**，不是重叠而是互补；已「偷」到的细节：(a) tool_search 描述文案模板（"Only a core set of tools is loaded by default…"）；(b) per-turn core/active/full 计数指标；(c) 空白名单=keep-all 边界语法定为验收用例；(d) compress_schema 的 schema 压缩思路（我们 tools schema 带详 comment 。可压）；(e)「每条 schema 每次 model call 都要付钱」的成本模型话术，适合直接进入 AGENTS/token 治理文档。

### 5.3 ③ session-search / foreign-sessions 对我们多会话场景的价值

- **session-search**：我们本地已有真实 FTS5 会话搜索（cf-shell session/storage/search_fts.rs v4 + search.rs + extension + session_picker 集成），而**上游把这套拆成「lease + recovery + debouncements + BM25」的独立 crate**。价值=吸收其**故障恢复与租约模式**（损坏库隔离重建、单进程引导租约、防 NFS 卡死的有界锁），移植按压 cf-shell 真实痛点（如有会话库损坏难复现类 user report 立即做），否则纳入季度巡检。
- **active-sessions**：纯新部件，low-cost——多开检测/崩溃残留本来就是我们 cf-shell 洞察不足的部分（AGENTS §11 提及 25+ 常驻进程的现实）——**可选移植**（3 files +31 净增，极小）。
- **foreign-sessions**：设计很小心（只读元数据、WAL 写风险规避、有界性第一、网络 FS fail-soft），但对我们当前产品优先级关联低——**留档不移植**；其「读他人 SQLite 只用&only-local-WAL 事务」的安全姿势值得在涉及 MDB/DB 读取功能的设计文档中引用。
