## 二、与 qidicode 验收体系的对照（均为本会话实证事实）

| Swarm 的做法 | qidicode 现状 | 差距/启示 |
|---|---|---|
| 主 Agent 拆活分派、子 Agent 并行 | ✅ 已同构小规模实践：指挥官拆 A/B/C 三面、三路 ling 并行验收、主会话汇总裁决 | **方向已验证**；规模瓶颈在内网端点并发保护（429），非方法 |
| 完成奖励：防挂空任务 | ✅ 部分已有：CI 绿门 + R-012 复跑 + 抽验（曾抓 ling 报"✅全过"漏测 cf-shell） | 可制度化：**子代理报告必须附可复现命令，指挥官抽验**（已隐性执行，升为明文） |
| 拆分奖励：防退回串行 | ⚠️ 相反约束：内网 429 并发保护**逼我们错峰**（3 路并行即触发） | 现实边界：并行度受基础设施限制，非意愿问题 |
| 结果奖励：只认真解决 | ✅ 同构：第八版 exe 才是终点（CI 绿≠交付，编译产物才算） | 一致 |
| Attention Residue：token 效率 +24%（模型层） | 同主题不同层：我们做 agent 工具层（字符感知估算/缓存命中率/--tools 每轮 -8894） | 无吸收面（模型厂领域），**同主题印证 token 效率是行业主攻方向** |

## 三、吸收条目（方法论级，无代码）

1. **子代理报告强制度**（升 R-012 配套）：验收报告必须附"可复现命令清单"，指挥官按清单抽验≥1 条——挂空任务的 Swarm 解法搬到流程门。
2. **并行度纪律**（写 AGENTS.md 候选）：内网端点 ling 并发上限 = 2 路（3 路实测触发 429）；错峰规则已有（A 零成本先行/B 延迟），固化为编排默认。
3. **"结果奖励"原则**：每轮验收的终点定义 = 产物（exe/commit 推送）而非过程报告——与本会话实际执行一致（第五~八版 exe 逐版可验），保持。

## 四、不吸收条目

- 底层三换（模型训练层）——与 qidicode（模型使用方）无交集
- 数百 Agent 规模化——内网基础设施不支持，且 qidicode 验收场景 3 路已够
- "1000 个 AI"宣传口径——按原文自述采信"数百量级"，避免引用未经第三方验证的数字
