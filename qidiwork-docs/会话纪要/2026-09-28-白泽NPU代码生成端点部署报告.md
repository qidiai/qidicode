## 2. 链路架构（笔记本 → NPU）

```
笔记本 (Windows, G:\qidicode 合成管线)
  │  HTTPS (TLS1.2/1.3, Let's Encrypt 证书, 严格 TLS 可用)
  ▼
luyou.qidiai.ltd:8443  [腾讯云 111.231.166.204, nginx]
  │  location /baize-npu/ → proxy_pass http://127.0.0.1:8766/
  ▼
127.0.0.1:8766  ← 反向 SSH 隧道（pod 内 ssh -R 自动重连循环，5s 重建）
  │  (隧道仅绑定服务器 loopback，公网不可直达)
  ▼
昇腾算力容器 pod:8000  [GitCode 昇腾模型生态 Model Agent 终端]
  └─ vllm-ascend 0.18.0 + Qwen2.5-Coder-14B-Instruct (BF16, TP=2 双芯片)
```

设计要点：
- **复用现有 8443 端口**（安全组已开放），不新开端口、不动现有应用，只加了一个 location（改前有备份 `/tmp/luyou.bak.*`，`nginx -t` 通过后零中断 reload）
- 端点公开但由 vLLM `--api-key` 鉴权；无 key 请求返回 401
- 隧道密钥 `baize-npu-tunnel` 在服务器侧以 `restrict,port-forwarding` 授权——**无法登录 shell，仅能端口转发**

### 冷启动 SOP（新会话，全程照抄）

**① 用户操作**：浏览器进 GitCode → 昇腾模型生态 → Model Agent → 终端入口（昇腾算力容器），打开终端。

**② pod 终端——生成隧道密钥并拉权重（后台）：**
```bash
mkdir -p ~/.ssh; chmod 700 ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/baize_npu -N "" -C baize-npu-tunnel -q
cat ~/.ssh/baize_npu.pub   # ← 复制这行公钥
nohup modelscope download --model Qwen/Qwen2.5-Coder-14B-Instruct --local_dir /opt/atomgit/models/Qwen2.5-Coder-14B-Instruct > /opt/atomgit/dl.log 2>&1 &
```

**③ 笔记本——把新公钥授权到服务器（把 <PUBKEY> 换成 ② 输出的公钥整行）：**
```powershell
ssh -i "$env:USERPROFILE\.ssh\id_ed25519" ubuntu@111.231.166.204 "echo 'restrict,port-forwarding <PUBKEY>' >> ~/.ssh/authorized_keys"
```
（服务器侧 nginx 配置与旧授权密钥都是持久的，无需再动）

**④ 权重下完后（`du -sh` 到 28G、`ps` 里 modelscope 进程消失），pod 终端——起服务：**

`~/start_baize.sh` 内容（如 pod 是全新的需重写，单行粘贴）：
```bash
printf '%s\n' '#!/bin/bash' 'export PYTORCH_NPU_ALLOC_CONF=expandable_segments:True' 'export ASCEND_LOG_PATH=/tmp/ascend/log' 'export OMP_PROC_BIND=false' 'export OMP_NUM_THREADS=1' 'export TASK_QUEUE_ENABLE=1' 'export VLLM_WORKER_MULTIPROC_METHOD=spawn' 'cd /opt/atomgit' 'nohup vllm serve /opt/atomgit/models/Qwen2.5-Coder-14B-Instruct --host 0.0.0.0 --port 8000 --served-model-name qwen2.5-coder-14b --tensor-parallel-size 2 --dtype bfloat16 --max-model-len 8192 --max-num-seqs 16 --gpu-memory-utilization 0.92 --api-key 1204c34f26665bf8ff291b9c7367cff614671c664ff97266 > /opt/atomgit/serve.log 2>&1 &' 'echo vllm_pid=$!' > ~/start_baize.sh
```

> 注：上面这行 printf 会原样重建 `~/start_baize.sh`（重建脚本的标准写法），勿改参数。

`~/start_tunnel.sh` 内容（同理单行重建后执行）：
```bash
printf '%s\n' '#!/bin/bash' 'nohup bash -c "while true; do ssh -i ~/.ssh/baize_npu -R 127.0.0.1:8766:127.0.0.1:8000 -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes -o StrictHostKeyChecking=accept-new -N ubuntu@111.231.166.204; sleep 5; done" > ~/tunnel.log 2>&1 &' > ~/start_tunnel.sh
```

| 资源 | 实测值 | 实测方法 |

### 本机模型承载上限的结论

14B 权重占 28G → 剩余存储预算 ~22G + 剩余显存 ~90G。**这台 pod 能承载的模型上限 ≈ 权重 ≤22G 的任何模型**（7B 级 dense / 未来 ≤22G 的小 MoE）。

- Qwen2.5-Coder-7B（15G）：✅ 可与 14B 共存，速度升级选项
- **Qwen3.8-27B（51.8G dense）**：显存能跑（arch `Qwen3_5ForConditionalGeneration` 在 vllm-ascend 0.18 注册表内，实测确认），但**存储放不下与 14B 共存**（28+52=80G > 50G 配额）。且它是 dense 27B，单流速度预计慢于 14B。仅当愿意停 14B 腾空间时才可测（28G 释放后 52G 恰好勉强放下）
- **Qwen3.8-Flash-Next**：**六层检查全过、第七层（存储）判死**——
  1. 官方仓 Qwen/Qwen3.8-Flash-Next 存在：131 分片 335.3GB BF16（Flash 本体不开源，只有 Flash-Next 开源）
  2. 官方零量化版（AWQ/GPTQ-Int4/Int4/INT8/W4A16/A3B 六命名实测全无）
  3. **社区量化生态存在**：unsloth/Qwen3.8-Flash-Next-GGUF（167万下载），UD-Q4_K_XL 仅 **103.7GB**（4分片）+ MTP 模块 4.4GB
  4. 社区先例：双 4090（96G 显存+62G 内存）跑通 111GB GGUF（"显存不够内存凑"）
  5. 框架支持：需 vllm-ascend **0.26.0rc1 特制包**（天翼云配方 16 卡 DP2×TP8+EP；PyPI 实测存在 wheel，但要 torch 2.10/torch-npu 2.10 → CANN 8.6+，本 pod CANN 8.5.1 无 root 不可升）；或 **llama.cpp CANN 后端**（910B 上 CPU+NPU 协同模式，算子不齐自动回退 CPU，4090 先例的机制）
