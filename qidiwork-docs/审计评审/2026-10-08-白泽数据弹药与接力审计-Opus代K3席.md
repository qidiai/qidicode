# Opus 代 K3 席位终审

## Q1 弹药缺陷裁决

**裁决**：弹药无结构性缺陷，容量墙+欠训是复合死因；但 d15 长答先验压制 d18 短答信号是**真实的叠加故障**（置信度 85%）。

**三层证据链**：
1. **LM 层单调改善**（8.71→8.00→7.30，累计 −16.2%）+ **遗忘门 PASS 不动**（−39.1% 纹丝不动）→ 弹药在被模型吸收，不是没进去。
2. **26 倍剂量零响应**（HE 0×4、MBPP 0、zh ~1.2→~1.3）+ Pythia-160M/GPT-Neo-125M HE≈0-1% 的规模叙事 → 生成层天花板是**容量×欠训**（3.3 tok/param vs 文献 20-100），不是数据量不够。
3. **d15 长答先验（p50=236 字，占 1.18M 中 97%）vs d18 短答（20k，1.47%）**：剂量比例 **65:1**，d18 的短答信号在 SFT 分布里被 d15 的长回复稀释——这是弹药**结构**缺陷，不是**数量**缺陷。但即使修复（d15 长度分层重采样），**也打不过容量墙**（Pythia 160M 短答训练后 HE 仍 0-1%）。

**对 K3 替补的"长度错配论"收紧**：长度错配真实存在（d15 完成字数先验），但它是**第二阶**因素（Opus 原分配：容量 15% + 欠训 30% + 格式错位 30% + replay 20% + im_end 5%，长度错配大致吃进"格式错位 30%"的三分之一 ≈ 10%）。**第 N 席把遗忘门剔出根因证据链**后，剂量-响应曲线才是弹药评价的唯一客观口径——而曲线显示：弹药在 LM 层**全被学到**，死因在 M 不是 D。

**封箱叙事**：120M LLM 失败不是弹药罪，是容量×欠训的物理裁决。SFT v3（tokenizer 手术 + 2ep + replay 减半）过门概率 &lt;15%，但**必须跑一次封案**——否则容量墙是推论不是实证。

## Q2 接力文档缺漏

**四处漏雷**（按严重度）：

1. **数据传输通道缺位**（S0 级）：d17（1.27M 条）/ d18（20k）/ d19（492）/ d20（5000）从**我们容器**到**桌面容器**的路径**全文未写**。Git 通道单命令槽 ≤8KB stdout 载不动，这些数据估算 **~500MB-2GB 文本**；桌面 /tmp 蒸发 + /opt 45-48G 已用——落盘位置也没定。**Phase D 的 d17-d20 弹药用不上就是空炮**。

2. **CANN host 开销 0.7ms/op × 3113 ops/token 未进文档**（S1 级）：这是**训练吞吐的硬约束**（host 提交主导，框架内无解），K3 分析里有、接力文档没有。27B 卡时预算（44-88 卡时）里**没算 host 开销**——实测训练吞吐可能再降 2-5×，最坏卡时翻到 **200-440**，Phase A 预算爆表而桌面不知道。

3. **R-A（尾 4 层线性注意力）/ R-D（vocab 未闭环）的 fallback 树全缺**（S1 级）：§4 只说"预注册 + 断言"，没写**"闸门不过怎么办"**。R-A 若坐实 chunk_gated_delta_rule，跨 pass 状态携带 vs 重置如何适配？R-D 若 Phase D 前 vocab 仍 None，是降级到不碰 embed 的 LoRA 还是停工？**没有决策树 = 现场判断 = 翻车**。

4. **Phase A exit criteria 未定**（S2 级）：§0 恢复双触发器写得清楚，但 Phase A **成功判据没写**——50 步冒烟 go 完到哪里算过？val_ppl 下降多少 + grad_var 多少 + 遗忘门预评阈值？没有量化出口，桌面线会**要么无限 spike，要么过早宣胜**。

**次级（S3）**：桌面 bashrc 未验证的 fallback 没有、ckpt 三层口径的监控脚本未附、J2 恒等检查（read_proj=0/alpha=0/LoopNorm=1）没升级成 SOP 的 go/no-go 工具。

## Q3 RAG 路线最大风险

**最大死点不是速度，是"数据管线与 RAG 的类别错位"**（置信度 90%）。

**三选一的真实排序**：

1. **第一死点 · 类别错误**：d17-d20 是 **SFT 指令-回复对**（instruction tuning data），**不是 RAG 知识库**（knowledge corpus）。RAG 栈需要的是：① 建筑领域文档语料库（S5 嵌入入库）；② RAG eval set（query → expected retrieved docs → expected answer）。**d17-d20 在纯 RAG 管线中根本用不上**——K3 席位"三块拼图现成"的叙事在"数据"这一块是**误导**。要么把 Flash-Next 做 LoRA（但那是另一条路线，已被 K3 自己判为高风险）；要么承认 RAG 栈的"数据"是**零**，需要新建知识库和 eval set。

2. **第二死点 · 产品体感**：Flash-Next 1.9-2.4 tok/s + CANN host 开销 → RAG 单查询典型答案 200-500 token = **100-250s/query**。Demo 可以，产品不行。CANN host 开销框架内无解，没有加速退路。

3. **第三死点 · 忠于检索**：Flash-Next 125B MoE 未做指令微调（在我们这里），prompt-based "引用约束"在未对齐模型上**脆弱**；S5 又是建筑行业专精，域外查询检索质量未知。幻觉 + 域外双重放大。

**合流 RAG 的真实工作量**：K3 预估 2-3 天**严重低估**——那是接口粘合的时间，不含**构建知识库**（建筑文档清洗/切块/入库，~1 周）+ **建 eval set**（~2 天）+ **prompt 迭代**（~2 天）。真实预算 **1.5-2 周**，且产品形态仍是 Demo 级。

## 一句话总裁决

**弹药无罪（LM 层全吸收 + 遗忘门锁死），容量×欠训是物理死因；接力文档四处漏雷（数据传输/CANN host/闸门 fallback/退出判据）必须堵；RAG 旗舰最大风险是"d17-d20 是 SFT 数据不是 RAG 知识库"的类别错位——K3 的"三块拼图现成"在数据一块是幻觉，先用 0.5 天把数据映射写死再谈 2-3 天合流。**
