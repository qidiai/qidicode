## 4. P3-b 四站点竞态评估（只评估，未改码）

四站点均为 401 归因在**归因时刻**读 live/pre-send 快照（re-resolve 竞态残留），与上游修复范围一致
（上游只修 sampler + tools 链）。共同影响面：遥测 `is_stale_snapshot` 字段准确性，**无功能破坏**。

**关键减项发现**：`cf-auth` 已内置 A-1 stamp 机制——`execute_with_stamp` + `StampedBearerSuffix`
（`retry_middleware.rs:16-31`，`lib.rs:16` 导出，已有单测 :286-330）：middleware 在发送时刻把
`bearer_suffix(token)` 塞进 request extensions，调用方经 `execute_with_extensions` 侧通道取回。
该机制正是为"middleware 持有 Authorization 头"的客户端准备的——即这四个站点。**修复 = 把各站点的
`client.execute(req)` 换成 `execute_with_stamp(&client, req)` 并把返回的 `Option<StampedBearerSuffix>`
线程进归因调用**（中间件 extensions 编排已完成，剩机械接线）。当前无任何生产调用点（A-1 只建了机制，
sampler 侧走的是自捕 header 尾片的 SentRequest 路线）。

### 站点 1 — storage（`cf-file-utils/src/storage_client.rs:633-637`，8 个调用点）
- **归因时刻读什么**：`self.credentials.snapshot().token`——归因时刻 live 快照（re-resolve）。
  代码注释自认可竞态："not the exact wire bearer — a refresh may have occurred between send and 401 response"。
- **发送路径**：Authorization 头由 `AuthRetryMiddleware` 在发送时刻从同一 provider 盖上
  （`with_auth_retry` :476；`add_common_headers` 不带 Authorization）。
- **竞态窗口**：发送→401 响应（ms 级，慢网络可达请求超时）。刷新落在窗口内 → 归因记的是新 token，
  与 held token 一致 → `is_stale_snapshot=false` 假阴性（漏报 stale）。
- **修复成本**：中。8 个 `fire_401_attribution` 调用点分散在 check_exists/batch_check_exists/
  batch_upload/batch_upload_json/upload/upload_file/upload_stream 等路径；且头由 middleware 盖上，
  client 代码拿不到实际 wire 值。务实方案：每次 execute 前 `credentials.snapshot()` 一次取尾片并作为
  参数传入（窗口从 发送→响应 缩到 快照→发送 μs 级），约 8 小改 + 1 helper。不能直接套 A-1 的
  SentRequest 类型（头不在自己手里），但原则（发送时刻 stamped fragment）可复用。
- **建议排期**：与 feedback 同批，随 registry 之后。

### 站点 2 — feedback（`cf-shell/src/agent/feedback_client.rs:440-456`）
- **归因时刻读什么**：`self.credentials.deployment_key.or(self.credentials.user_token)`——**构造时刻**
  的静态字段，不是 live resolve。
- **发送路径**：`send_json`/`send_empty` → `with_auth_retry` + `ShellAuthCredentialProvider`
  （live resolve，发送时刻盖章）。
- **竞态窗口**：client 存续期（feedback client 通常按批构造，秒~分钟级）。有 AuthManager 时
  wire token 是 live 的，归因却报构造时刻静态 key → 与 held token 不一致 → `is_stale_snapshot=true`
  假阳性（几乎必然，只要登录态 token 与静态字段不同源）。
- **修复成本**：中低。仅 2 个发送咽喉点（send_json/send_empty）；同 middleware-owns-header 问题，
  发送前 resolve provider 取尾片传入 `record_401_attribution_if_needed`。
- **建议排期**：与 storage 同批。

### 站点 3 — session registry（`cf-shell/src/agent/session_registry_client.rs:225-239`）
- **归因时刻读什么**：`self.credentials.resolve()`——归因时刻 live re-resolve，**正是 A-1 缺陷类**。
- **发送路径**：单一咽喉点 `send_authed`（:184-207）→ `with_auth_retry` + live provider。
- **竞态窗口**：发送→401 响应（ms 级）。刷新落窗口 → 假阴性。
- **修复成本**：**低**。唯一发送咽喉点 `send_authed`；捕获 provider 尾片（execute 前一次 resolve）
  或把 sent fragment 从 `send_authed` 线程到 `check_response`→`record_401_attribution`，
  1 helper + 2 调用点。A-1 stamp 模式直接适用。
- **建议排期**：四站点中排第一（最便宜且是精确 A-1 类）。

### 站点 4 — idle-resume（`cf-shell/src/session/acp_session_impl/session_setup.rs:360-412`）
- **归因时刻读什么**：`creds`（:362 `chat_state_handle.get_credentials().await`）——**请求前**快照，
  且取自 `am.auth().await`（:369，可能主动刷新）**之前**。
- **发送路径**：每次调用现构造 `middleware_client = with_auth_retry(shared_client(), provider)`，
  middleware 发送时刻盖 live token。
- **竞态窗口**：get_credentials→发送，含一次潜在主动刷新（百 ms 级）。方向与其他三站点**相反**：
  归因片段比 wire token 旧一代 → 与 held token 不一致 → `is_stale_snapshot=true` 假阳性——
  且恰好发生在"空闲恢复且 token 已过期"这条本代码要守护的路径上。
- **修复成本**：中。单一站点，但 provider 在作用域内、middleware 现构造，可发送前 resolve 一次
  取尾片（窗口缩到 μs 级）；更干净的做法是 middleware 暴露 last-sent fragment。
- **建议排期**：registry 之后。

**总结**：registry（低）→ idle-resume（中）→ storage（中）/feedback（中低）同批。
四站点的修复都不改变断言语义或功能行为，纯遥测准确性提升，可作为独立 "attribution fidelity"
跟进 PR，与本批（sampler+tools 链）分离。
