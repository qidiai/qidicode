## 根因机制（实测实锤，2026-10-09 PTY 诊断）

**pager 首帧前的 inline-viewport 启动 probe 在 ConPTY 下死锁——不是渲染慢，是首帧根本没渲染。**

诊断链（自建临时诊断测试实测，用后已删）：

1. `diag_first_bytes`（逐秒抓 raw 字节十六进制）：pager 进程活着（running=true），但 **15 秒内只输出 4 字节 `1b 5b 36 6e` = `ESC[6n`（cursor-position 查询），之后完全沉默**。屏幕空白。
2. `respond_to_queries(true)` 因果实验：harness 改为回答查询后，**pager 立即活**——完整 TUI 渲染（spinner / 模型选择器 / 登录状态），welcome 秒出。
3. 修复后分步计时（`diag_scroll_steps`）：welcome **1.99s**、30 次 PageUp 最慢仅 **48ms**（零次超 1s）、50 次滚轮 516ms、全流程 15.85s——**滚动路径本身完全健康**（prepare_layout 增量 / render 增量 / scroll 纯 offset，指挥官此前排除的 1/2/3 全部正确）。

**机制闭环**：
- pager 默认 TUI = inline viewport；`cf-ratatui-inline` 的 `compute_inline_size`（terminal.rs:1274）首帧构造时调 `backend.get_cursor_position()`（crossterm 0.28.1，Windows 走 Win32 API）。
- raw_output 里出现 `ESC[6n` 且回复后解锁 → 查询-回复死锁在 ConPTY 链上：ConPTY（conhost）把子进程的设备查询转发给 ConPTY 客户端（harness 扮演的"终端"）而非自己回答；pager 的位置查询（Win32 经 conhost）与 conhost 的转发同步互相等待。
- harness 的 alacritty 终端（ptyctl）解析到该查询后会产生 CPR 回复排进 `drain_responses`，但 `respond_to_queries` 默认 **false** → 回复被丢弃 → pager 永远等 → 首帧挂死。
- **真实终端（Windows Terminal 等）自动回复设备查询 → 真人使用不受影响**——这是 harness 仿真保真度缺陷，非产品 bug。
- 46.6 分钟 / scroll_matrix 3.5 小时的机制：首帧挂死是单点，各处 deadline（welcome 20s / top marker 30s / settle 45s / matrix CELL_HARD_CAP 60s）连环超时 + 挂死状态下 PTY 链清理等待堆积 = 时长爆炸。scroll_matrix 178 case 全撞 60s 硬上限 ≈ 3 小时，与实测吻合。
