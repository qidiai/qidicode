## 2. 缺陷与修复对照

### 缺陷 A — 401 归因同构竞态（re-resolve）
- 旧：`cf-sampler/src/client.rs` `current_sent_bearer_prefix()` 在 401 时刻 re-resolve `bearer_resolver.current_bearer()`——与发送时刻的独立 resolve 之间任何轮换 → 归因读到错误代次的 token。
- 修：`post()` 在**构造 headers 的时刻**把凭据尾片 stamp 进 `SentRequest { builder, sent_bearer }`（`sent_fragment_from_headers` 从最终 headers 提取 `bearer_suffix`）；六 arm（chat_completion / chat_completion_stream / create_response / create_response_stream / create_message / messages_stream）把 `sent_bearer` 线程化穿过 `handle_response` / `record_401_attribution`。**re-resolve 路径彻底删除**；`current_sent_bearer_suffix()` 降级为 auth_info 诊断专用（doc 注明 401 归因必须用 post() 捕获）。

### 缺陷 B — 前/尾片方向 bug（红→绿核心）
- 旧：sampler 取**前** 12 字符（`String::truncate(12)`）；shell `token_suffix` 取**尾** 12（JWT 共享 `eyJ0eXAiOiJh` 头部，尾片唯一）。组合效果：`is_stale_snapshot = (发送前12) != (当前尾12)` 对一切 >12 字符 token **恒 true** → 主采样链路 401 归因遥测整体失效。
- 修：两侧统一到 `cf_auth::bearer_fragment::bearer_suffix`（尾片，单一来源）。cf-sampler 的 `SENT_BEARER_PREFIX_LEN` 删除并 re-export `BEARER_SUFFIX_LEN`；cf-shell `token_suffix` 委托同一函数（30+ 调用点签名不变）。

### 缺陷 C — 非 ASCII bearer 字节切片 panic
- 旧：`truncate(12)` 按字节切，非 ASCII bearer 在字符边界 panic。
- 修：`bearer_suffix` 用 `char_indices().rev().nth(BEARER_SUFFIX_LEN - 1)`（char 边界安全）。附带修：cf-sampler 捕获路径原用 `HeaderValue::to_str()`（拒 obs-text，非 ASCII 凭据会静默丢成 `None`）→ 改 `as_bytes()` + `from_utf8`（合法 UTF-8 即接受；ASCII 头行为不变）。

## 3. 处方偏离 R-005：request extensions → 参数线程化

踩点处方要求"发送时刻 stamp 进 request extensions，401 arm 从 `response.extensions()` 读回（reqwest Response 保留请求 extensions）"。**该前提经源码实测为伪**：

- reqwest-0.13.4 `async_impl/client.rs:2604-2656`：`Request` 的 extensions 仅用于 timeout fetch；`Response` 的 extensions 由 hyper/server 侧构造，**不携带请求 extensions**。
- 因此 extensions 通道在本 crate 的 HTTP 路径上不存在。改采上游同款**参数线程化**设计（`post()` 返回 `SentRequest { builder, sent_bearer }`，片段作为 fn 参数穿过 `handle_response`/`record_401_attribution`）——满足处方的全部语义要求（发送时刻捕获、零 re-resolve），且与上游实现逐行对齐。
- 唯一合法的 extensions 通道在 middleware 侧：reqwest-middleware 的 `Middleware::handle(&self, req, extensions: &mut http::Extensions, next)` 提供 per-execution extensions 侧信道，`execute_with_extensions(req, &mut ext)` 把它还给调用方——`StampedBearerSuffix` 即住在这里（§5）。

## 4. 随包移植的上游语义（同一 commit 内的配套改动）

1. **sole auth source**：`post()` 在 resolver 接入时无条件移除 Authorization 与 x-api-key，仅当 `current_bearer()` 返回 Some 才插入新 bearer——resolver 返回 None（硬过期会话）时**不发送凭据**而非带陈旧种子 key 上线。本地无测试依赖旧行为（所有 resolver 测试均返回 Some），已全量移植。
2. **fail-closed `is_stale_snapshot`**：`match (sent_suffix, current_suffix) { ("", _) => false, (_, None) => false, (sent, Some(held)) => sent != held }`——"没发凭据"与"没持凭据"都不是 stale。
3. **`current_or_expired()`**：`compute_attribution_payload` 读 `current_or_expired()` 而非 `current()`——硬过期 token 在大多数 401 到达的窗口保持可见（`current()` 在该窗口为 None，会把该事件要填的字段全部置空）。本地 `AuthManager::current_or_expired()` 已存在（manager.rs:710）。

## 5. middleware feature 使用者核查结论（踩点存疑项）

**cf-file-utils 是真实使用者**：`crates/codegen/cf-file-utils/Cargo.toml:46` → `cf-auth = { workspace = true, features = ["middleware"] }`。因此按上游同款移植了 `StampedBearerSuffix` + `execute_with_stamp`（retry_middleware.rs）：

- `apply_auth_header` 在写入 Authorization 的同时把 `StampedBearerSuffix(bearer_suffix(token))` 插入 extensions；
- 两个新测试：`execute_with_stamp_reports_last_stamped_bearer`（stale→401→refresh→fresh→200，stamp == 末次 token 尾片）、`execute_with_stamp_is_none_when_nothing_stamped`。
- 本地 `CredentialSnapshot.token` 为 `Option<Zeroizing<String>>`（上游参考为 plain String）——保留本地形态，测试用 `.map(zeroize::Zeroizing::new)`。
