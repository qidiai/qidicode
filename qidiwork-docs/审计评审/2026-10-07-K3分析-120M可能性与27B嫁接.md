## 1 · Q1：120M 的剩余可能性还剩多少

### 判据基座（先对齐口径）
- 四门终局：遗忘门 **PASS −28.6%** / HumanEval **0/164** / MBPP **0** / 中文 **~1.3**（剂量响应终表 §一；四门裁决包 §一）。
- 剂量-响应：d18 靶向 0→26 倍，生成层 0%→0%→0%，**边际收益消失**（剂量响应终表 §三）。
- 七假设排除后唯剩"容量/欠训墙"：**3.3 token/param vs 文献 20-100**（K3 替补审计 B3；GLM 根因 H2/H6）。
- Opus 终审责任分配：**容量 120M 15% / 欠训 30% / 训练-评测格式错位 30% / replay 反向拉力 20% / im_end 模板化 5%**（Opus 仲裁 Q1）。
- 四方共识：**停止层与内容层是两个独立故障**；rep=1.2 只救停止不救内容（四方会审 §3.1、GLM F5/§1）。

### a) tokenizer 手术（im_end 注册 + 重渲染 + 重训 SFT ~6.5h）——**预期收益有界，且非内容主因**
- 手术实修的是 T1-T4 缺陷：`<|im_end|>` 被切 5 子词、BPE 边界漂移、eval id 级停止为死代码（K3 替补审计 A1 T1-T4；四方会审 E1-E6）。**这些是"停止脆弱"的放大器，不是内容根因**（K3 判 A1；四方共识 §3.5）。
- **可回收份额量化**：Opus 把 im_end 模板化定 **5%**；停止失败已被 rep=1.2 修到 10/10（GLM §1；四门裁决包 关键发现2）。故**手术相对"rep=1.2+壳重评"的增量内容收益 ≈ 5% + 残余停止脆弱**——预期 **中文 +0.2~0.4 分（1.3→约1.6-1.8），HE/MBPP 不动**。
- **注意混淆**：手术必须重渲染重训才生效（四方会审 §4 分歧2），即与"2ep + replay 减半"**捆成一次 SFT v3 跑次**。此时主导变量是 **2ep（H6）+ replay 减半（H4）= Opus 的 b+d = 50% 责任**，tokenizer 只占 5%——**别把 SFT v3 的收益记在 tokenizer 账上**。
- **壳重评（行动1）已实锤可提分**（主理人口述；对应 Opus 行动1）：它回收的是 **c) 30%**（评测裸文本 vs 训练 ChatML 壳），**零训练成本**——这是全案最便宜的一刀，已完成。
- **判决**：手术**值得做**（作为 120M 封箱的最后判决实验），但**不是救命稻草**——四门预注册判据（A/B/C/D）在 2.2 已全灭（K3 替补审计 A4），SFT v3 的**过门概率 <15%**。

### b) 预训练补训（欠训墙 6B tok）——**几何不可行，直接判死**
- Chinchilla 最优 ≈ 20 tok/param → 120M 需 **~2.4B tok**；50 tok/param = **6B tok = 23 天 @36 tok/s**（Opus 仲裁 行动3 原文："非 50 tok/param 的 23 天方案"）。
- 即便退到 2.4B tok（5-7 天）也**吞掉整周算力**，而它只攻 **b) 30%** 组件；Opus 明令"**行动1、2 跑完前禁止上任何长周期训练**"（Opus 仲裁 Q3）。
- 且代码门 0 分按规模叙事归档（Pythia-160M/GPT-Neo-125M HE≈0-1%，K3 替补审计 B3；GLM H2），补训不改代码门结论。
- **判决：6B 路线否决（几何）；2.4B 路线低 EV 否决（吞周算力换 ≤30% 组件，且四方共识判"容量墙是代码门充分解释"）。**

### c) 白泽 S5（0.66MB，BGE-M3 质 97.6%）——**这是 120M/白泽线真正"达标"的产出**
- 硬事实：S5 **0.66MB，BGE-M3 质量 97.6%（0.786/0.805），建筑行业微调**（`nas_competition/addend_baize.md` §11.16；`G:\实验测试\模型研究\白泽成果包_20260825\`；GitCode `baize-s5` 分支 commit `a5e8af2`）。
- **为什么它"达标"而 120M LLM 不达标**：120M 的失败**全部落在"指令跟随 + 精确符号执行"维度**（四门全在语义侧，K3 替补审计 A4）；**RAG 嵌入只需要表示质量，不需要指令跟随**——S5 绕开了整堵墙。
- 体量账：0.66MB vs BGE-M3 ~2.27GB = **1/237 体积**，CPU 毫秒级推理，垂直场景加成（`addend_baize.md` §11.16）。
- **判决：S5 应升格为白泽线的旗舰交付物，而非 120M LLM 的附属。120M LLM 按"封箱归档 + 容量墙定案"叙事处理。**

### Q1 一句话总裁决
**120M 生成线的剩余可能性 <15%（唯一剩余实验 = SFT v3 判决跑次，1 天）；但白泽线并未失败——它的合格产出是 S5 嵌入（已达标），战略重心应从"120M LLM 追分"切到"以 S5 为锚的自研 RAG 栈"。**

## 2 · Q2：27B 嫁接路线真实形态

### 前置：GLM 裁决复核（成立，且需再收紧一层）
- GLM：27B 从头预训被公式拆断——mix_/M3 弹药（~500M-1B tok）在 27B = **0.02-0.04 tok/param**（比 120M 更欠，与 M3 285 相差 8000-15000×），**只剩 LoRA/inter-pass 插件路线**（27B 接力审计 §5.2）。
- **本分析追加收紧**：GLM 说"LoRA-on-Qwen"，但未区分**哪一档 Qwen**。桌面"27B"实为 **Qwen3.8-Flash-Next 125B MoE（qwen4exp，GGUF Q4 111GB）**（主理人侦察）。**GGUF Q4 是推理格式、不是训练基底——它不能做 LoRA/QLoRA 打底**。GLM 的"LoRA-on-Qwen"必须落到 **dense 27B**，不是 125B MoE。

### a) LoRA-on-Qwen 可行性（GGUF 微调 / QLoRA / ZeRO 分片 / 坑位）
- **GGUF Q4 打底 = 类别错误（判死）**：GGUF 是 llama.cpp 推理格式；llama.cpp 无训练能力（legacy `llama-finetune` 只支持全精度转换+极小模型，已废弃）。QLoRA 需 **bitsandbytes 4-bit NF4** 对**冻结基底**量化——**必须用原始 BF16/FP16 权重**，微调后**再量化回 GGUF** 部署。故 125B MoE 若真要微调，链路 = 下 BF16（335GB，131 分片，`2026-09-28 报告` §10）→ QLoRA → merge → 量化 GGUF。
- **硬件账（125B MoE）**：910B×2 = **128GB HBM 总量**。BF16 250GB **放不下**；Q4 62GB 放得下但**不可训**。QLoRA 4-bit 基底 ~62GB + 激活 + 优化器，双卡紧；但 **bitsandbytes-npu / peft / deepspeed 在容器实测缺失**（27B 接力审计 §4.1；P3 裁定"容器 peft/deepspeed 均 missing"）——工具链是硬阻断。
- **CANN host 开销是训练层死结**：桌面实测 **0.7ms/op × 3113 ops/token，host 提交主导**，框架内无解（主理人侦察）；推理已慢到 1.9-2.4 tok/s，**训练吞吐只会更差**。
- **可行基底 = dense 27B**：Qwen3.8-27B dense 已部署、**20.9 tok/s**、BF16 **52G 恰好放进 64G/卡**（`2026-09-28 报告` §11）。这是 M5.1 的既定目标，也是唯一 LoRA 可行基底。
- **坑位清单（LoRA-on-dense-27B）**：① peft/deepspeed 需先装（arm64 wheel）；② **尾 4 层含线性注意力**（qwen3_5，chunk_gated_delta_rule）→ loop 语义质变（跨 pass 状态携带 vs 重置），R-A 为 S1 级转移风险，须预注册+断言（C 线回执 R-A；27B 通报 §一）；③ 恒等初始化（read_proj=0/alpha=0/LoopNorm=1）首日必做正向信号检查（27B 接力审计 J2）；④ 单卡 b1×2048 仅 1.4G 余量（P3 裁定），LoRA+inter-pass 优化器态要精算。
- **判决：125B MoE GGUF 微调否决；LoRA 唯一现实路径 = dense 27B（52G）+ 我们的 d17-d20 数据，且须先过 R-A 层型闸门与 J2 恒等检查。**

### b) 全参微调 27B 的硬件账——**物理不可行**
- 27B dense 全参微调显存需求（每参数字节）：**fp32 权重 4B + fp32 梯度 4B + AdamW(fp32 m+v) 8B = 16 B/param**；混合精度（bf16 权重 + fp32 master + Adam）≈ **16-18 B/param**。
- 27B × 16B = **432GB**；即使 ZeRO-2/3 双卡分片 = **216GB/卡 > 64GB HBM**。bf16 纯权重 54GB 也仅够**前向**，加梯度/优化器即爆。
- 对照实测：LoRA 态 b1×2048 已用 **59.9G/61.27G（余量 1.4G）**（P3 裁定）——全参需再×~8 显存。
- **判决：全参 27B 在 910B×2 128GB 上物理不可行（差 ~3.4×），只有 LoRA/QLoRA 一条路。此账独立证实 GLM 裁决。**

### c) 两线合流（S5 嵌入 + Flash-Next 生成 + 我们数据管线）= **最高价值出口，建议定为战略主线**
- **三块拼图全部现成**：
  - **检索**：白泽 S5（0.66MB、BGE-M3 质 97.6%、CPU ms）——**已达标**（§1c）。
  - **生成**：Flash-Next 125B MoE（已部署闭环，中文连贯，8 类 bug 全球首撞全修，1.9-2.4 tok/s）——**已工作**（主理人侦察）。
  - **数据**：我们的数据管线（d17 1.27M / d18 ×20k / d19 492 / d20 5000 全弹药）——**已备齐**（四门裁决包 §二）。
- **为什么这是数据管线成果兑现的最高价值出口**：120M 的失败是"模型学不会指令跟随"；而在 RAG 里 **LLM 只需在检索到的上下文上综合**（Flash-Next 胜任），**检索质量由 S5 承担**——**数据管线与嵌入模型在这里"不经过那堵墙"就能组合出可交付产品**。
- **形态**：`use_baize.py` 封装 `/embed` 端点 → 与 Flash-Next `/v1/chat/completions` 组成 RAG 管线 → 建筑文档向量化入库 → 端到端验证（`addend_baize.md` §11.16 部署步骤 1-4）。
- **风险**：① Flash-Next 速度（1.9-2.4 tok/s）与 CANN host 开销——影响体感不影响可行性；② RAG 需要生成模型"忠于检索、不乱编"——125B 有能力，但须 prompt 工程 + 引用约束。
- **判决：两线合流不否决，反而应**升为战略主线**——它是唯一"用现有资产、不赌墙、可交付"的路线。**

### Q2 一句话总裁决
**GLM"只剩 LoRA-on-Qwen"成立，但必须落到 dense 27B（125B MoE GGUF 不可训、全参 27B 不可行）；真正的最优出口不是"27B 嫁接白泽架构"，而是"两线合流 RAG 栈"——S5 检索 + Flash-Next 生成 + 数据管线，三者现成、绕过容量墙、可交付。**
