# 白泽 第五席终裁

## 分歧 1 裁决（带 EV 计算：手术回收百分比 × 中文分预期）

**裁决：GLM"值得做"成立，DeepSeek"低优先"也成立——两者不矛盾，矛盾在归账。**

EV 拆账（基于 Opus 五因子 15/30/30/20/5）：
- c) 格式错位 30% 已被 rep=1.2 壳重评回收**停止层+结构层**，但短答 3/10 硬指标未达 → **c) 实际回收约 20%，残 10%**（停止脆弱性 + 壳-内容耦合）。
- 手术命中区 = im_end 5% + c) 残 10% ≈ **净新 EV 10-15%**（上限，含边界漂移修复）。
- 中文分换算：1.3 分基线，10-15% 份额 × 当前头部空间（≈3 分）= **+0.3~0.45，落点 1.6-1.75**。GLM 的 1.6-1.8 偏乐观上限，DeepSeek 的 1.6-1.8 口径一致但判"低优先"看的是 HE/MBPP 不动——两者在同一数轴不同端。

**执行约束（这是真正的分歧焦点）**：
1. 手术必须重渲染重训 → 物理上**绑进 SFT v3 同一次跑**，无法与 2ep/replay 减半解耦。
2. SFT v3 的主导变量是 2ep(H6) + replay 减半(H4) = Opus b+d = **50% 份额**；tokenizer 仅 10-15%。
3. 故**裁决语**：SFT v3 作为 120M **封箱终判实验**跑一次（1 天，7h），手术纳入其中；但**预注册归账表**必须把 tokenizer 份额与 2ep/replay 份额拆开记（哪怕只能靠先验估计），**禁止把 SFT v3 整体收益记在 tokenizer 账上**——否则下次复盘又会误读为"手术救了命"。
4. 过门概率 **<15%**；主要价值是**闭合叙事**（动→制度有效、不动→容量墙定案），不是追分。

## 分歧 2 裁决（带风险分配与桌面可行性修正）

**裁决：A 合流 RAG 栈优先（旗舰），B LoRA spike 并行但降级为"可行性探路"，不卡产出节奏。**

风险分配表：

| 路线 | 资源依赖 | 桌面长跑依赖 | 产出可见性 | 第 7 天可交付概率 |
|---|---|---|---|---|
| A 合流 RAG | 我们容器为主，桌面仅做 Flash-Next **推理 API**（已部署、无需长跑） | **无** | 高（demo 可演） | **75-85%** |
| B LoRA spike | 桌面长跑（peft/deepspeed 安装+R-A 闸门+J2 检查+50 步冒烟） | **强**（12h 窗口+驱动未验证直冲） | 低（仅可行性信号） | 30-40% |

**桌面可行性修正（关键）**：DeepSeek 原表写"S5 RAG 栈 2-3 天"是对的，但**三份文档都没拆清桌面在 A 路线里只扮演"API 服务端"，不是训练端**——Flash-Next 已在跑、只需被调用，RAG 客户端在**我们容器**上写 `use_baize.py` + embed 服务 + 建筑文档向量化入库。桌面 12h 上限+驱动崩溃**冲击的是 B，不是 A**。这个事实两席都没点明，但它直接改变路线选择。

**B 的降级理由**：125B MoE GGUF 不可训（共识）、全参 27B 物理否决（共识）、剩下 LoRA-on-dense-27B 还要先装 peft/deepspeed+过 R-A+J2——这些**前置工程在桌面 12h 窗口+驱动未验证下，是"赌一把能不能装上"的状态**。放到第 6-7 天作为"spike"合适，放第 1-3 天挤占旗舰路线不合适。

## 新证据判（做梦数据饥饿 / 桌面 2-3 天可行性）

**做梦类比（d19 492 条 vs 285 条）——方向半对，结论反转**：
- 类比成立的部分：**少量数据 × 单次训练 ≠ 稳定表征**，285 跑 1 次梦效果差是经验锚点。
- 类比不成立的部分：d19 在 120M SFT 里不是"做梦素材"，是**靶向弹药**（d17 1.27M 已经是量的主体，d19 是边界/难例补刀）。120M 的 0 响应**不是因为 d19 太少**，是因为 d17+d18+d19+d20 四件装合训**从未在任何规模被测过**（GLM §5.1 已点明），加上欠训墙 3.3 tok/param。
- 真正指向：**这个类比反而是 A 路线的强佐证**——"百万级 chunk 的 RAG 知识库"正是服务器级做梦机制的类比对应物，S5 嵌入+建筑文档库天然提供百万 chunk，**绕过"几百条经历不够做梦"的坑**。做梦机制考古不是"120M 要补"，是"RAG 栈走对了"。

**桌面 2-3 天可行性**：
- A 路线实际路径拆分：Day A1 S5 传入+embed 服务起（我们容器，不碰桌面长跑）→ Day A2 use_baize.py 封装+Flash-Next API 对接（调桌面但不长跑）→ Day A3 建筑文档向量化+E2E 验证（我们容器为主）。**全程不需要桌面 12h 以上连续运行**，Flash-Next 已是常驻服务。
- 结论：**2-3 天在桌面当前约束下可执行**，前提是严守"桌面只做推理 API，不做训练/长跑"。
- 若 B spike 挤进来，需在桌面同时装 peft/deepspeed → **挤占 ttyd 单 tty**（GLM §4.2 已警告），风险上升。故 B 排到 A 之后。
