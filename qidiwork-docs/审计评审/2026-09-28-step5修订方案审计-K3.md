## 逐项结论

### #1 Session 持久化 → 【建议】（可行，2 个安全细节 + 1 个竞态需补）

**实证**：
- `app/lib/core/api.dart` `Session` 类纯内存（`static String? token`），类注释自承"后续若要『保持登录』可引入 shared_preferences"——step-5 根因正确。
- `pubspec.yaml` 当前依赖仅 dio/provider/url_launcher/qr_flutter——**shared_preferences 与 flutter_secure_storage 均未引入**，无论选哪个都是新增依赖（方案未写明）。
- 401 处理已存在全局拦截器：非登录请求 401 → snack + `Session.onUnauthorized()`（= `AuthModel.logout`）+ popUntil 回登录页（api.dart `createDio`）。

**结论与依据**：
1. **明文 token 风险属实且比常规更宽**：SharedPreferences 在 Android 存 `/data/data/<pkg>/shared_prefs/` XML，沙箱保护、root 可读；且实证 `app/android/app/src/main/AndroidManifest.xml` **未设 `android:allowBackup="false"`**（默认 true）→ `adb backup` 可导出明文 token。本 App JWT = 完整会话凭证且可发起资金操作（见 #2），**建议直接用 flutter_secure_storage**（Android Keystore 加密）；若坚持用 shared_preferences，必须同步补 `allowBackup="false"` 并在交付文档记录残余风险。
2. **user 对象不必持久化**：恢复流程本来就要调 `/me` 验证，`/me` 返回最新 user；持久化 user 只带来字段漂移问题。建议只存 token，`/me` 成功后置 `AuthModel.user` 再进主页。
3. **竞态存在但可收敛，方案需补三态**：
   - 恢复期间 AuthGate 现状是二态（`isLoggedIn ? RootScaffold : LoginPage`，main.dart）。冷启动有 token 但 `/me` 未返回时 `isLoggedIn=false` → **登录页闪帧 + Logo 动画白播一次** → 再跳主页。需给 AuthGate 加 restoring 态（splash/空页）。
   - `/me` 401 时会走全局拦截器 → 最终收敛回登录页（不卡死），但会**误弹"登录状态已失效"snack**。恢复路径应自行 catch 401 → 静默清持久化 token + 清 Session，不触发 snack。
   - 恢复成功需同时满足 `isLoggedIn` 双条件（`Session.hasToken && user != null`，api_service.dart AuthModel）——注意赋值与 `notifyListeners()` 顺序。

### #2 JWT TTL 168h → 【FAIL · 必须修订】（本审计唯一实质安全缺口）

**实证**：
- 现状 TTL = 24h，硬编码 `backend/app/modules/user/service.py:41` `_JWT_EXPIRE_HOURS = 24`（模块常量）；`backend/app/config.py` Settings 无该项——方案"config.py 加 `JWT_EXPIRE_HOURS: int = 168` + `_create_token` 读 settings"可行，diff 极小。
- 无 refresh token：全后端 + 全 App grep 仅 UI 刷新图标命中——"TTL 是唯一续期手段"属实。
- token_version 机制已有且接线完整：payload 写入（service.py:57）、鉴权比对（service.py:194）、改密 +1（service.py:386）、重置密码 +1（service.py:630）、每请求 `is_active`/状态校验（service.py get_current_user）。

**FAIL 依据**：
1. **token_version 不能缓解窃取**：它只在"改密/重置"后生效；而被窃 token 的攻击者改不了密（change-password 需旧密码）也不需要改——直接用 token 操作即可。step-5 方案把它列为缓解项是误判。
2. **关键证据——资金操作存在无二次校验通道**：`backend/app/modules/ledger/router.py:95-112` `/api/ledger/transfer`（用户间转账）**仅凭 JWT 即放行**（无支付密码、无邮箱码）；对比提现端点（router.py:53-61）有 P10 支付密码门。窃取 token → 调 transfer 把余额转到攻击者 UID = 直接资金损失。24h→168h 把该窗口放大 7 倍。
3. 每请求的 is_active/封禁校验（已有）只能挡"事后封号"，挡不住"窃取时点到发现"之间的窗口。

**修订要求（二选一，前置强制）**：
- a) 给 `/api/ledger/transfer` 增加支付密码（未设置则先引导设置）或邮箱码二次校验，再放宽 TTL 至 168h；
- b) 暂不动资金端点，则 TTL 折中 ≤72h，并在方案中书面记录残余风险由产品确认。
- 顺带（部署纪律，非本方案范围）：生产 `SECRET_KEY` 必须经 .env 覆盖默认值 `"change-me"`（config.py），否则 JWT 可被伪造，TTL 长短无意义。

### #3 登录动画 → 【PASS + 建议】

**实证**：
- 现状 `app/lib/views/login.dart`：`initState` 内 `_logoAnim.forward()`，1500ms 单 fade、`Curves.easeIn`——无 didChangeDependencies。v1.0 若在 didChangeDependencies 放 forward()，键盘弹出（MediaQuery 变化）即触发重播——step-5 对该错误前提的判定正确。
- AuthGate 重播机制成立：main.dart `auth.isLoggedIn ? const RootScaffold() : const LoginPage()`——登出/登录切换使 LoginPage 重新挂载 → 新 State → initState → 动画重播。✅
- BrandLogo 使用点：login.dart:137 `size:112` / home.dart:205 `size:44`——"44px 是首页 banner 不是登录页"属实。

**建议**：
1. fade + scale 0.85→1 + easeOut 方向正确（easeOut 前段上升快，低透明度窗口短，改善"不可辨"）；1800ms 偏长，建议 1200~1500ms，真机 release 包验收（profile/debug 帧率失真）。
2. **与 #4 联动**：动画"不可辨"的一半根因是资产本身（暗底海报，见 #4 目视证据）——换 512² 亮盾标后动画才谈得上可辨，两项应同批验收。
3. 预期管理：#1 静默恢复落地后，冷启动不再经过登录页，动画主要场景变为"登出后"——这正是现有架构天然支持的，无需额外代码。

### #4 Logo 资产 → 【建议 · option b 否决】

**实证（图像目视 + 像素实测）**：
- `logo.png` = **2048×2048 方图**，但内容是**竖版海报**：上 60% 盾形标，下方 "Fortalg" + "垒算智擎" 文字堆叠，右下角带"豆包AI生成"水印，暗色底。塞进 44px 方槽（BoxFit.cover + ClipRRect）= 整体缩微、文字糊、水印变噪点——step-5"海报式资源塞图标槽"根因**正确**；v1.0"BoxFit.contain"对方图无效的判断**正确**。
- `brand_board.png` = 2848×1600，目视确认是**品牌应用展示板**（官网页眉/应用图标/商务名片/后台系统四格拼贴样机 + 水印）——**不是干净横幅素材**。

**结论**：
1. **option b（brand_board.png 做宽横幅）否决**：直接用作首页 banner 会呈现"提案 PPT 截图"效果，且带水印与无关 UI 样机。只走 option a：从展示板中部抠纯盾形标，出 512×512 去水印方形图标，登录页/首页/mine 页统一替换。
2. `cacheWidth: (size * 3).round()` 正确且必要：2048² RGBA 全尺寸解码 ≈ 16.8MB，336² 解码 ≈ 0.45MB。cacheWidth 按物理像素计，3x 覆盖主流 density（4x 屏轻微降采样无感知）；与换 512² 小资源叠加后内存问题彻底消除。
3. **方案遗漏的实施细节**：`pubspec.yaml` assets 仅声明 `assets/logo.png` 一个文件（brand_board.png / brand_logo_dark.png 现存但未打包）——新 512² 资产需同步加入 assets 声明，否则打包缺失走 errorBuilder 盾图标兜底。

### #5 推荐人合并 → 【PASS + 建议】

**实证**：
- `service.py register()`：消费 `invite_code`（`User.ref_code` 匹配 → `inviter_id` → `UserInvite` 两级固化 → `_resolve_inherited_region` 辖区继承）；`referrer` 参数已接收但**未消费**（service.py register 注释明写"当前未消费，推荐关系以 invite_code 一次性固化"）——step-5 根因正确。
- Partner 表字段（models/__init__.py:175-204）：user_id / type / region_code / status / granted_by / custom_ratio / created_at——**无 referrer / invite_code 字段**，v1.0 的错误前提删除正确。
- "注册时一次性固化、注册后不可改"是分销模块底线（service.py 头注）——UI 合并为一框、提交仍走 invite_code，不触碰该底线，**安全**。

**建议（referrer 回退逻辑的契约需写死）**：
1. 优先级：`invite_code` 优先；`referrer` 仅在 invite_code 为空时生效；两者同填且不一致时 invite_code 胜（与"可同时冗余填"兼容——同值冗余时两路径殊途同归）。
2. 匹配失败行为：建议与 invite_code 一致 400"推荐人无效"——静默忽略会让用户误以为挂靠成功，分销链事后不可补。
3. 语义限定：`referrer` = 推荐人的 ref_code（邀请码），与 invite_code 同域。**不要**扩展为用户名匹配（用户名可枚举 → 恶意挂靠任意高佣账户，才是真越权方向）。限定为 ref_code 后无越权：走的是同一固化路径，攻击面与 invite_code 完全一致。
4. 测试 4 用例：invite_code 优先 / referrer 回退命中 / 两者皆空 / referrer 无效→400。

### #6 验证码校验 → 【PASS + 建议】

**实证**：
- `_email_codes` 内存 dict（email → {code, expires}，TTL 300s，同邮箱 60s 重发限频，service.py）；register 收 `verification_code` 不校验（注释明写）；`verify_email`（P10 登录态绑定）已于 d3b4b40 修复越权（按当前用户绑定邮箱比对，不再全表撞码）。
- 前端现状：login.dart 注册邮箱 validator **非空 + 格式** = 事实必填。

**结论**：
1. 校验时机：**必须在 `db.add(user)` 之前**；建议放在 409 用户名查重之后（最小 diff，不改变既有枚举权衡——该权衡 service.py 有专段论证，不动）。过期/错误 400，与 verify_email 文案风格一致。
2. 方案未覆盖的边界，需补：
   - a) **email 空 + code 非空** → 应 400"验证码需与邮箱一同填写"；现方案"跳过校验"等于静默吞掉用户输入错误。
   - b) **校验通过应同时写 `email_verified=True` 并 pop 码**——否则用户注册时已证明邮箱控制，却仍过不了 `set_payment_password` 的前置（email_verified），且 5 分钟内同码可复用注册多号。
   - c) email 非空 + code 空：邮箱必填口径 → 400"请填写验证码"；选填口径 → 放行但 `email_verified=False`。**口径定了要同步改前端 validator**（当前前端必填，前后端口径需一致）。
   - d) `_email_codes` 单进程内存：多 worker 部署注册校验会漂移——既有约束（verify_email 同受限），记 TODO Redis，不阻塞本期。
3. 测试：正确码通过 / 错码 400 / 过期 400 / 无码+邮箱（按口径）/ 码+无邮箱→400 / 通过后 email_verified=True / 码一次性。

**结论**：
