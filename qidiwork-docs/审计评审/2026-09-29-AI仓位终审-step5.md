#### P0-1 ｜ 测试用例与实现阈值矛盾："数据不足"用例在当前实现下必然失败

- **证据**：

  if n < max(2 * ADX_PERIOD, BB_PERIOD, MIN_BARS):   # 28
      return AiVerdict(bars=n, enough_data=False)
  # test_ai_sizing.py:292-302
  def test_evaluate_fail_open_on_insufficient_data():

      assert v.enough_data is False              # ← 必然 AssertionError

### P1（必修）

#### P1-1 ｜ AI 缩量可把订单压到交易所最小名义价值之下 → 策略被直接置 error 停摆（现金路径）

- **文件行号**：`backend/engine/runner.py` 补丁 R8 新增 `_ai_scale_qty`（插在 `def _trend_gate` 之前）+ R9 `gated()`；触发点在 `backend/engine/trade_mixin.py:339-342`，兜底捕点在 `backend/engine/runner.py:507-515`（基线镜像行号）
- **问题描述**：`_buy_cb` 的第 ③ 道校验是"数量×价格 < 5 USDT → `raise MinNotionalError`"，该异常一路透传到 `handle_tick` 被捕获 → **`_mark_error_and_stop`：策略置 error、写 error_reason、永久停驱动**（非重试、非跳过）。而 `_ai_scale_qty` 只处理了"缩放后 ≤0 → 返回 None"这一事实上不可达的分支（ratio≥0.1 且引擎已保证 qty>0），**没有处理"缩放后仍 >0 但名义价值跌破 5 USDT"这一真实可达分支**。
- **量化窗口**（`_plan_qty`：`max_cost = 3×budget`，`buy_by="cost"` 时首单面额 = 3B×权重/权重和）：

  | 组合 | 首单面额 | ×0.5 | ×0.1（ai_min_ratio 下限） |
  |---|---|---|---|
  | flat，B=30U，N=6 | 3×30/6 = **15U** | 7.5U ✅ | **1.5U ✗ error** |
  | martingale，B=350U，N=6 | 3×350/63 = **16.7U** | 8.3U ✅ | **1.7U ✗ error** |
  | flat，B=100U，N=6 | 50U | 25U ✅ | 5U（临界，`<5.0` 判否，险过） |

  即：首单面额落在 **5~50U** 区间的策略，一旦 `ai_min_ratio` 被热改到 0.1~0.5 且处于多头趋势市，**首次开仓即把策略打死**——恰好打死在这个新功能最该生效的场景里。App 不下发 `ai_min_ratio`（恒默认 0.5），窗口收窄到 5~10U；但 `ai_min_ratio` 已进热改白名单（0.1~0.9 合法），API/后台可将窗口拉到 5~50U。
  （旁证：App 默认参数链 `sequence` 未传→martingale、`buy_by` 未传→cost、`max_orders` 默认 8、最大仓默认 100U → 首单 3×100/255≈1.18U，**未缩放就已破线**，说明小预算组合本就贴着红线运营，缩放只是把雷区放大。）
- **证据**：

  ```python
  # runner.py 补丁 R8（新增）
  scaled = float(qty) * v.ratio
  ...
  return scaled if scaled > 0 else None      # ← 只防 ≤0，不防 scaled*price < 5.0
  # trade_mixin.py:339-342（既有，未随本提交调整）
  if float(qty) * float(price) < _MIN_NOTIONAL_USDT:
      raise MinNotionalError("首单金额低于交易所最小名义价值 5 USDT……")
  ```

- **建议修法**（二选一，推荐前者+保底组合）：
  1. `gated()` 内（或把 price 传进 `_ai_scale_qty`）加最小名义价值保护：`if scaled * price < 5.0: return {"ok": False, "blocked": "ai_sizing_min"}`——本次 tick 不买、不改账、下 tick 重试验证一次（与既有 blocked 契约完全一致；牛市里比例恢复或价格变动后自然成交）；
  2. 或保底下抬：`scaled = max(scaled, _MIN_NOTIONAL_USDT / price)`，保证"至少按最小可行面额成交"，语义上仍满足"按比例（不低于交易所下限）建仓"。
  同时把 `_MIN_NOTIONAL_USDT` 的单一来源显式化（runner 侧引用 trade_mixin 常量或复制常量并注明同口径），并补一条回归用例：`test_scaled_buy_below_min_notional_blocks_instead_of_erroring`（断言 `runner._stopped is False`、无 error、`blocked == "ai_sizing_min"`）。
- **同类次级风险（P2-4）**：`_fmt_qty` 对 LOT_SIZE 向下取整，缩放量小于一个 step 时格式化为 `"0"` → 交易所拒单 → 4 次尝试耗尽 → 连续 5 次失败置 error。修 P1-1 的最小名义价值保护可顺带覆盖绝大多数情形。

#### P1-2 ｜ 换档即静默清空引擎双键 + App 回填只读客户端标记键 → "界面开、引擎关"长期漂移

- **文件行号**：`backend/app/modules/strategy/service.py:238-252`（`apply_tier`，基线镜像行号）；`app/lib/views/strategy_edit.dart:169-171`（改前副本行号）

- **证据**：

- **影响**：用户视角"我开着追踪策略"，引擎侧空头不停买、多头不缩量——功能静默失效且无任何告警；属本提交引入的**新漂移面**（此前该开关对引擎本就是死开关，无"显示与行为不一致"的问题）。
- **建议修法**（两层都补）：
  1. 服务端：`apply_tier` 像保留 `budget` 一样保留 `trend_filter`/`ai_sizing`/`ai_min_ratio`（非网格形状参数，不属"重置为模板默认"的语义范围）；
  2. 前端：回填改为**以引擎键为准**：`_trackingOn = (p['trend_filter'] ?? p['ai_sizing'] ?? p['_tracking_enabled']) != false`；
  3. 回归：Python 侧加"apply_tier 后 ai 键仍在"用例；Dart 侧加"编辑带 trend_filter=false 的老策略回填为关"用例（扩 `tracking_toggle_payload_test.dart`）。

#### P1-3 ｜ "追踪策略"对**新策略默认开启** ＝ 默认变更资金行为；且部署即变更在途策略行为

- **文件行号**：`app/lib/views/strategy_edit.dart:170`（`_trackingOn` 缺省 true）+ `_buildParams()` 补丁后新增 `'trend_filter': _trackingOn, 'ai_sizing': _trackingOn`（`patch_flutter.py:10-18`）

## 4. 五个审计重点的逐项判定

### 4.1 数值正确性（重点 1）

- `ratio = lo + (1-lo)*score` 恒在 `[lo, 1.0]`：**成立**（`lo` clamp 到 [0.1,0.9]，score 各路有界且 clamped，权重和 1.0）。边界：score=0 → ratio=lo；score=1 → ratio=1.0；`lo=0.9` 时区间 [0.9,1.0]（用例 `test_ratio_floor_tracks_custom_min` 已锁）。
- 三信号归一**真落 [0,1]**：① DI 分歧度 `|pdi-mdi|/(pdi+mdi)`（和 0 → 0）✅；② 价格位置 `min(close/mid,2)/2`（mid≤0 → 0.5）✅；③ 动量 `(1+tanh(20·pct))/2`（tanh 有界）✅。
- clamp 边界：`0.05→0.1`、`0.95→0.9`、`2→0.9`、`"abc"/None/NaN→0.5`、`True→0.9`（bool 的数值语义由上层校验拦截，两层防御各司其职，已在测试注释中说明）✅。
- fail-open：数据不足/None/异常三路全覆券；`_score` 内部退化值有界；runner 侧 R6 再包一层 try/except（异常时沿用上次评定，不阻断趋势判定）✅。唯一残留：`_hlc` 的 `float()` 解析异常未经 evaluate 捕获（由 R6 兜住），且无正价卫生检查（P3-6）。
- **一处必须记住的口径事实**：数据充足门槛是 **28 根**（=2×ADX14，与 trend_filter 完全一致），不是 60 根；runner 每次取 60 根，故正常路径恒充足。fail-open 只在取数失败/异常时生效（P0-1 的用例写错了这个数）。

### 4.2 闸门逻辑安全（重点 2，最重要）

- **该拦没拦（bear 漏判）**：方向判定 = 末值 DI+ 与 DI− 比较（无阈值，相等即 neutral 保守拦）。强下跌序列 -DI≫+DI → bear → 拦 ✅；趋势市内 ±DI 胶着 → neutral → 拦（保守，与旧全拦一致）✅；`_ai_verdict` 缺失/数据不足 → 拦 ✅。**未发现漏判路径**。
- **不该拦的乱拦（震荡误伤）**：`bb_expansion` 恒拦（异动保护，不分方向）——维持原语义 ✅；`adx_trend + bull` 放行（#52 明文要求）✅；非趋势市（reason=None）直接放行 ✅。**真正的"误伤"在缩放侧而不在拦截侧**：见 P2-3（震荡市也缩量）。
- **与 GridEngine 记账自洽（净量语义）**：缩放只改本次回调的 qty，引擎以成交回报的净到账量落账（`grid.py:541-558`），费用/均价/止盈基线全部基于实际成交 → 记账自洽 ✅；`filled_count`/权重序列索引不受缩放影响，各单按"当时 ratio"独立缩放，属文档化行为（"每笔按当时比例"）。
- **缩放后零头/负值**：负值不可能（ratio≥0.1>0、qty>0）；**"缩放后 >0 但跌破交易所最小名义价值"这一真实分支未处理 → 策略被打死（P1-1）**；LOT_SIZE 取整归零亦未处理（P2-4）。`scaled ≤ 0 → None → {"ok": False, "blocked": "ai_sizing_min"}` 分支写了但实际不可达（死代码），恰恰漏掉了可达的那一半。
- **与熔断 waterfall 的契约一致性**：两者同为 `{"ok": False, "blocked": ...}`、均不改账、均不计连续失败、均只拦买单；差别仅在拦截位置（waterfall/market_guard 在 `_buy_cb` 内、事件循环侧；trend/ai 闸门在 `gated()` 内、worker 线程侧、桥接之前）——这反而更好：闸门拦截不占用事件循环、不产生任何交易所调用 ✅。
- **与 P1-5 僵尸策略修复（K3 上轮 P1-B）无冲突**：本提交未动 `halt:` 分支与 `_handle_halt`。

### 4.3 热改一致性（重点 3）

- 运行态同步：`update_params` 内 `if "ai_sizing" in hot or "ai_min_ratio" in hot:` → 同步两字段 + `self._ai_verdict = None`（旧评定作废，防新旧 ratio 混用）✅；非 GridConfig 字段不进 cfg_fields 循环 ✅。
- 旧 verdict 作废：直接置 None → 闸门退化为"保守拦"（趋势市）直到下次刷新重算 ✅ 安全侧失效，非危险侧。
- 两侧白名单 11 键对齐：runner `HOT_PARAMS` 与 service `_HOT_PARAM_KEYS` 均补为同一 11 键，且有 `test_whitelist_alignment_runner_vs_service` 防漂移双保险 ✅；`test_engine_pool.py` 的字面量断言也同步更新（补丁 E）✅。
- 遗漏路径：① `trend_filter` 仍不可热改（P2-1）；② `reload_params` → `update_params(parsed)` 的路径未经测试直接覆盖（现有用例只走 `update_params` 直调），跨进程落地的"作废 verdict"链路建议补一条；③ admin-web 无策略参数编辑入口（模块清单核实），不存在第三处白名单。

### 4.4 契约风险（重点 4）

- **双键半边更新**：App 路径两键同源于 `_trackingOn`，**不可能半边** ✅；但**后端热改路径可以**（P2-1），且 `trend_filter` 不可热改造成"能关缩放不能关闸门"的不对称。
- **编辑老策略回填口径**：回填写 `p['_tracking_enabled']`，**不认引擎键** → 本提交前建的策略（有 `_tracking_enabled=true`、无引擎键）显示"开"而引擎"关"；本提交后建的策略两套键一致；一旦热改单键即漂移。修法见 P1-2/P2-1。
- **换档清键**：`apply_tier` 整份覆盖 → 引擎键与标记键齐丢（P1-2）。
- **默认值不一致**：引擎缺省 False、App 缺省 True（P1-3）。
- **回测口径不一致**：回测丢键（P2-2）。

### 4.5 客户需求符合度（重点 5）

- **#52「空头暂停买入，多头 AI 比例建仓」**：字面语义**已达成**——`_trend_blocks_buy` 方向化（bear/neutral/未知 → 拦；bull → 放行），`_ai_scale_qty` 多头按 ratio 缩放；卖出永不受限（"暂停买入"的正确读法）。"ADX 分多头/空头"以 DI+/DI− 比较实现，且只在 ADX≥25 进 adx_trend 后才做方向分流 —— 与"用 ADX 分多空"一致 ✅。
- **#53「预判行情按比例建仓」**：以三信号复合评分（DI 分歧度 0.4 / 布林中轨位置 0.3 / 10 根短动量 tanh 0.3）等价达成；HSC 无公开口径已在模块头与交付文档双处注明，`_score()` 为可替换内核（接口不变：klines → score∈[0,1]）✅。客户若后续给出 HSC 定义，只换 `_score` 即可，这个接口预留是加分的。
- **可能更贴原意而被遗漏的点**：① "按比例建仓"在客户 DCA 语境里也可能指"按比例投入预算/分批建仓"，当前是等价的数量缩放（同价下 qty∝金额），建议交付说明里点明口径；② 比例无可视化（P3-8）；③ 无"HSC 口径澄清"待办项登记（建议进 backlog，防终验时客户问"HSC 呢"无从答复）。
