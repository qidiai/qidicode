## 一、自由审查发现（按严重度排序）

### 🔴 H-1（必查）全量 SFT 的内存峰值未经等比验证——冒烟只测了约 1/17 的内存轮廓

`train_sft_m4.py` 的数据准备是**单进程 Python list-of-lists → 全局 PAD → torch.tensor** 的实现（patches/train_sft_m4.py:70-196）：

- `sft_input_ids`（~6,800 万真实 token 的 Python int 对象，id>256 不进小整数缓存，每个出现一次分配一个 ~28B 对象）≈ **2.5GB 级**；
- `padded_ids` / `padded_labels`（525,537 × 768 指针矩阵，两份）≈ **6.5GB**（PAD_ID=0 与 -100 恰好共享小整数缓存，纯指针开销）；
- `sft_ids_tensor` + `sft_labels_tensor`（int64）= 2 × 525,537 × 768 × 8B ≈ **6.5GB**；replay 40k × 768 两张量 ≈ **0.5GB**；
- 且原始 list（`sft_input_ids`/`sft_labels`/`padded_*`）为模块级变量、**建张量后不释放**；每 epoch 还有 `torch.cat([sft, replay])` 再复制一份 ≈ **+3.4GB**。

合计**稳态 ~14-17GB、epoch 边界峰值 ~18-20GB（模型/NPU HBM 另计）**。冒烟仅 30k 样本（≈全量的 1/17，数据段 ~1GB），**完全没有踩到这个内存轮廓**。"冒烟先行验证全链"在**内存维度上不构成全量外推证据**。容器宿主内存未知——若 pod RAM ≥ 32GB 大概率可过，若 16GB 则启动后 10-30 分钟内 OOM 必崩。
**处置**：发射后前 30 分钟必须盯 `/tmp/sft_smoke.log` 与容器 RSS；或发射前以 `--max-samples 100000` 中规模试跑数据准备段做内存外推（不改代码的最低成本验证）。

### 🔴 H-2（必查）正式 SFT 时长估计"2.5-3h"证据不足——两个速率锚点相差 8 倍，今晚"SFT→评测"排程可能落空

runbook 阶段 6 称"2 epoch ≈ 32,800 步 ≈ 2.5-3h（768 ctx）"，隐含 ~0.3s/step。但本地证据给出**两个互相矛盾的速率锚点**：

| 锚点 | 证据 | 折算 |
|---|---|---|
| M2 实测（m2_train.log） | T0 10ep=4416s、T2=8114s、T3=8862s（6,250 步/ep，batch32×**256**） | T2 ≈ **130ms/step** |
| M3 回执反推（out_850 + 方案快照） | T2 E12 完成于 01:02，E13 ~61%（~37,200 步）于 ~11-12 时 | T2 ≈ **1.06s/step** |

SFT 是 batch32 × **768**（3× token/step）× 实际 ~35,316 步（见 M-1）：
- 按 M2 锚点外推（130ms × 3 ≈ 0.39s/step）→ **≈ 3.8h**（+数据准备/两轮遗忘评测 ≈ 4-5h）→ runbook 口径基本成立；
- 按 M3 锚点外推（1.06s × 3 ≈ 3.2s/step）→ **≈ 31h** → 今晚评测必然落空。

两个锚点无法本地裁决（M3 慢 8× 的原因未知——可能与 SFS 数据盘、并发双臂、resume 路径有关）。**一锤定音的证据就在冒烟日志里**：step 200 与 step 800 两条 loss 打点的时间戳差 ÷ 600 步 = 真实 768-ctx 步速。
**处置**：发射正式 SFT 前先取冒烟日志时间戳外推总时长，再决定"今晚评测"还是"明天评测"；排程对外承诺以此为准。

### 🔴 H-3（必改）eval_m4 代码提取丢顶格 import + max_new=256 —— pass@1 存在**结构性低估**，验收门可能被错误判 FAIL

三个独立缺陷叠加，全部压在 HumanEval 一侧：

1. **`extract_code` 从首个 `def/class/@` 行起提取**（eval_m4.py:89-116），其前的**顶格 `import` / `from typing import List` 被丢弃**。HumanEval 大量题目的签名含 `List/Set/Dict/Any` 注解——即便模型生成完美代码，拼接执行时 `def has_close_elements(numbers: List[float],…)` 在 import 丢失下 **def 语句求值即 NameError**，直接判 fail。这影响约 1/3-1/2 的 HumanEval 任务，足以把真实 5-10% 的 pass@1 压到门下。
2. **`max_new_tokens` 默认 256**：B 决策"剥围栏保留全文"训练出的模型会先写散文再写代码（f793 风格），256 token 常在代码中途截断 → 提取失败/半截代码。建议评测时提到 ≥512。
3. 好消息（不构成缺陷）：HumanEval 的 `check(candidate)`→`check(entry_point)` 改名已在 fetch 侧完成（humaneval_prompts.jsonl 164 条实测：0 条无 check 调用、0 条残留 candidate 占位），MBPP 的 ref→gen 函数名替换也已实现——**主拼接逻辑是对的**，问题集中在 import 丢失与生成长度。

**处置**：评测前修 `extract_code`（保留首个 def 之前的连续顶格 import 行，或拼接时前置标准 import 块）+ `--max-new-tokens 512`。这是**验收门判定有效性**问题，不改则门的 FAIL 不可信（过高估计失败）。

### 🟠 M-1 scheduler 的 total_steps 不含 replay —— 尾部 ~2,500 步 lr=0，"32,800 步"口径失真

`total_steps = (len(sft_ids) // 32 + 1) × epochs`（train_sft_m4.py:230）按 **525,037**（扣 500 val）计算 = 32,816；但每 epoch 实际批次 = (525,037 + 40,000 replay) / 32 ≈ **17,658**，2 epoch 实际执行 **~35,316 步**。cosine 在 32,816 步处归零后，**剩余 ~2,500 步（≈7%）以 lr=0 空转**；warmup 基数同样偏小。runbook"2 epoch ≈ 32,800 步"与调度器口径一致但与真实执行步数不符（R-008/R-006 双重命中）。危害有限（尾部本就近零学习率），但应修正口径并在 M4 报告中记实际步数。

### 🟠 M-2 遗忘门 pre/post 测量子集不一致：500 vs 300 chunks

pre-SFT 基线取 `mix526m.npz` val 前 **500** chunks（train_sft_m4.py:223），每 epoch 复测取前 **300**（:293）。前 300 是共享子集，但 pre 多出的 200 chunks 使 `(post-pre)/pre` 的回退率**系统性偏移**（多出的 200 块的难度差直接进入分母口径）。冒烟实测 26.75 → post 的门判定用的是不同子集。修法：两侧统一（都是 300 或都是 500），一行改动。

### 🟠 M-3 去污染索引面缺口：HumanEval 只索引了 prompt 字段

`decontam_check.prompt_text`（decontam_check.py:60-66）：HumanEval 记录**只取 `prompt`**（题面+签名+docstring），`canonical_solution` 与 `test` **不进索引**；MBPP 则 text+code+test_list 全进。后果：SFT 语料若混入 HumanEval 的**标准解答代码**，只有它与题面重叠 >0.5 才会被抓——self-test 注释自认"附加代码会稀释比例"，而题面+解答的混合样本 Jaccard 常落在 0.3-0.5。**"0 剔除"对 HE 解泄漏不设防**（R-002 主裁决）。CodeFuse 是中文 Python 习题集，与 MBPP/HE 的题源（初级编程题）存在天然同构风险，此缺口并非纯理论。修法：容器侧复读时把 `canonical_solution`+`test` 并入 prompt_text（一行），分钟级成本。

### 🟠 M-4 容器侧 decontam"复读"排在正式训练**之后**——检查/消费顺序倒置

runbook 阶段 6（SFT 发射）在前、阶段 7（fetch + decontam 复读 + eval）在后。复读若发现污染，**模型已经吃进脏数据**，只能重训。本地已有 1138-prompt 口径的 0 剔除结果兜底，风险被压低但未消除（本地口径不覆盖 M-3 的索引缺口）。修法：把 fetch+复读挪到阶段 4.5（训练前），成本只是把阶段 7 的前两条命令提前执行。

### 🟠 M-5 阶段 4 字节校验注定打印 MISMATCH（自设假警报）+ runbook 转写错误

实测数学：本地 sft_data.jsonl = 367,558,773 B（CRLF）；git 文本归一后 = 367,558,773 − 525,537（每行少 1 字节）= **367,033,236 B**——E1"字节差=行数"**精确成立 ✅**（这是本次审计独立复算确认的）。但 consequence 未被登记：`send_m4_deploy.py` 的校验 `got == m['total_bytes']`（manifest=367,558,773，CRLF 口径）在容器 LF 环境下**必然 MISMATCH**——一个"注定失败"的校验门。每出现一次"预期中的 MISMATCH"，团队对**真实**校验失败的耐受度就被训练一次。另：runbook 阶段 4 括注"357,052,4xx 量级"为**转写错误**（真实 367,558,773，差 ~10.5MB，两个口径都不是 357M）。修法：manifest 记 LF 字节数（367,033,236）或各分片 sha256（现字段 sha256_1k 语义不明，建议明确为"前 1KB 哈希"或改全文件哈希）。

### 🟠 M-6 train_sft_m4 无任何中间断点——中断代价 = 整个 epoch 重跑

对比 M3 v2 的步级断点（ckpt_every=5000、零重复 seek，m3_resume_commands.md §4 是本线自己建立的最佳实践），M4 SFT **只存 epoch 末** train_ckpt.pt 与 best_model.pt（train_sft_m4.py:303-309）。若 SFT 真在 4-30h 区间（见 H-2），中途任何崩溃/断电 = 丢一整个 epoch（含数据准备重启）。回放 `--replay-samples` 与调度器状态也未入 ckpt。发射风险窗口越长，此项越实。
