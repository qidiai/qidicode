# 参赛作品功能规划 v2（openJiuwen 智能体创新大赛）

> 日期：2026-10-08 ｜ 上游：[2026-10-08-立项.md](./2026-10-08-立项.md)
> 底座：QidiWork 0.1.x（G:\qidwork，实机已验证）
> 定位：功能规格与开发分期，直接指导 11-12 月 DEMO 开发；创意材料功能章节以本档为源
>
> **v2 变更（用户裁决）**：废弃 v1 的六大并列业务场景划分，改为**两级分类体系——先归几大类、大类下细分小类，目标是把办公场景全部囊括**；投标去旗舰化，降为"文书写作"大类下的最深小类。

## 一、功能总览

参赛作品 = **QidiWork 底座（已建成）+ 三层增量（本档规划）**：

```
┌────────────────────────────────────────────────────────────┐
│ 增量③ 两级场景货架 UI：大类卡片墙 → 小类目页 → 一键进入        │ ← 新 UI
├────────────────────────────────────────────────────────────┤
│ 增量② 对话路由：会话内意图识别 → 自动挂载大类人设+小类片段     │ ← 新逻辑（轻）
│         → UI 实时高亮当前大类/小类                            │
├────────────────────────────────────────────────────────────┤
│ 增量① 场景包：6 大类人设基底 × 34 小类专项片段 + 模板 + 示例   │ ← 新内容（重）
├────────────────────────────────────────────────────────────┤
│ 底座（已有，零改动复用）：agent stdio + ACP 多会话、           │
│ office-workspaces 数据面、15 技能芯片、四格式预览、产物卡片、   │
│ 权限审批、设置页、会话恢复、系统通知、安装包/升级器              │
└────────────────────────────────────────────────────────────┘
```

**设计铁律**：参赛 fork 不动内核。三层增量全部落在 GUI 侧（src-tauri + Vue）与场景包侧（新增 `~/.qidi/scenes/`），工程风险锁在已验证边界之外。

## 二、办公场景总分类体系（核心设计）

> 覆盖目标：一名中小企业办公人员的日常事务，能在货架里找到对应小类。
> 划分原则：大类按"办事性质"切（写/处理/算/会/流程/知识），互斥好懂；小类按小白求助时的说法命名（"我要写个通知"→事务文书）。

## 三、增量①：场景包（两级结构）

```
~/.qidi/scenes/
├── <category-id>/            # 大类（6 个）
│   ├── category.json         # 名称/图标/一句话/小类清单
│   ├── persona.md            # 大类人设基底（统一语气/输出规范/禁则）
│   ├── templates/            # 大类共享模板
│   ├── specs/
│   │   └── <sub-id>.md       # 小类专项片段（34 个，进入小类时叠加注入）
│   └── examples/<sub-id>/    # 小类示例任务（小白"试试看"）
└── registry.json             # 全局注册表（货架渲染数据源）
```

- **人设组装规则**：进入小类 = 大类 persona 基底 + 小类 spec 片段拼接注入——避免 34 份独立人设的维护爆炸
- `skills.map`：按大类收敛技能白名单（如"文档处理"只挂 office-tools/OCR/印章；"文书写作·标书"挂 bid-* 全套），收敛 agent 行为半径
- 场景包独立于 skills v0.1.5 包机制，参赛安装器同时装配两者

## 四、增量②：对话路由（双通道的隐式通道）

### 4.1 分层路由（DR-1，沿用 v1 决策）

- **L1 会话内路由（P0，承诺口径）**：通用对话直接说需求（"帮我写个请示"/"这份扫描件转 Word"），大类人设 + 技能白名单让 agent 自主完成——本质提示词工程，**零内核改动**；GUI 监听工具调用事件，按 技能→大类/小类 映射表实时高亮当前场景徽标
- **L2 跨会话路由（P2 增强，不承诺）**：意图分类判定大类跳转 → 自动切换工作区会话。DEMO 不做
- 兜底：映射不命中时保持"通用助手"态，宁可不切不切错

### 4.2 显式通道（一键切换，两级）

- 大类卡墙（首屏 6 张大卡）→ 点进小类目页（该大类下小类 + "试试看"按钮）→ 点小类 = 创建/进入任务工作区 + 注入 persona 组装结果
- 已有任务工作区继续沿用（WorkspaceSidebar 逻辑），升级为**大类分组树：大类 → 任务**（小类信息体现在任务模板与徽标）
- 切换不丢对话（ACP 多会话原生支持）

## 九、功能风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 34 小类铺面过大、persona 质量稀释 | 高 | 两级人设组装（基底+片段）控维护量；演示只用 P0 小类；P1 小类按模板量产、抽检 |
| 小类命名小白看不懂 | 中 | 命名用小白求助原话（"我要…"句式校验）；创意期做一轮非技术用户盲测 |
| L1 路由"场景感"不足（徽标不切/切错） | 中 | 技能→大类映射人工核准 + 兜底通用态 |
| 批注闭环赶不上 12/30 | 中 | 独立排期不阻塞主线，DEMO 脚本可剪 |
| 参赛 fork 与内核演进漂移 | 低 | 冻结内核 0.1.x 基线，只改 GUI/场景包层 |
| 标书小类去旗舰化后深度优势被淹没 | 中 | 大类一卡墙首屏位 + 标书"试试看"用最强实录演示 |

## 附：决策记录

- **DR-5**（v2 分类法）：两级体系——6 大类按办事性质切分，34 小类按小白求助原话命名，目标全场景囊括；取代 v1 六大并列业务场景（用户裁决 2026-10-08）
- **DR-6**（人设组装）：大类 persona 基底 + 小类 spec 片段拼接，反对 34 份独立人设——维护成本与一致性双杀
- **DR-1**（路由分层，沿用）：L1 会话内承诺、L2 跨会话增强
- **DR-4**（工程边界，沿用）：增量全落 GUI 侧与场景包侧，内核零改动
- **DR-7**（标书定位）：由 v1"旗舰场景"降为"大类一内最深小类"——分类学上归位，演示学上仍是最重头戏
